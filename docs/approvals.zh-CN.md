# 审批

[English](approvals.md) | **简体中文**

agent 做的有些事，在有人点头之前不应该发生。这篇文档说明：什么会被拦下等待批准、谁能批准、每条规则在哪里强制。一句话概括：**模型只负责传话，算不算数由代码决定。**

## 什么会被拦下

只有会离开沙箱的动作。目前就是 `git push`。

- 推送由出站代理拦下，它看到的是真实的请求。判断依据是请求会造成什么结果（哪些引用移到哪些提交），而不是命令长什么样，所以换一种写法绕不过去。
- 留在沙箱内部的命令默认不拦：它们做什么都留不到沙箱之外。如果某个部署仍然希望对某些本地命令询问，可以设置 `GATE_HOLD_PATTERN`（一个匹配 shell 命令的正则）。这层检查匹配的是命令文本，只能防误操作。

## 一个问题怎么提、怎么答

1. worker 被停住，上报一个问题。问题的编号由 Worker 一侧生成，容器里给出的任何东西都不会被当作编号。
2. **Brain 自己**把问题发到任务所属的对话里。它把要发生的事原样写出（不做 Markdown 渲染），并附一个只属于这一个问题的 4 位确认码。同一个作用域里，一个确认码不会给两个问题用。
3. 有人作答。模型调用 `answer_task`，带上它认为对方作出的决定。
4. 代码读取这个人自己发的那条消息，逐条检查下面的规则，全部通过才把决定传给 worker。

在飞书里，提问是一张带按钮的卡片。按下按钮等同于这个人说了“approve 码”或“deny 码”；是谁按的由飞书给出，而不是取自卡片本身。

## 规则

### 怎样才算批准

| 规则 | 强制位置 |
|---|---|
| 批准必须是问题**实际送达之后**发出的一条消息，而且整条消息就是 `approve 码`（或“同意”“批准”加确认码）。多一句别的都不算，所以“do not approve 码”不是批准 | `#answerTask`、`readDecision` |
| 决定从消息原文读出，不采用模型的转述 | `readDecision` |
| 绑定到某一个问题的消息（按了它卡片上的按钮，或者在飞书里非话题场景下直接回复那条提问）不需要重复确认码，说一句“可以”就够。同样的话在别处说，不算回答任何问题 | `readTiedDecision`、`ingest` |
| 要执行的内容太长、无法完整展示时，只能拒绝，不能批准 | `taskEvent`、`#answerTask` |
| 一条消息只能批准一个问题。一个问题只有一次决定；重试只会重发这次决定，不会产生新的决定 | `#answerTask` |

### 拒绝

| 规则 | 强制位置 |
|---|---|
| 拒绝也要说出来：`deny 码`，或者确认码旁边出现任何表示拒绝的词。一句无关的话不算拒绝 | `readDecision` |
| **任何**成员的拒绝都压过批准，不论先后，包括还在收件箱里排队的那条 | `#answerTask` |
| 如果 worker 已经按批准执行了，之后才到的拒绝会被如实报告为“来晚了”，那次批准仍归在作出批准的人名下 | `#answerTask`、`TaskSandbox.answer` |

### 谁能批准

| 规则 | 强制位置 |
|---|---|
| 消息必须来自本作用域的成员，而且是明确对 agent 说的 | `#isDecider` |
| 在群聊或仓库里，只有发起这个任务的人能批准 | `#answerTask` |
| 同一批消息里有好几个人提出请求时，任务不记发起人，于是没有人能批准 | `#dispatchTask` |
| 不是由人发起的任务（比如 CI 失败后自动派出的）不能被批准，只能被拒绝 | `#answerTask` |
| 问题没能送达任何人时，不能被批准 | `taskEvent`、`#answerTask` |
| 在仓库里，没有关联到租户用户的 GitHub 账号不算成员；只有 owner、member、collaborator 的评论才会被当作对 agent 的请求 | `#isDecider`、`connectors/github.ts` |
| 在飞书群里，只认 @ 了本机器人的消息，而且发送者必须属于安装该应用的组织 | `connectors/feishu.ts` |
| 自动事件（PR 打开、CI 失败）不算任何人的请求，也不算任何人的同意 | connector 给出 `explicit: false` |

### 改主意

| 规则 | 强制位置 |
|---|---|
| 批准必须是那个人的最后一句话。之后又说了别的，就要重新确认。“最后”按发言时间算（只要来源提供了时间），所以后发的“等一下”即使比先发的批准更早到达，也算在批准之后。这一条跨 run 生效 | `#answerTask`、`saidAt` |
| 批准人在同一时刻（就来源所能分辨的精度而言）说了两句话时，需要重新确认 | `#answerTask` |

### 在哪里作答

| 规则 | 强制位置 |
|---|---|
| 回答属于提问所在的那个对话。在 GitHub 上就是同一个 PR | `#answerTask`、`quotesOpenQuestion` |
| 在同一个飞书群里，带着某个未决问题确认码的回复不管打在哪里，都归到那个问题上；同一个人随后在原处说的话，仍然算作他之后的发言 | `ingest`（`route_by_code`）、`#saidSinceWhereTyped` |

### 事后可能变化的来源

GitHub 评论可以被编辑和删除。

| 规则 | 强制位置 |
|---|---|
| 批准只在它所依据的那条评论仍是原样时才算数。每条评论的状态是它的时间戳加文本指纹；编辑或删除会让之前的文本作废，不论通知以什么顺序到达 | `#revise`、`#standing` |
| 动手之前会向 GitHub 重新读一遍那条评论，因为变更通知可能还在路上。读不到就不批准 | `#refreshStanding`、`commentStanding` |
| agent 自己发出的提问也会被核对：仓库维护者能改别人的评论。提问只要被编辑过，哪怕又改了回去，就不能再批准，只能拒绝。要继续的话，先拒绝它（或取消任务），再重新提出请求，这样会产生一个新的提问 | `#answerTask` |
| 引用块和代码里的 @ 不算对 agent 说话 | `connectors/github.ts` 的 `ownWords` |

### 对整个任务批准

批准人可以批准一次推送，**并同时批准同一任务里之后对同样分支的推送**。

| 规则 | 强制位置 |
|---|---|
| 这必须由批准人自己说出：在他自己的消息里写 `approve all 码`，或者点卡片上对应的按钮。模型加不上去 | `wantsStanding`、`#answerTask` |
| 只对“更新或新建分支”的推送提供、记录和使用。包含标签或删除的推送，不管点了哪个按钮，都只批准这一次 | `standingEligible` |
| 范围是同一个仓库、同样的分支，并且只在这一个任务内。它确实包含之后改写该分支历史的推送，卡片会在批准之前写明 | `TaskSandbox.authorize` |

### 其他保护

| 规则 | 强制位置 |
|---|---|
| `instructions.md`（agent 的长期指令）只能在完全由成员消息触发的 run 里修改，而且不能由一条仅作为“对提问的回复”被接收的消息来改 | `#instructionEditors` |
| agent 自己发的 GitHub 评论带有标记，不会被当作任何人的话再读回来 | `connectors/github.ts` |
| 被挂起的推送，其答复只属于那一个请求，只能用一次。推送用的凭据在发出时才取，所以等待期间收回访问权就能拦住它 | `outbound.ts`、`TaskSandbox.authorize` |

系统和 worker 发来的文本是信息，不是指令。提示词里这样告诉了模型，但上面这些规则都不依赖模型是否照做。

## 审计

每次派活、批准、拒绝、取消以及对长期指令的改动，都会写入该作用域的 `audit` 表。批准的记录里保存着当时提出的问题和作出回答的那条消息。

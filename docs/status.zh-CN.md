# 现状

[English](status.md) | **简体中文**

这是很新的软件。它已经在 Cloudflare 上运行，并对真实的服务做过验证；同时它也有一份做得不好的事情的清单。两者都列在下面，供你判断它是否适合你的用途。

## 验证过什么

### 自动化测试

`pnpm test` 在 Workers 运行时里运行测试，模型和沙箱容器用替身代替，不需要 Docker、密钥或网络。覆盖范围：

- 收件箱（去重、批量）、会话隔离、工具幂等、run 的放弃、对话窗口、额度暂停、定时器和记忆规则；
- [审批](approvals.zh-CN.md)里的每一条规则、任务回报、审计和数据清理，包括对已有数据的迁移；
- 出站代理的每一条放行和拒绝规则，以及推送请求的解析（包括浅克隆产生的真实格式）；
- GitHub 的验签和归一化、GitHub App 的令牌流程，飞书的解密、验签、卡片和归一化；
- webhook 处理函数的端到端测试，使用真实的加密和签名；
- 飞书长连接：对着一个住在独立 Durable Object 里的替身，测试连接、心跳、事件及其回执、卡片点击及其应答、分片消息、拒收和退避；
- 任务对象自身对挂起问题和长期批准的记录；
- 以某个人的身份读取飞书文档（对着飞书的替身）：发出邀请、授权返回、别的账号或别的组织完成授权、链接被用两次、被拒绝、被伪造或过期、授权返回途中被收回、这个人无权打开的文档、飞书不再认可的令牌，文档里写着让 agent 去读另一篇文档、读取途中授权被收回或被替换、飞书一开始没收下邀请，以及这个人给过应用的权限比读文档所需的更多或更少。

### 在 Cloudflare 上手工验证

- 对话和记忆、定时器触发的主动提醒、租户之间和聊天之间的隔离。
- 派出沙箱任务、一个 13 分钟的长任务、任务运行中重新部署、容器被销毁后自动恢复、带旧数据的作用域升级。
- **GitHub**，用一个私有仓库和安装在它上面的真实 GitHub App：评论派出任务，任务用按该安装和仓库签发的令牌克隆，推送被拦下，一条批准评论放行，分支移动到被批准的提交，结果以 App 机器人的身份发出。另外验证了：批准评论发出后立刻删除不会生效；被编辑过的提问不能被批准；一个任务做两次推送，在 `approve all` 之后只问一次。
- **飞书**，用一个真实的企业自建应用：单聊、群里 @、带按钮的审批卡片，以及在绑定了仓库的群里批准一次推送。两种接入方式都走过；使用长连接时，消息、卡片和按钮点击都是经这条连接到达的。
- **connector 接口改造之后**：升级后重新打开了一个已有聊天作用域，迁移 12 和 13 后历史记录完整；在重新构建的镜像里跑了一个沙箱任务；在飞书群里通过卡片批准了一次推送，卡片更新为“已批准”；在 GitHub 上 @ 机器人得到了回复。没有手工走到的：答复未确认时被搁置的提问，以及“结果无法核实”这种结局，这两种只有自动化测试覆盖。

### 自动化测试没有覆盖的

带真实容器的沙箱（容器无法在测试运行时里运行，所以靠在部署上手工验证）、alarm 的自愈、任务清理。

## 已知限制

大致按重要性排序。

1. **飞书用 webhook 接入时，卡片点击偶尔会丢。** 飞书的服务器访问 Cloudflare 不稳定：见过一次点击超时，也见过一次根本没有到达。请使用长连接。长连接有自己的代价：每个应用一个常驻的 Durable Object；每次部署会重连一次；而且它必须是该应用唯一的长连接客户端。
2. **已关闭的审批卡片可能还留着按钮。** 如果某条提问的投递回执丢了，agent 会用同一个编号再发一次，以便找到它并把它关闭。飞书的文档只保证去重，不保证返回原消息的编号；拿不到的话，卡片会保持原样。点它不会批准任何东西。
3. **判断一条 GitHub 评论是不是在对 agent 说话，用的是一种简化的 Markdown 读法**，不是完整的解析器。把正文误判为代码，只会让人需要再 @ 一次；反方向的已知情况都已堵上，但不能证明已经穷尽。
4. **固定文案没有做本地化。** 飞书卡片只有中文；发在 GitHub 和控制台上的提问只有英文。
5. **沙箱里的 token 用量是容器自己报的。** 模型调用次数由代理计数并有上限，但 token 数取自 agent 日志的末尾，所以日志特别长、任务丢失或被取消时会少记。又因为这部分用量在任务结束时才入账，租户的每日额度可能被超出一些。
6. **推送没有检查 push option 和 capability，也没有限制分支。** 批准的人看到的是引用和提交，决定权在人。“对这个任务批准”包含之后改写已批准分支历史的推送。
7. **沙箱内的命令不经审查**，除非设置了 `GATE_HOLD_PATTERN`，而那层检查只是对命令文本做正则匹配。
8. **观测手段只有日志和每个作用域的健康数字。** 没有告警。
9. **对话变长时只是截断**，没有做摘要，也没有离线整理记忆。
10. **管理接口只有一个密钥**，没有角色，也没有按租户的管理权限。
11. **飞书应用的密钥和单仓库 webhook 的 secret 以原值存放在 Registry 这个 Durable Object 里**，依赖平台的静态加密。（租户的 API key 不是这样：只保存哈希。）
12. **所有租户共用一个模型密钥，而且沙箱里的 agent 只会访问 OpenAI 的接口。** `OPENAI_BASE_URL` 能改变 Brain 的去向，但改变不了沙箱里的 agent。
13. **沙箱任务的状态是整份读写的。** 已知的并发覆盖都处理了，但没有系统性地改成按字段更新。
14. **沙箱无法从 npm、PyPI 等包仓库下载依赖。** 测试可以使用镜像自带或项目随附的工具和依赖；仍需从包仓库下载依赖的测试无法按原配置运行。
15. **读取飞书文档只对着真实的飞书验证了一部分。** 已经在真实环境里看到的：授权卡片、同意、浏览器跳回。在飞书当前的接口换取令牌时，格式正确的 PKCE 校验码被拒绝（20049）；为此提供了按应用切换到较早接口的开关，但飞书在较早接口上是否校验了校验码，尚未证实。一次授权大约两小时有效（即飞书签发的令牌的有效期），目前不会续期，过期后会重新邀请授权。只能读文档（docx）和本身是文档的知识库页面，读到的是纯文本，最多 40,000 个字符。
16. **没有实现其他类型的 worker。** 调研过的一种见 [docs/research](research/)。

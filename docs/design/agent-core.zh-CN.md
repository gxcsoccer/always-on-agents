# 设计：把事做完、接得上话、有回应

状态：草案，待评审。还没有任何代码按这份文档改动。

这份文档回答一个问题：怎样让 agent 在对话里更像一个助理，同时不为某一个连接器、某一个工具写特例。它描述五个通用机制、它们对现有代码的改动，以及分几步建、每一步怎么验证。

## 1. 起因

2026-11-21 第一次在真实飞书里用"读文档"功能，记录暴露了四个问题：

| 现象 | 直接原因 |
|---|---|
| 点完授权，还要再说一句话它才干活 | 授权回调只保存令牌。原来那个请求已经结束了，没有人接着做 |
| 刚总结完，追问"第二点展开说说"，它不记得说过什么 | 读过外部内容的那次运行，结束时整段记录被替换成一句固定的话 |
| 发出消息后干等 5 到 14 秒；授权时一次冒出三条消息 | 没有"已收到"的表示；卡片由连接器自己发，模型又用自己的话说了一遍 |
| 说话像工单系统：让用户"把链接和总结一起再发一次" | 提示词是为"被事件唤醒的后台代理"写的；工具的限制被原样转述给用户 |

这四个问题都可以就事论事地修，比如"授权成功后把那条消息重放一遍"。但每一种修法到下一个连接器（邮件、日历）都要再写一遍。所以这里只做通用机制，"飞书读文档"是它们的第一个使用者，现有的"审批"和"worker 任务"是第二个。

## 2. 原则

1. **机制通用，证明各自负责。** 生命周期（等待、恢复、取消、过期）只有一套；"条件是否成立"由有资格的一方证明，互不代替。时钟只能证明时间到了，worker 只能汇报分给它的任务，只有人能批准一次推送。
2. **模型决定怎么做，运行时决定能不能做。** 该不该追问、用哪个能力、值不值得记，交给模型。能读什么、能写到哪、发给谁、留多久，由代码执行，不写在提示词里。
3. **权限跟着"这次要做的事"走，不跟着"历史上出现过什么"走。** 用户说"别读 B，只总结 A"时，A 和 B 都是他亲手贴的。
4. **来源由运行时传播，模型不能自证清白。** 模型把外部内容改写、摘要、压缩，都不会让它变得更可信。
5. **对人只有一个声音。** 所有发给人的消息经过同一个出口；状态提示可以丢，结果不能丢。
6. **每一步都保持线上可用**，并且用至少两类真实任务验证，防止"通用机制"退化成一堆行为分支。

## 3. 现在的结构（简述）

一个作用域（一个人、一个群或一个仓库）是一个 Brain 对象，里面有：

- `inbox`：所有进来的事件。
- `runs`：一次运行，即一轮"模型思考、调工具、再思考"的循环，由一批事件触发，结束就结束了。
- `items`：对话记录，也是模型的输入。
- `outbox`：要发出去的消息，按顺序、可重试、不重复。
- 三种"等一等"各有各的实现：
  - 等 worker：`tasks` 表，worker 汇报时变成一条事件；
  - 等人批准：任务上的问题、`unsettled` 表、审批卡片；
  - 等时间：`timers` 表，到点变成一条事件。

"等用户授权"是第四种，目前没有实现，所以授权完没有人接着做。

## 4. 机制一：请求可以等待，条件成立后接着做

### 4.1 概念

**请求**：一个人让 agent 办的一件事。它由这个人的一条或几条原话开始，可以跨越多次运行，直到办完、取消或过期。今天"运行结束"就等于"事情结束"，这是问题一的根源。

**等待**：请求停下来等一个条件。等待由工具通过协议声明，不由模型编造。一条等待记录包含：

| 字段 | 含义 | 例子（授权） | 例子（推送审批） |
|---|---|---|---|
| 条件类型 | 在等什么 | 某人授权某连接器 | 某人批准某次推送 |
| 谁能证明 | 只有它发来的信号才算数 | 飞书连接器 | 这个对话里有资格的人 |
| 绑定的动作 | 条件成立后要做的那一个动作，原样保存 | 重新执行那次 `feishu_read_document` 调用，参数不变 | 放行那个提交到那个分支 |
| 回复给谁 | 结果送到哪里 | 原来的单聊 | 原来的对话 |
| 何时失效 | 过期时间、被取消、被新目标取代 | 10 分钟 | 任务结束 |
| 版本 | 请求每次被修改加一 | | |

### 4.2 流程

1. 运行中，工具返回"需要等待"和上表的内容。Brain 先把等待记录写进存储，再让任何入口（卡片、链接）出现。
2. 这次运行正常结束，不占着任何资源等人。
3. 条件成立时，证明方通知 Brain："等待 X 的条件成立了"。这个通知只让请求**有资格被检查**，本身不是许可。
4. Brain 检查：通知来自声明的证明方；请求还在、版本没变、没过期。然后**从保存的原始消息重新计算权限**（和今天 `#actingFor` 的判断相同），再核对当前的授权、文档版本和回复对象。
5. 通过后，Brain 自己重新执行绑定的那一个动作，把结果交给模型继续。恢复时不会把回调伪装成"用户说了一句话"。
6. 重复通知、乱序通知只推进一次。通知丢了可以对账。

### 4.3 等待期间用户又说话了

等待中的请求会列给模型看（和今天"正在运行的任务"列表一样）。用户说"授权好了""算了""换成另一篇"都是普通消息：

- 模型理解意思，提出结构化的修改：继续、取消，或把目标换成 B；
- Brain 校验这个修改属于哪个请求、哪个版本，再执行；
- 换目标或取消后，旧版本作废：迟到的"A 已授权"通知不能再让 A 继续；
- 指的是哪一个不清楚时，由模型问人，Brain 不猜。

### 4.4 现有三种等待怎么并进来

| 现有 | 并入后 |
|---|---|
| worker 汇报 | 条件类型"任务有结果"，证明方是那个任务的 worker |
| 推送审批 | 条件类型"人批准"，证明方是有资格的人。现有的全部保证原样保留：批准的是具体的提交和分支、谁批的、被编辑过的消息不算、执行结果要对账 |
| 定时器 | 条件类型"时间到"。由定时器开始的运行**不继承**任何人的权限，和今天一样 |

第一步不迁移定时器，只把新的"授权"和已有的"worker、审批"放到同一套记录上，用两类任务验证这个抽象。

## 5. 机制二：内容带来源，按来源决定能做什么、留多久

### 5.1 现在的规则和它的代价

现在的规则（PR #5）：一次运行只要用过连接器的工具，之后只能"回复这个人"和"再读"；运行结束时整段记录换成一句话。它挡住了文档里的恶意指令，代价是 agent 记不住自己刚说过的话。之后为了让"先发链接、再说总结"能用，又加了一条"承接上一条链接，只一次，10 分钟内"（PR #8）。这两条都是特例，本节用一个通用规则替换它们。

### 5.2 三个分开的问题

每条内容分别记录：

1. **谁真的说过**：这个人、agent 自己、系统。用户贴来的一封邮件，里面的字仍然是"引用"，不是他的指令。
2. **信息从哪来**：这个人的原话，还是经某个工具从外部读来的（哪个工具、替谁读的）。
3. **允许拿来做什么**：给谁看、能不能写进记忆、留多久。

### 5.3 传播规则（第一版，保守）

- 一次模型生成的**全部输出**（回复、工具参数、摘要、重试和恢复后的输出）继承这次**实际看到的所有输入**的限制。
- 来源不明的内容按受限处理。
- 模型不能解除限制，改写和压缩也不能。

### 5.4 上下文按请求组装

为了不让"读过一篇文档"永久影响整个对话，每个请求只装进它需要的上下文：

- 只和用户原话有关的请求，上下文里没有外部内容，agent 有全部能力。
- 追问上一份答复的请求，上下文里带着那份答复（它是外部内容派生的），于是这次运行自动只能读和回复。
- 从"带外部内容的上下文"里做有副作用的事（派任务、写长期记忆、发给别人），需要这个人对**具体动作**的批准。这就是机制一里的一次"等人批准"。"读完文档去写代码"因此不需要单独设计。

### 5.5 保留策略

| 内容 | 保留 |
|---|---|
| 用户原话 | 和今天一样 |
| 外部正文、工具原始输出 | 不保留 |
| agent 发给用户的那份答复 | 短期保留，只在这个私聊里，带来源和期限；撤销授权后复查 |
| 答复里每条结论对应的出处（哪篇文档、哪个版本、哪几处） | 和答复一起保留。追问时重新核对权限、重读对应段落；文档改了或权限没了就明说，不悄悄换一份新摘要 |
| 用户明确说的偏好（"以后先给结论"） | 在一个只看用户原话的独立步骤里提取，可以查看和更正 |

外部派生的内容不进全局记忆、定时任务、日志或别的会话。

### 5.6 "这次能读哪篇文档"

不采用"目标在这个人的历史消息里出现过"作为许可。执行器只接受**当前请求已经绑定的**动作、规范化后的资源和回复对象：

- 候选来自本次明确的选择，或同一个未结束请求里明确指向的对象；
- 否定（"别读 B"）、歧义、换目标都要被表示出来，不能退化成搜历史；
- 模型负责理解"它""第二点"指什么，Brain 负责核对；
- 资源规范化、真实的访问权限、授权是否有效，仍由工具负责。

### 5.7 替换旧规则的条件

新机制要先证明等价，再删旧规则。新旧两套判断并行运行一段时间，逐例检查新放行的情况。必须覆盖：混合来源、跨会话、撤权后追问、压缩后恢复、多次追问同一份答复、两个并行请求、引用和转发、过期。新机制应当确实放行原来误拒的合法追问。

## 6. 机制三：对人只有一个出口

现在授权卡片由飞书的授权对象直接发，模型不知道，于是又用自己的话说一遍。

- 工具需要人做一件事时，返回一个结构化的"需要交互"和一个不透明的操作引用，不自己发消息。
- Brain 决定是否发、何时发，经 `outbox` 发出。连接器负责把它画成卡片或文字。
- 同一个请求、同一次等待，最多一个有效入口；完成后最多一份最终答复。
- 授权凭据、真实的授权链接、签名校验留在连接器内，Brain 和模型都看不到。
- 渠道支持编辑就更新同一张卡片（先保存消息编号）；不支持就退化成"一张邀请加一个结果"。

现有的审批卡片已经是这个形态，它是这条机制的第一个实例。

## 7. 机制四：状态信号

- Brain 在请求的真实阶段发出状态：已收到、在做什么、已完成。
- 每个连接器按自己的能力呈现：飞书可以是消息上的表情或可更新的卡片，GitHub 可以是 👀，控制台可以是一个状态字段。
- 状态走单独的、可丢弃的通道，带请求版本和序号，过期或晚到的直接丢弃。
- 状态不能拖住结果，也不能晚到盖住结果。做不到这一点的渠道就不显示独立状态。
- 最终结果、失败、需要人操作的事，仍然走有序、可重试的 `outbox`。
- 分开计时：收到消息到看得见反馈；条件满足到结果送达；人自己操作花的时间另算。

## 8. 机制五：提示词和记忆

- 提示词按**当前场景**选，不按作用域一刀切。同一个私聊里，既可能有人在等回复，也可能来一条后台汇报。
- 对话场景的原则：沿用对方已经给的材料和目标；明确就做完；只有缺一个会改变结果的信息时，才问那一个问题。不转述内部限制。
- 工具的说明同步修改，否则模型仍会照着工具的话催用户重发。
- 记忆是 agent 自己的一个可选步骤：请求结束后，在只含用户原话的上下文里决定要不要记。一句话说了两遍不算偏好，明确说"以后都……"才算。长期的、共享的写入都能追溯来源，可以更正和删除。

## 9. 接口变化（草案）

连接器工具的返回值多一种，不再自己发消息：

```ts
type ToolOutcome =
  | { result: unknown }                                  // 和今天一样
  | {
      wait: {
        condition: string;                               // 条件类型，如 "authorisation"
        prover: string;                                  // 谁能证明，如连接器名
        expires_at: number;
        interaction?: { kind: "open" | "confirm"; ref: string };  // 要人做的事；ref 只有连接器能解开
      };
    };
```

证明方通知条件成立：

```ts
brain.satisfied(waitId: string, by: string): Promise<void>   // 只表示"可以检查了"
```

通道多两个可选能力：

```ts
interface Channel {
  deliver(...): ...;                                     // 现有
  render?(interaction): unknown;                         // 把交互元素画出来
  status?(target, signal: { request: string; version: number; seq: number; phase: string }): Promise<void>; // 可丢
}
```

存储上新增 `requests`、`waits` 两张表；`items` 增加来源、受众、期限三列；`tasks` 里与等待有关的字段逐步由 `waits` 承接。

## 10. 建造顺序

每一步结束时线上都可用，并有明确的验收。

| 步 | 内容 | 用什么验证 |
|---|---|---|
| 0 | 一份最小契约：请求标识、动作/对象/受众、条件类型、版本和终态，加一组先失败的测试 | 评审通过 |
| 1 | 请求与等待（薄的一层）加"一个出口" | 授权后不再说话就收到一份结果；同一套记录承载 worker 汇报和推送审批，现有审批测试全部通过 |
| 1b | 状态信号 | 收到消息到看得见反馈的时间，在真实渠道上测 |
| 2 | 来源传播和按请求组装上下文 | 追问"第二点的依据"能答中并定位原文；新旧判断并行比较后，删除"整轮抹掉"和"承接一次链接" |
| 3 | 场景提示词（可以提前）；记忆步骤（等第 2 步成立） | 真实对话记录对比 |

## 11. 验收用例

应当成立：

- 给链接和目标、点授权，不再说话，只收到一份摘要。
- 接着问"第二点的依据呢"，答中上一份摘要的第二点，并能指出原文位置。
- 文档改版或权限被收回后追问，明确说明，不换一份新摘要。
- 进程重启、重复回调后，结果仍然只有一份。

不应当成立：

- 等待 A 时改成 B，迟到的"A 已授权"让 A 继续。
- 定时器或 worker 的通知让一次推送被批准。
- 定时器开始的运行用到了某个人的文档权限。
- 文档里写的指令，让 agent 写了长期记忆、派了任务或发给了别人。
- 用户说"别读 B"，B 仍被读取。

## 12. 没有解决和有意不做的

- 流式输出：排在状态信号之后。
- 跨作用域的记忆：不在这份设计里。
- 飞书在较早的换令牌接口上是否校验 PKCE：仍然未知，与本设计无关。
- "按请求组装上下文"里，怎样判断一个请求需要哪些历史，是这份设计里最不确定的部分，第 2 步开始前要单独细化。

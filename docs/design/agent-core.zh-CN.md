# 设计：把事做完、接得上话、有回应

状态：草案第三版，评审已确认，待定稿。还没有任何代码按这份文档改动。

这份文档回答一个问题：怎样让 agent 在对话里更像一个助理，同时不为某一个连接器、某一个工具写特例。它描述五个通用机制、它们对现有代码的改动，以及分几步建、每一步怎么验证。

读法：第 1、2 节和每个机制开头的"一句话"和例子，足够了解要做什么；其余是给实现和评审用的细节。

## 1. 起因

2026-11-21 第一次在真实飞书里用"读文档"功能，记录暴露了四个问题：

| 现象 | 直接原因 |
|---|---|
| 点完授权，还要再说一句话它才干活 | 授权回调只保存令牌。原来那次运行已经结束，没有人接着做 |
| 同一篇文档每次都从头总结，不记得刚说过什么。由此推断：追问"第二点展开说说"接不上（从代码推断，聊天里没有实际试过，是要验收的情形） | 读过外部内容的那次运行，结束时除用户原话以外的记录被替换成一句固定的话 |
| 发出消息后干等 5 到 14 秒；授权时一次冒出三条消息 | 没有"已收到"的表示；卡片由连接器自己发，模型又用自己的话说了一遍 |
| 说话像工单系统：让用户"把链接和总结一起再发一次"（链接和要求分两条发的问题，之后已在 PR #8 修过一次） | 提示词是为"被事件唤醒的后台代理"写的；工具的限制被原样转述给用户 |

每个问题都可以就事论事地修，但每一种修法到下一个连接器（邮件、日历）都要再写一遍。所以这里只做通用机制。"飞书读文档"是它们的第一个使用者，现有的"推送审批"和"worker 任务"是第二个。

## 2. 原则

1. **机制通用，证明各自负责。** 生命周期（等待、恢复、取消、过期）只有一套；"条件是否成立"由有资格的一方证明，互不代替。时钟只能证明时间到了，worker 只能汇报分给它的任务，只有人能批准一次推送。
2. **模型决定怎么做，运行时决定能不能做。** 该不该追问、用哪个能力、值不值得记，交给模型。能读什么、能写到哪、发给谁、留多久，由代码执行。
3. **权限跟着"这次要做的事"走，不跟着"历史上出现过什么"走。** 用户说"别读 B，只总结 A"时，A 和 B 都是他亲手贴的。
4. **来源由运行时传播，模型不能自证清白。** 改写、摘要、压缩都不会让外部内容变得更可信；模型也不能靠"挑选上下文"把自己之前受限时生成的计划洗干净。
5. **批准不改变数据政策。** 批准只能放行一个被看清、被冻结的具体动作，不能放行政策本来就禁止的数据流向。
6. **对人只有一个声音。** 所有发给人的消息经过同一个出口；状态提示可以丢，结果不能丢。
7. **每一步都保持线上可用**，用至少两类真实任务验证，并且不削弱现有审批的任何一条保证。

## 3. 现在的结构

一个作用域（一个人、一个群或一个仓库）是一个 Brain 对象，里面有：

- `inbox`：所有进来的事件。
- `runs`：一次运行，即一轮"模型思考、调工具、再思考"。
- `items`：对话记录，也是模型的输入。
- `outbox`：要发出去的消息。它保存的是发送意图，负责重试和去重；人最终是否只看到一次，取决于各渠道能不能给回执、能不能去重或对账。
- 三种"等一等"各有各的实现：
  - 等 worker：`tasks`、`task_events`，worker 汇报时变成一条事件；
  - 等人批准：任务上的问题、`unsettled` 表、审批卡片，规则见 [审批](../approvals.zh-CN.md)；
  - 等时间：`timers`，到点变成一条事件。

"等用户授权"是第四种，目前没有实现。

要注意，一件事并不总是由人开始：定时器可以启动一个任务，之后在私聊里由本人批准它的推送；群里没有唯一的请求者时则不能批准；自动开始的任务本身不带任何人的工具权限。新设计必须保留这些区别。

## 4. 机制一：请求可以等待，条件成立后接着做

**一句话**：把"一件要办的事"和"一次运行"分开。事情可以停下来等一个条件，条件成立后由合适的一方接着做。

**例子**：你发"总结这篇文档"，需要授权。请求停下，等"你授权了飞书连接器"这个条件。你授权后，飞书连接器确认条件成立，文档被读取，摘要发给你。你不需要再说话。

### 4.1 四个要分清的状态

一件事从等待到完成，中间有四个状态，任何相邻两步之间进程都可能崩溃：

1. **条件可查**：有人报告"可以去查了"。
2. **许可成立**：条件的所有者独立核实，确认成立。
3. **效果已发生**：动作执行了（文档读了、推送放行了）。
4. **结果送达**：渠道确认已交付。

报告（第 1 步）从来不等于许可（第 2 步）。重新发起一个可能产生第二次效果的动作之前，先对账。

### 4.2 谁来执行恢复

Brain 只负责协调。恢复时真正做事的一方因情况而异，每种情况由一个**适配器**声明：谁执行、幂等键是什么、能查到什么事实、结果不明时怎么收尾。

| 情况 | 条件由谁证明 | 恢复时谁做什么 | 结果不明时 |
|---|---|---|---|
| 等用户授权后读文档 | 连接器，按邀请和授权代次核实 | 原连接器重新核对权限并重读。读是可以安全重试的 | 重读 |
| 等人批准推送 | 有资格的人，规则见第 4.5 节 | 只把决定交回原来的任务和问题，由持有真实请求的出站代理放行 | 向 worker 查询它记录了哪个决定；查不到就记为未知并审计 |
| 等 worker 完成 | 那个任务的 worker | 只消费对应的终态汇报，不重开工作 | 现有的"任务丢失"处理 |
| 等时间 | 时钟 | 产生一条事件，不带任何人的权限 | 现有处理 |

### 4.3 等待记录和通知

- 等待由工具通过协议声明，模型或外部文本给出的标识不能充当凭据。
- 绑定的动作、对象、回复对象、原始人类事件的引用、恢复方式和执行者、期限、副作用的幂等键，都由运行时或受信的适配器持有。
- 先写下等待记录，再让任何入口（卡片、链接）出现。回调先于记录到达、或者互相错过时，能靠对账唤醒。
- 通知要认证调用者身份并限流，按"等待或请求的版本、条件的实例或代次、发出方绑定的租户/任务/邀请、来源事件编号"去重。通知里自称是谁不算数。
- 取消、换目标、撤权让旧代次失效；迟到的"A 已授权"不能再让 A 继续。
- **每次恢复或重试执行之前，个人权限都从原始事件重新计算**，保存事件的引用不等于保存了许可。重算的内容和今天的判断相同：同一个受信来源、同一个租户/应用/私聊、同一个人、全部是他的普通直达消息；再核对当前的授权和访问权限、动作和资源、请求版本、期限、固定的回复对象。不得拼入这次回调、别的批次或别的任务的权限。原始依据已经过期或被清理时，不能悄悄沿用旧许可。

### 4.4 等待期间用户又说话了

等待中的请求会列给模型看。用户说"授权好了""算了""换成另一篇"都是普通消息：模型理解意思，提出结构化的修改（继续、取消、换目标）；Brain 校验这个修改属于哪个请求、哪个版本，再执行。有两个可能的对象时由模型问人，Brain 不猜。

### 4.5 现有审批：原样保留

[审批](../approvals.zh-CN.md)里的约束表是这份设计的规范性依赖，不在这里重写规则。其中包括：

- 问题必须实际送达并且能完整阅读，按原问题和回执绑定，只是"已排队"不算；
- 只有可信渠道、正确的对话里的人才能批准；在群和仓库里必须是唯一的原请求者（私聊里本人可以批准由定时器开始的任务，见第 3 节）；任何有资格成员的拒绝优先，包括还在排队的拒绝；同一个人在原处的后续发言会影响尚未执行的批准；一条回复只批准一个问题；
- 批准前重查可以被编辑的答复和问题：答复被改则旧版本失效；问题被改过，即使改回去也只能拒绝；查不到就不批准；
- 单次批准和"这个任务不再问"分别记账；后者只覆盖这个任务、这个仓库里已经批准过的那些分支（一次推送可以包含多个分支，每一个都要在其中），标签和删除分支拿不到持续许可；
- 先把绑定原问题的回答意图存下来，再交给 worker；送达情况不明时向 worker 查询，"已决定、确认未决定、无法查明"分别收尾，未知要审计，结论只写一次。worker 报告的是它记录了哪个决定，不代表远端推送成功。

**第一步不动审批的存储**：`tasks.pending`、`tasks.answering`（在调用 worker 之前保存的、绑定原问题的回答意图）、`task_events`、`unsettled` 和 worker 的决定记录仍然是事实来源。批准、拒绝、保存决定、向 worker 对账，仍然只有原来的写入路径。新机制通过一个共同接口去**观察**它们的生命周期，测试可以驱动真实的审批入口；不建立第二套批准状态机，不双写，也不用一个等待标志代替 `tasks.answering`。

## 5. 机制二：内容带来源，按来源决定能做什么、留多久

**一句话**：每条内容记下"谁说的、从哪来、允许拿来做什么"，由运行时一路带着走。用它替换现在"读过就全删"的规则。

**例子**：它给你发了摘要。你回复那条摘要说"第二点的依据呢"。运行时确认你指的是哪一份答复、你现在是否还有权读那篇文档，然后重读对应段落回答你。这次运行因为带着外部内容，自动只能读和回复。之后你问一件无关的事，上下文里没有那份摘要，agent 恢复那个请求本来可以用的能力。

### 5.1 现在的规则和它的代价

现在的规则（PR #5）：一次运行只要用过连接器的工具，之后只能"回复这个人"和"再读"；运行结束时，除用户原话外的记录换成一句话；待发送的消息另有一套送达后清除的规则。它挡住了文档里的恶意指令，代价是 agent 记不住自己刚说过的话。后来为了让"先发链接、再说总结"能用，又加了"承接上一条链接，只一次，10 分钟内"（PR #8）。两条都是特例。

### 5.2 三个分开的问题

1. **谁真的说过**：这个人、agent 自己、系统。用户贴来的邮件、转发的消息，里面的字是"引用"，不因为出现在用户消息里就成了他的指令。
2. **信息从哪来**：这个人的原话，还是经某个工具从外部读来的（哪个工具、替谁读的）。
3. **允许拿来做什么**：给谁看、能不能写进记忆、留多久。

### 5.3 传播规则

- 一次模型生成的全部输出（回复、工具参数、摘要、重试和恢复后的输出、后续调用）继承这次实际看到的所有输入的限制。
- 多个输入的限制取**交集**：受众取最窄，用途取最少，期限取最早。
- 来源不明、或者老数据没有标记的，按受限处理。
- 模型不能解除限制。

### 5.4 追问：已交付答复的引用

摘要发出后，原来的请求已经完成。追问不重开旧请求，也不复活旧授权。为此新增一种有期限的记录：**已交付答复的引用**。它绑定实际送达的那一份答复，记下：每条结论对应原文的哪个位置、出处的版本或内容指纹、谁可以看、到什么时候。

- 文档之后改过，不等于被引用的那一段改过。能核对且那一段没变，就继续引用；核实到那一段确实变了，才提示这一段有变化；定位不到，就说明"当前版本里无法核对当时引用的这一段"。不让一份新摘要的第二点冒充旧摘要的第二点。
- 这种引用只用于**回答之后**的追问。回答之前、当前还没办完的目标（先发一个链接，下一句说"总结"）属于同一个未结束的请求，由机制一负责，仍然必须能接上。
- 依赖：要能知道"用户回复的是哪条消息"。飞书的接口会返回每条消息的编号，但我们的飞书连接器目前只把审批问题的编号作为回执交回，普通答复的没有交回。这是连接器要补的，不是飞书的限制。

判断"这句话是不是在追问、追问哪一份"分两段，第一段看不到任何外部内容：

1. **路由**。只看三样东西：当前这条经过核验的用户消息；渠道原生的"回复某条消息"关系；这个私聊里最小的结构化元数据（有哪些未过期的答复引用，不含摘要、标题、摘录）。
   - 用户直接回复了机器人的某份答复：就是那一份。
   - 没有直接回复：模型只根据用户这句新话，提出"延续上一份 / 新的事 / 不确定"。只有一份有效答复且明显是追问（"第二点"）时绑定；有两份可能或指向不清，就问一个问题；明确是新的事，用空上下文。
2. **核实并加载**。模型只是提名。运行时核实：对象存在、属于这个会话/租户/人、没过期、当初确实送达了、**这个人现在仍有权访问它的出处**。核实通过才把那份答复和需要的原文加载进来。权限被收回的，在任何旧内容进入模型之前就拦下；无法重新核实的不加载。

追问得到的是它自己的、范围很窄的权限。

### 5.5 上下文按请求组装

"按请求组装"必须覆盖现有的每一个把历史带进模型的入口，只给 `items` 加列是不够的：

- 同一会话里多条事件合成一批；
- 取整个会话最近一段记录作为输入；
- 系统提示里的作用域级内容：任务标题、记忆文件；
- 之前存下的工具调用，以及恢复时重放的部分。

只含用户原话的请求仍然受原有的权限判断约束。

### 5.6 从受限的上下文里做有副作用的事

"读完规格去写代码"是合理的目标，但**等待和批准只解决"何时继续"，不解决"能不能流向那里"**。

第一版的边界保持不变：外部派生的内容不跨会话，不写成长期指令或长期记忆。在受限的上下文里，agent 可以把方案或补丁**展示给原来那个人**。

要把一份材料交给执行者（worker、子代理）时，按这个顺序：

1. 能力和数据政策是否允许这个受众？不允许就只能收窄，批准也放不开。
2. 向有权批准的人展示并**冻结**这个动作：谁执行；哪个仓库、工作区、分支；会把哪些内容交给谁（能看到实际要交出的最小摘录或完整补丁，只给摘要或哈希不算预览）；是沙箱里的改动还是对外推送；可见的影响；时限和次数。
3. 批准绑定这个不可变的提案版本。执行时重新核对权限和实际交出的内容；模型改了材料或目的地，必须另批。
4. 批准一次交付，不会洗白上下文，也不等于批准之后的推送。
5. 审批卡片本身不能把规格提前泄露给无权看的群。

### 5.7 保留和清除

| 内容 | 保留 |
|---|---|
| 用户原话 | 和今天一样 |
| 外部正文、工具原始输出 | 不保留 |
| 已交付的答复及其出处引用 | 短期，只在这个私聊，带来源和期限 |
| 用户明确说的偏好（"以后先给结论"） | 在只看用户原话的独立步骤里提取，可查看、可更正 |

"核对访问权和有效期"发生在内容被加载之前，并且覆盖所有出口：还没发出的消息、被拉取的接口、摘要和压缩、错误信息、日志。

### 5.8 "这次能读哪篇文档"

不采用"目标在这个人的历史消息里出现过"作为许可。执行器只接受当前请求已经绑定的动作、规范化后的资源和回复对象。否定、歧义、换目标都要被表示出来。资源规范化、真实的访问权限、授权是否有效，仍由工具负责。

### 5.9 替换旧规则的条件

新旧两套判断并行，只比较**判断**，不为了比较多读一次文档或多发一条消息。判准：

- 旧的拒绝、新的放行：逐例解释；
- 新机制越权：必须是 0；
- 约定要放开的追问：必须成功。

达标后才删除"整轮抹掉"和"承接一次链接"，并保留一个切回旧的严格策略的开关。实现顺序是：先做带来源的读取、清除、迁移和撤权处理，最后才打开"保留答复"。

## 6. 机制三：对人只有一个出口

**一句话**：工具不自己发消息。需要人做一件事时，把"需要交互"交给 Brain，由 Brain 统一发。

- 工具返回结构化的"需要交互"和一个不透明的引用。
- Brain 先存下发送意图，再经 `outbox` 发出。同一个请求、同一次等待，最多一个有效入口；完成后最多一份逻辑上的最终答复，用唯一键保证；人是否只看到一次，取决于渠道的幂等和对账能力，结果不明时按渠道能力处理。
- 引用在连接器**发送时**才被解开。真实的授权链接、凭据、签名校验留在连接器内，不回传给 Brain，也不进日志。
- 渠道支持编辑就更新同一张卡片（需要先存下消息编号）；不支持就退化成"一张邀请加一个结果"。

现有的审批卡片已经是这个形态。

## 7. 机制四：状态信号

**一句话**："已收到、在做什么、做完了"作为连接器的通用能力，可以丢，不能挡住结果。

- 状态只描述真实发生的阶段，带请求版本、序号和有效期；请求到了终态，晚到的状态直接丢弃。
- 每个连接器按能力呈现：消息上的表情、可更新的卡片、GitHub 的 👀。
- 不能保证晚到的状态不盖住结果的渠道，就更新同一个对象，或者不显示独立状态。
- 最终结果、失败、需要人操作的事，走有序、可重试的 `outbox`。状态发送失败不影响它们。
- 分开计时：收到消息到看得见反馈；条件满足到结果送达；人自己操作的时间另算。

## 8. 机制五：提示词和记忆

- 提示词按**当前场景**选。同一个私聊里，既可能有人在等回复，也可能来一条后台汇报。
- 对话场景的原则：沿用对方已经给的材料和目标；明确就做完；只有缺一个会改变结果的信息时，才问那一个问题；不转述内部限制；出现未知错误时不拿"请把全文贴过来"当默认答案。
- 工具的说明同步修改。
- 记忆是 agent 自己的一个可选步骤，在只含用户原话的上下文里进行。一句话说了两遍不算偏好，明确说"以后都……"才算。写入都能追溯来源，可以更正和删除。

## 9. 接口变化（方向，不是定稿）

这里只列出接口必须表达什么，具体形状在第 0 步确定。不承诺用一张表承载所有语义。

- **工具的结果**分三种：成功、失败、等待。等待里由工具给出的只有"条件类型"和"需要的交互"；其余由运行时填。
- **等待的生命周期**：事务性的认领、取消、被取代、对账、结果不明、终态。
- **通知**：带认证的调用者身份和去重键，见第 4.3 节。
- **适配器**：每种条件声明执行者、幂等键、可查的事实、结果不明时的收尾。
- **发送**：带稳定的键和回执，以及渠道能提供的去重或查询。
- **交互的呈现**：在连接器内解开引用。
- **状态**：带版本、序号、有效期，失败不挡结果。
- **内容的标记**：来源、受众、允许的用途、期限；缺标记按受限处理。

## 10. 建造顺序

每一步结束时线上都可用。

**第 0 步：契约。** 产出物，评审通过后才写实现：

- 一页"事件、状态转移、可观察证据"表，用两个真实例子填同一张表。每行写：当前状态、事件及其可信来源、要重新核对的条件、唯一可以写入或执行的一方、幂等和对账的依据、允许的下一个状态（含未知）、能在数据库、渠道或 worker 上断言什么。
- 先填最容易混淆的两行，再由它们展开下面的两条时序：
  1. 授权已经保存，回调重复或进程重启：检查原请求，得到同一份逻辑上的摘要。
  2. worker 已经收到批准，回包丢失后又被取消：查询原问题的决定，只报告核实到的结果，不能由此宣称远端已经推送。
- 两条带故障注入的时序：一条是"读文档"，一条是"现有审批"。每次注入后可以断言的内容：数据库状态、动作执行次数、人看到的回复数、审计记录。
- 现有的审批测试全部保持通过。明确列出哪些新行为在旧实现上应该失败；这些失败的测试不合入主线，不算进展。
- 第 5.4 节的路由约定在这一步定下来。

**第 1 步：等待与恢复，加一个出口。** 读文档的完整流程，加上现有审批的适配器（只观察，不改存储）。

**第 1b 步：状态信号。** 可以独立做。

**第 2 步：来源和上下文。** 顺序见第 5.9 节。

**第 3 步：提示词和记忆。** 提示词可以提前；记忆等来源隔离完成。

## 11. 验收用例

**应当成立**

- 给链接和目标、点授权，不再说话，只收到一份摘要。之后多次追问都能接上。
- 回复某一份答复问"第二点的依据呢"，答中那一份的第二点，并指出原文位置。
- 进程重启、重复或乱序的回调之后，有副作用的动作只发生一次，逻辑上的答复只有一份。可以安全重复的读取允许多次实际调用。
- 先发唯一的一个链接，下一句只说"总结"，能接上（PR #8 已有的正例必须保留）。

**不应当成立**

等待与恢复：

- 等待 A 时改成 B，迟到的"A 已授权"让 A 继续。
- 授权仍然有效，但原请求的依据已经失效，文档仍被读取（读取次数应为 0）。
- 回调早于等待记录到达，导致请求永远不被唤醒。
- 最终答复已经投递但确认丢失，于是再发一遍，或者误报为已送达。
- 定时器或 worker 的通知让一次推送被批准；定时器开始的运行用到了某个人的文档权限。

审批（现有保证不得被穿透）：

- worker 已经收到批准但回包丢失，随后发生取消、新问题或重启：不应再次推送，也不应把原批准误报为已撤回；worker 无记录可查时，明确记为未知并审计。
- 问题投递途中被取消；问题被编辑后又改回；排队中的群成员拒绝；同一个人在原处、在批准执行之前的后续发言：尚未执行的旧批准都不能生效。（已经执行的决定不会被之后任何话题里的发言推翻。）

来源与上下文：

- 同一个人在两个租户或两个应用里、同一个私聊里有两份已完成的答复：回复第一份必须找到第一份；没有明确依据就问。
- 另起一个新问题时，模型的输入里出现了旧文档的正文。
- 撤权发生在"读取之后、进入模型之前"，或"已入队、尚未送达"时，内容仍被披露。
- 期限已过、压缩后恢复、老数据，把内容带了回来。
- 文档里写的指令，让 agent 写了长期记忆、派了任务或发给了别人。
- 文档改版后追问"第二点"，得到的是新摘要的第二点，却没有说明依据已经变了。
- 用户说"别读 B"，B 仍被读取。

冻结的提案：

- 获准后换了收件方、仓库或补丁，仍被执行。
- 执行失败却报告成功。
- 审批卡片把规格泄露给无权看的人。

## 12. 没有解决和有意不做的

- 流式输出：排在状态信号之后。
- 跨作用域的记忆：不在这份设计里。
- 飞书在较早的换令牌接口上是否校验 PKCE：仍然未知，与本设计无关。
- 把审批的存储迁到统一的等待记录上：第 1 步不做，是否做、何时做，等适配器在线上跑稳之后再定。

# 接入仓库的自助流程：缺什么，在对话里补什么

状态：草稿 v1（2026-11-28）。待 Codex 评审、用户定夺。

## 1. 问题

2026-11-28 一天里，为了让 agent 能读一个组织的私有仓库，运维手工做了三件事：

1. 把 GitHub App 的一次安装登记到租户（管理接口）。
2. 把一个群绑定到一个仓库（管理接口）。
3. 个人授权没有入口：没授权过的人只会被告知"读不到"（#129 留下的）。

用户的要求（原话）："这个绑定也要自动化，不能这种"。目标：人在对话里说一句"看看这个仓库"，缺哪一步，agent 就在对话里带着人补上，补完原来那件事自动继续。管理接口只作为运维的兜底。

## 2. 别人怎么做

- **GitHub 官方对"装完之后归谁"的说法。** 安装后跳回 Setup URL 时带 `installation_id`，但官方明确说这个参数可以伪造，"不应依赖它的有效性"；正确做法是为安装的人生成用户令牌，再确认这次安装确实与他有关（`GET /user/installations` 列出该用户有显式权限的安装）。安装链接可以带 `state` 回传。([About the setup URL](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/about-the-setup-url)、[Sharing your GitHub App](https://docs.github.com/en/apps/sharing-github-apps/sharing-your-github-app)、[REST: installations](https://docs.github.com/en/rest/apps/installations))
- **GitHub 的 Slack 集成。** 先连接个人的 GitHub 账号；在频道里 `/github subscribe owner/repo`；App 没装到那个仓库时，提示去安装；私有仓库的链接预览只对已登录、有权限的人显示。([README](https://github.com/integrations/slack/blob/master/README.md)) 它的文档没有写明"订阅私有仓库的人必须对仓库有什么权限"，这一点我没有查到出处，不引用。
- 共同点：**身份靠个人授权证明，安装靠 GitHub 自己的页面，绑定在对话里用一句话或一张卡片完成**，没有哪一步需要找运维。

## 3. 设计

### 3.1 唯一的通用改动：启动前检查可以回答"等一下"

#128 给 worker 加了启动前检查（`prepareStart`），它现在能回答三种：照常、不启动、绑定。加第四种：**等待**，带上已有的等待描述（等什么、给谁看什么卡片、到什么时候为止）。

Brain 对"等待"的处理复用连接器工具已有的那一套（发卡片、条件达成后自动续做、超时和取消都不启动任何东西、重放只启动一次）：把这次交办记为一个等待中的请求，条件达成后重新做一次启动前检查。不新造状态机。

下面三个分支都只是"启动前检查在什么情况下回答等待、卡片上写什么、谁能点"。

### 3.2 分支一：本人没有授权（私聊）

就是 #95B 的第 3 步。私聊里点名一个读不到的仓库、且本人没有有效授权时，回答等待，卡片是现有的 GitHub 授权卡片（措辞改为"读取这个仓库"）。授权完成后重新检查：能读就绑定启动，仍读不到就按 #129 的统一说法回复。

是否发卡片只取决于"本人有没有有效授权"，与仓库是否存在、是否接入无关（#129 评审定下的原则，不向没证实权限的人确认仓库存在）。

### 3.3 分支二：App 没装到这个仓库所在的账号

**安装本身不能替人做**，GitHub 要求有管理权的人在它的页面上点。我们做的是前后两头：

- **前**：仓库读不到、且本人已授权时，回复里附上 App 的安装链接，说明"如果这是你们组织的仓库，需要组织管理员安装"。同样不确认仓库是否存在。
- **后**：**谁装的，就登记到谁所在的租户。** GitHub 在安装完成时会发一条签名的 `installation` 事件，里面有安装者的 GitHub 账号。我们已经记录了"哪个 GitHub 账号是哪个租户的哪个人"（个人授权时绑定的）。安装者的账号恰好属于一个租户的一个人 → 自动把这次安装登记到那个租户，并在他的私聊里告诉他。
- 安装者的账号我们不认识（他还没在对话里授权过）→ 这次安装先记为"待认领"。之后有人用这个账号完成授权时，自动认领。
- 不用 Setup URL 的回跳来登记：它的参数可以伪造（见 §2），而签名事件里的安装者是 GitHub 说的。

**为什么是"安装者"而不是"任何能看到这次安装的人"：** 把一次安装登记到租户，意味着这个租户的 agent 可以为该账号下 App 被允许的所有仓库签发凭据。只对其中一个仓库有读权限的人不应该能替整个组织做这个决定；能在 GitHub 上完成安装的人，GitHub 已经确认过他有这个权力。

待核实（写代码前对着真实事件确认）：组织成员"申请安装"、由管理员批准的情况下，事件里的 `sender` 和 `requester` 各是谁。在确认之前，这种情况只认 `sender`。

### 3.4 分支三：群没有绑定这个仓库

群里有人点名一个读不到的仓库时：

- 回复统一的"读不到"，并说明"要让这个群能用这个仓库，需要一位对它有写权限的成员确认"。
- 提出请求的人如果已授权、且 GitHub 说他对这个仓库有写权限 → 给他**私下**发一张确认卡片（群里不出现仓库是否存在的信息）："让『群名』里的所有人都能通过 agent 读这个仓库的代码，并在群里审批后推送。确认？"
- 他确认 → 绑定，在群里公告"谁把这个群绑定到了哪个仓库"，原来那件事自动开始。
- 他没有写权限或没授权 → 不发卡片，只有统一的说法。别的有权限的成员在群里提同样的请求时，会收到卡片。

规则：

- **确认的人必须有写权限**（用他自己的令牌问 GitHub，取 `permissions.push`）。绑定之后群里任何人都能让 agent 读代码、发起推送（推送仍需群里审批），所以这个决定应该由本来就能写这个仓库的人做。
- **只在组织内部的群里**（沿用现有的群归属检查）。
- **一个群可以绑多个仓库**（现在只能一个，这是存储上的限制，不是有意的设计）。
- **解绑**：任何对该仓库有写权限的成员在群里说一声即可；运维接口保留。
- 仓库必须在本租户的安装之内（现有的租户边界检查）。

### 3.5 不变的

- 群里不借个人权限（#95B 的决定）。群里读私有仓库只走"绑定 + 安装凭据"。
- 令牌不进沙箱；每次请求前的复核；撤销时停任务（#129）。
- 管理接口都保留，作为运维兜底。

## 4. 实施顺序

1. 启动前检查的"等待" + 私聊的授权卡片（分支一）。
2. 安装事件自动登记 + 待认领（分支二）。
3. 群绑定的确认卡片 + 一个群多个仓库（分支三）。

每一步单独一个 PR，先测试，过 Codex。

## 5. 请用户定的

1. **安装登记给谁**：按"安装者所在的租户"自动登记（建议）；还是每次仍要人确认一下。
2. **群绑定谁能确认**：要求写权限（建议）；还是只要能读就行。
3. **绑定后是否在群里公告**是谁绑的（建议公告）。
4. **一个群能否绑多个仓库**（建议可以）。

## 6. 不做

- 替人安装 App（GitHub 不允许）。
- 群里用个人权限读（另议）。
- 按读者过滤群里的输出。

# 接入仓库的自助流程：缺什么，在对话里补什么

状态：v7（2026-11-28），评审已无阻塞项，待用户确认 §5 后按 §4 开工。Codex 和另一份书面评审都看过 v4 的 §3.3 并赞成；v5、v6 写清了它们要求的地方。群绑定按用户定的做法改为"群里发链接、由 GitHub 判断谁能确认"（§3.3）；其余已按两份评审对 v1 的意见修改（见 §7）。

## 1. 问题

2026-11-28 一天里，为了让 agent 能读一个组织的私有仓库，运维手工做了三件事：

1. 把 GitHub App 的一次安装登记到租户（管理接口）。
2. 把一个群绑定到一个仓库（管理接口）。
3. 个人授权没有入口：没授权过的人只会被告知"读不到"（#129 留下的）。

用户的要求（原话）："这个绑定也要自动化，不能这种"。目标：人在对话里说一句"看看这个仓库"，缺哪一步，agent 就在对话里带着人补上，补完原来那件事自动继续。管理接口只作为运维的兜底。

## 2. 别人怎么做

- **GitHub 官方对"装完之后归谁"的说法。** 安装后跳回 Setup URL 时带 `installation_id`，但官方明确说这个参数可以伪造，"不应依赖它的有效性"；正确做法是为安装的人生成用户令牌，再确认这次安装确实与他有关（`GET /user/installations` 列出该用户有显式权限的安装）。安装链接可以带 `state` 回传。([About the setup URL](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/about-the-setup-url)、[Sharing your GitHub App](https://docs.github.com/en/apps/sharing-github-apps/sharing-your-github-app)、[REST: installations](https://docs.github.com/en/rest/apps/installations))
- **GitHub 的 Slack 集成。** 先连接个人的 GitHub 账号；在频道里 `/github subscribe owner/repo`；App 没装到那个仓库时，提示去安装；私有仓库的链接预览只对已登录、有权限的人显示。([README](https://github.com/integrations/slack/blob/master/README.md)) 它的文档没有写明"订阅私有仓库的人必须对仓库有什么权限"，这一点我没有查到出处，不引用。
- 共同点：**身份靠个人授权证明，安装靠 GitHub 自己的页面，绑定在对话里用一句话或一张卡片完成**，没有哪一步需要找运维。

## 3. 设计

### 3.1 唯一的通用改动：启动前检查可以回答"等一下"

#128 给 worker 加了启动前检查（`prepareStart`），它现在能回答三种：照常、不启动、绑定。加第四种：**等待**，带上已有的等待描述（等什么、给谁看什么卡片、到什么时候为止）。

等待挂在 Brain 已有的"等待中的请求"上，此时**还没有任务**：不写任务、不占名额、不起沙箱。发卡片、到期、取消、重查条件、卡片去重都是现成的。

现成的机制有三处不能直接用，要补（Codex 对着代码指出的）：

- **恢复入口。** 现在恢复一个等待中的请求，是把保存的工具调用重放给连接器工具。Brain 自己启动的 worker 没有这条路。要加一个专用的恢复入口：只执行当初保存下来的那一次交办（worker、仓库和选项、任务说明、标题、原消息的引用），不让模型重填参数。用最初那个请求的编号作为任务的幂等键，原调用重放、条件重复达成、再次进入等待，找到的都是同一份记录。
- **提出人。** 恢复时这一轮处理的是系统事件，不是人的消息；现在"谁提出的"取自当前这一轮的消息，恢复时会变成空，私聊借权限的判断就会当成普通任务。要从原消息重新核验出本人、来源会话和消息版本，一路传给启动前检查和任务归属；核验不成立就终止，不把系统唤醒当成人。
- **写任务前再确认一次。** 启动前检查要问外面，会花时间。回来之后、写任务之前，在同一步里确认：这份请求仍然有效、等待的条件没有换代、原授权没被撤回。取消和启动只有一个交接点：没写任务之前取消就是零任务，写了之后走已有的任务取消。

另外四条契约（书面评审对着代码列的），第一步就要定干净，免得做群绑定时返工：

- **保存的是整份交办**：worker、标题、任务说明、选项、接续自哪个任务、后续动作（`then`）。恢复时原样使用，模型不能改写。
- **启动前检查要拿到调用编号**，发授权邀请时用它去重（同一次交办只有一张卡）。
- **`then` 的处理**：借个人权限的任务不允许带 `then`（#129）。这条要在进入等待之前就判断并拒绝，不能等人授权完回来才说不行；判断只看"这是私聊里本人点名的仓库"，不看仓库是否存在，所以不泄露什么。群绑定之后启动的任务带的是另一种记录（见 §3.3），用的是安装凭据而不是个人权限，允许带 `then`，等待期间要保存并在恢复时复核。
- **等待中的交办要能被取消**：现在"取消请求、取消工作"只认连接器工具的等待，要把这一类也登记进去；取消后不启动任何东西。

验收：同一个回调来两次、条件在入库之前就达成、等待中取消或改了原话、写完任务后重启、两个独立的请求共用一张授权卡。每份有效的原请求最多启动一次。

### 3.2 第一条路：私聊里没有授权

私聊里点名一个读不到的仓库、且本人没有有效授权时，回答等待，卡片是现有的 GitHub 授权卡片（措辞改为"读取仓库"）。授权完成后原来那件事自动继续：能读就启动，仍读不到就按 #129 的统一说法回复。

是否发卡片只取决于"本人有没有有效授权"，与仓库是否存在、是否接入无关：对不存在、没接入、读不到三种输入，看到的表现必须相同。

### 3.3 第二条路：内部群请求一个没绑定的仓库

**用户定的做法（2026-11-28）："直接发链接到群里，保证只有有权限的人才能点击授权"。** 取代 v3 里"私下给有权限的人发确认卡片"的做法。

绑定是在给这个群**现在和以后的所有成员**授予这个仓库的访问。流程：

1. 群里有人点名一个读不到的仓库。先确认这个群此刻是组织内部的群：是外部群、或者暂时查不到，就直接拒绝，不发链接，也不去探这个仓库。是内部群，agent 在群里回统一的一句话，附一个链接："要让这个群能读这个仓库，请仓库管理员点这里确认。"原请求进入等待（§3.1）。
2. 任何人都能打开链接，第一步是用 GitHub 登录（App 的用户授权）。
3. 用登录者自己的令牌问 GitHub 这个仓库：他是不是管理员（`permissions.admin`）、仓库的数字编号是多少。
4. 是管理员 → 确认页写明：哪个租户的哪个群、哪个仓库、**只读**、怎么撤销。他点确认才绑定。
5. 不是管理员、仓库不存在、App 没装到这个仓库 → 同一个页面："你没有权限确认，或者这个仓库在这里不可用。"什么都不发生。
6. 绑定后在群里公告：哪个仓库、只读、哪个 GitHub 账号授权的、怎么撤销。等待中的原请求自动继续。

为什么这样更好（相对 v3）：

- **权限由 GitHub 当场判断**，不用我们去找谁是管理员，也不用把 GitHub 账号对应到聊天里的人。管理员不需要事先在这里授权过；不在群里的管理员，把链接转给他就行。
- **群里天然没有差别**：不管仓库存不存在、提问的人是谁，群里都是同一句话加同一种链接，同样进入等待、同样到期。v3 里要专门压掉的那些回执不再出现差别。
- **不需要新的交互卡片**：确认在网页上完成，带链接的卡片现在就有。也不需要用 App 的凭据列出管理员。

要守住的：

- **链接是一个猜不到的短期随机地址，本身不含任何内容。** 指向哪个租户、哪个群、哪个仓库、什么时候到期，都存在我们这边。（v4 写的是"带签名的链接"：签名只保证内容没被改，租户、群和仓库名会跟着链接一起被转发出去。）
- **群里的这份邀请，和每个人打开它的那一次，是两回事。** 同一份邀请可以被很多人打开：聊天软件抓链接预览、普通成员登录后被告知不可用、管理员看了一眼关掉，都只影响那一次浏览，不消耗邀请。只有真正绑定成功才结算这份邀请。每次打开各有自己的登录状态和确认凭证。
- **确认页上的租户名和群名从我们自己的记录里读**，不从链接里读，按纯文字显示。写的是"这个群现在和以后的所有成员都能读取这个仓库"，不写精确人数。通常群已经绑了别的仓库时根本不会发链接（见下）；万一两份邀请并发、另一份先绑上了，后打开的确认页只说"这个群已有绑定"，不向群外的管理员透露是哪个仓库。
- **链接可以被转发，所以登录完不能自动绑定**：必须在写明后果的确认页上点确认（管理员可能是被人转发链接引来的）。确认页用和现有授权回跳同样的办法防伪造提交（确认词只在他的浏览器里）。
- **登录只用来核对这一次**：不把他的 GitHub 账号和聊天里的人关联，不进个人授权的记录，不改变任何人的个人授权，不保存可续期的凭据。从登录到点确认之间，他的访问令牌按这一次浏览加密暂存几分钟，确认或超时即清除：这是为了在点确认的那一刻用它**再问一次 GitHub**（登录时是管理员、点确认时已被降权的，要拦住）。只记住第一次看到的"是管理员"是不够的。
- **回跳和个人授权的回跳分开**：按用途分流，各自的记录各自存；群绑定这条路失败就在这条路里结束，不会落进个人授权的写入路径。
- **谁能确认：仓库的管理员。** GitHub 的角色表里，决定"谁能访问这个仓库"的权力属于 Admin。
- **第一版只给群读取。** 存储上区分"只读绑定"和现在运维做的"读写绑定"，执行端按这个区分去借凭据。
- **点确认的那一刻全部重新核对**：链接没过期没用过；群此刻仍是组织内部的群；他此刻仍是管理员、仓库编号没变；仓库此刻仍在本租户的安装之内。
- **授权的含义是"管理员代表组织授权"**，不依赖他以后是否还在。仓库或安装被移除、群变成有外部成员的群、有人撤销绑定时，立即停止借出，并拦住还在路上的结果发往这个群。
- **先保持一个群一个仓库。** 群已经绑了别的仓库时，不发链接，直接在群里说："这个群现在绑定的是某某仓库，暂时不能同时绑定多个；要换请先解绑。"群绑了哪个仓库是群里人本来就知道的事，这句话不透露新问的那个仓库是否存在，也省得管理员登录一趟才被告知。多个仓库以后再做。
- **登录之前什么都不显示。** 打开链接后，在完成 GitHub 登录并确认他是管理员之前，页面不出现租户名、群名或仓库名（链接可能被转发或被抓取）。
- **如实告诉管理员 GitHub 那边会留下什么。** 核对身份用的是同一个 App 的用户授权，GitHub 的授权页会照常列出这个 App 的全部权限（包括读写代码），授权后他的 GitHub 设置里会留下这个 App。这和"只给群只读"并不矛盾，但他会疑惑，所以确认页上要写明：我们只用这次登录核对他是不是管理员，不保留他的授权；GitHub 那边的记录他可以自己撤销。
- **解绑**：群里有人明确说要解绑这个群的仓库时，agent 发一个同样方式的解绑链接，仓库管理员登录确认后解绑；仓库已经不在本租户的安装之内时，群里的内部成员可以直接清掉这条无效绑定；运维接口保留。发解绑链接和清除无效绑定都是"动作"类的工具：要本人明确说出，读过外部内容的那一轮里不能用。
- **防刷**：同一个群对同一个仓库，链接有效期内不重复发新的；每个群同时有效的链接有上限。
- **绑定写入只成功一次**：现有的绑定方法在冲突时直接覆盖，自助入口不能用它。在一步里核对当前绑定的版本、写入只读绑定、记下要发的公告。两位管理员同时确认同一个目标，只生效和公告一次；目标不同时保留先成功的；运维绑定的群保持原来的权限。绑定记的是仓库和安装的数字编号，撤销或重绑时版本加一。
- **群里的这类任务也要"绑定到一份记录"。** 现在只有借个人权限的任务带着记录，Brain 在收下结果前会问一句"还作数吗"（#129）；群里的任务是普通任务，没有这一问，解绑、进了外人、仓库被移出之后跑完的结果照样会发到群里。所以自助绑定的群，任务启动时也带一份记录（哪个租户、哪个群及其来源、哪个仓库及其编号、哪个安装、只读、绑定的版本），收结果前用同一个机制复核。
- **记录要分种类，各走各的规则。** 现有代码里有四处把"任务带着记录"直接当成"借了个人权限"：带记录就不许有 `then`；带记录的任务重放时要求提出人不变；带记录就用个人令牌克隆，不再用安装凭据；带记录的任务不留工作区、不能接着做。群绑定的记录是另一种：用安装凭据、允许 `then`、允许接着做（接着做之前复核绑定的版本和内部群）、交结果前同样要问"还作数吗"。实现时这四处都要按记录的种类分开，不能沿用现在的隐含假设。
- **只读要一路做到底。** 现在沙箱克隆和拉取代码时借的是能写的凭据。只读绑定的群，克隆和拉取要借只读的，推送那条路不借；否则要么只读是假的，要么只读的群连克隆都做不了。
- **绑定记录里要多存几样**：群所在的聊天应用和组织（借出前核对"仍是内部群"要用，现在的记录里没有）、仓库编号、只读还是读写、谁绑的、什么时候、版本。运维以前手工绑的记录没有这些，按"读写、来源从租户登记的聊天应用里取"兼容。
- **借凭据、接着做、往群里发结果之前，都核对群此刻仍是内部群、绑定仍是那个版本**；不是就停住。这样解绑后即使重新绑回同名的仓库，排队中的旧任务也不会恢复发布。
- **唤醒等待的请求**：等待的条件是"这个租户、这个群、这个仓库、只读"这一个绑定意图，邀请属于这个意图而不是挂在第一个请求上。绑定成功后用一个固定编号的事件通知这个群的 Brain（可重试；先绑定、后才登记等待的顺序也要对），每个等待中的请求按自己的原话、是否被取消、是否过期各自决定继续与否，各用各的幂等键。取消其中一个只影响它自己。
- **确认人可以不在群里、不在这个租户里。** 前提是：租户允许内部群发起自助共享，且仓库属于本租户已确认的安装。群里发起的人指定了"给谁"，仓库管理员确认"给不给"。去查他是不是那个 GitHub 组织的成员，只能证明他属于那个组织，证明不了他属于这个群，第一版不查。企业以后若要接收方也审批，可以加群主确认。

它管不了的：仓库所在的账号还没装 App 时，GitHub 不会告诉登录者关于这个仓库的任何事，确认页只能显示"不可用"。那是 §3.4 的事。

**顺带要补的两个现有缺口**（自助绑定上线前必须补，否则自助会把它们放大；它们对现在运维绑定的群同样存在）：

- **群后来进了外部成员。** 现在借凭据时只查"这个群绑了这个仓库"，不查群是否仍是内部群。以前靠运维把关；自助之后，内部群绑完私有仓库、第二天拉进外部客户，代码就会发到有外人的群里。要在借出凭据之前复核群仍是内部群。
- **解绑之后还能接着做。** 群里的任务是普通任务，结束后工作区保留一天供"接着做"。解绑之后的一天内，群里的人仍能从旧任务接着做，读到已解绑仓库的代码。要在"接着做"时复核群现在仍绑定着那个任务所在的仓库。

### 3.4 之后：把 App 的安装接入租户

**安装本身不能替人做。** 而且"装了"不等于"归这个租户"：Codex 指出，GitHub 的安装事件只保证有一个操作者账号，并不保证这个人有权替组织决定"接入哪个租户"；一个账号只在一个租户里出现过，也不能证明他有这个意图。所以 v1 的"谁装的归谁的租户"不成立。

改为：

- **这一条路不是"等待后自动继续"。** 安装常常要另找组织管理员、隔很久才完成，把原请求一直挂着不划算。所以是：回复里给出安装链接（由 App 的名字拼出；没配置时只说需要安装），装好并接入后在私聊里通知发起的人，由他重新提出原来的请求。
- **从租户这边发起。** 对话里遇到没接入的仓库时，回复里给出安装链接，同时记下一份短时、一次性的接入请求：哪个租户、谁发起的、期望的是哪个组织。
- **两边都要有人点头**：GitHub 那边有权装的人完成了安装（签名事件作证），租户这边发起请求的人确认"把这个组织的这些仓库接入这里"。同一个人两边都有权时，一次确认即可。确认页上写明接入的是哪个租户、哪些仓库。
- **只认领空位**：已经归别的租户的安装不动；同一个租户重复认领是同一件事。现有的登记方法会直接覆盖已有归属，自助入口不能用它。
- **安装事件先记为待确认**，有期限、有数量上限（App 是公开的，陌生人可以反复安装）。它的验签要放在"按安装查租户"之前，否则新安装查不到租户会被直接拒掉。
- **一个 GitHub 账号可以在多个租户里用**，所以"这个账号属于哪个租户"永远不能当作意图：必须是在某个租户的对话里点了确认。
- **另外两种事件也要处理**：安装被删除（清掉登记和待确认记录）；组织早就装了、这次只是在"只选部分仓库"里加了一个仓库（GitHub 发的是另一种事件，不是新安装）。
- **通知要可靠**：事件处理里不能只尝试发一次私聊就算了，要走带重试的投递。
- **卸载、暂停、移除仓库**之后按当前状态复核，旧事件和过期的卡片不能恢复授权。
- 上线前要拿到一次真实的"成员申请、管理员批准"的事件样本再定字段怎么认，不依赖文档没有承诺的含义。

这一步比前两条路复杂，放在它们之后。在它做好之前，接入安装仍由运维完成，回复里明确说这一步目前需要人工。

### 3.5 不变的

- 群里不借个人权限（#95B 的决定）。
- 令牌不进沙箱；每次请求前的复核；撤销时停任务（#129）。
- 管理接口都保留，作为运维兜底。

## 4. 实施顺序

1. 启动前检查的"等待"和专用恢复入口 + 私聊的授权卡片（§3.1、§3.2）。
2. 内部群里发链接、由仓库管理员确认、只读绑定（§3.3），连同"借出前复核内部群""接着做时复核绑定"两个现有缺口一起。
3. 安装接入租户（§3.4）。
4. 以后：一个群多个仓库、群里推送、安装在租户之间转移。

每一步单独一个 PR，先测试，过 Codex。

## 5. 请用户定的

0. **已定（2026-11-28）**：群绑定用"群里发链接，登录 GitHub 后由 GitHub 判断有没有权限确认"。
1. **群绑定谁能确认**：仓库管理员（建议，Codex 的意见）；还是有写权限就行（书面评审的底线）。
2. **群绑定第一版只读**（建议）；推送以后再开。注意：现在运维绑定的群是能推送的（需审批），自助绑定的群第一版不能。
3. **管理员离职后绑定是否保留**（建议保留，理由见 §3.3）。
4. **安装接入**放在第三步、在那之前仍由运维做（建议）；还是提前。
5. **一个群多个仓库**：后做（建议，Codex 的意见）；还是和群绑定一起做（书面评审的意见）。

## 6. 不做

- 替人安装 App（GitHub 不允许）。
- 群里用个人权限读（另议）。
- 按读者过滤群里的输出。

## 7. 评审记录

### 书面评审对 v4 的意见（2026-11-28，用户转来）

赞成 v4 的方向和 §5 的全部建议项。其中两处（邀请和单次登录分层、短时暂存令牌用于确认时复核）与 Codex 对 v4 的意见相同，v5 已写。v6 补上它另外指出的：

- 群里的任务要带一份记录，否则解绑后在路上的结果拦不住；只读要落实到克隆和拉取借的凭据上。
- 绑定记录要存群的来源、仓库编号、读写、版本；登录前页面什么都不显示；如实告诉管理员 GitHub 那边会留下授权记录。
- 群已绑了别的仓库时直接在群里说，不发链接；解绑从哪里发起；实施顺序里一句旧措辞。

### Codex 对 v4 §3.3 的评审（2026-11-28）

赞成群里直接发链接，并同意第一版允许群外的仓库管理员确认。要求写清三处，v5 已写进 §3.3：邀请和每次打开分开、链接本身不含内容；点确认时怎样再证明一次管理员权限（选了"短时暂存访问令牌，确认时再问 GitHub"）；绑定和唤醒各自只生效一次。

它的验收场景：预览和无权的人都打开过之后，管理员仍能确认；登录后被降权，确认失败；两人同时确认、或确认的应答丢了再试，绑定和公告只生效一次；两个任务共用一份邀请、取消一个、通知重复送达，另一个只启动一次，群随后变成外部群时拦住在路上的结果。真实安装权限下"是不是管理员"的判断还需要集成验证。

### 书面评审对 v1 的意见（2026-11-28，用户转来）

和 Codex 的结论大体一致，另外对着代码补了这些，v3 都已写进正文：

- 安装自动登记的四种出错方式（先在别的租户授权过的人会把公司的安装带到别的租户；待认领同样会被别的租户认走；一个账号多个租户没有定义；现有登记方法会覆盖已有归属），以及要处理删除安装、增选仓库两种事件，待确认记录要有期限和上限。
- 群里三处会露出差别的地方（沉默与回复、"卡片已私聊发你"、"未授权"）。
- 等待机制接到交办上的五处契约缺口（幂等键、保存整份交办、调用编号、`then`、取消）。
- 点确认那一刻的全部复核；群后来进了外部成员；解绑后一天内还能接着做；解绑的权限和防误触发。
- 分支二其实不自动继续，文档要说清；没授权的管理员在群里的死胡同；确认卡片缺交互基础；通知的数据路径和重试。

**两份评审不一致的两点，留给用户定（§5）：**

- 群绑定谁能确认：这份评审认为至少要写权限；Codex 认为应是仓库管理员、且第一版只读。这份评审同时指出一个现状：现在绑定的群借到的是能写的凭据，而群里审批推送时只核对审批人是群里的本组织成员，不核对他在 GitHub 上有没有写权限。这正是"第一版只读"要避开的。
- 一个群多个仓库：这份评审建议现在就支持；Codex 建议后做。

### Codex 对 v1 的评审（2026-11-28）

赞成方向，要求改三处，v2 都已采纳：

- §3.1：等待的位置对（任务写入之前），但恢复入口、提出人的重新核验、写任务前的再确认这三处现有机制不够，要补。
- 安装归属：v1 的"谁装的归谁的租户"不安全（事件里的操作者不保证有组织级的决定权；一个账号只属于一个租户也不证明意图）。改为从租户发起、两边确认、只认领空位。
- 群绑定：门槛应是仓库管理员而不是写权限；第一版只读，执行端要真的区分读写；"只给有权限的人发卡片"本身会向旁人泄露信息，群里的回执要统一。
- 最小交付：先做私聊授权续办，再做内部群只读绑定；安装认领、多仓库、群里推送都往后。

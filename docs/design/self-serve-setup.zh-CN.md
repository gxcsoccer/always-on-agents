# 接入仓库的自助流程：缺什么，在对话里补什么

状态：草稿 v2（2026-11-28）。已按 Codex 对 v1 的评审修改（见 §7），待用户定夺。

## 1. 问题

2026-11-28 一天里，为了让 agent 能读一个组织的私有仓库，运维手工做了三件事：

1. 把 GitHub App 的一次安装登记到租户（管理接口）。
2. 把一个群绑定到一个仓库（管理接口）。
3. 个人授权没有入口：没授权过的人只会被告知"读不到"（#129 留下的）。

用户的要求（原话）："这个绑定也要自动化，不能这种"。目标：人在对话里说一句"看看这个仓库"，缺哪一步，agent 就在对话里带着人补上，补完原来那件事自动继续。管理接口只作为运维的兜底。

## 2. 别人怎么做

- **GitHub 官方对"装完之后归谁"的说法。** 安装后跳回 Setup URL 时带 `installation_id`，但官方明确说这个参数可以伪造，"不应依赖它的有效性"；正确做法是为安装的人生成用户令牌，再确认这次安装确实与他有关（`GET /user/installations` 列出该用户有显式权限的安装）。安装链接可以带 `state` 回传。([About the setup URL](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/about-the-setup-url)、[Sharing your GitHub App](https://docs.github.com/en/apps/sharing-github-apps/sharing-your-github-app)、[REST: installations](https://docs.github.com/en/rest/apps/installations))
- **GitHub 的 Slack 集成。** 先连接个人的 GitHub 账号；在频道里 `/github subscribe owner/repo`；App 没装到那个仓库时，提示去安装；私有仓库的链接预览只对已登录、有权限的人显示。([README](https://github.com/integrations/slack/blob/master/README.md)) 它的文档没有写明"订阅私有仓库的人必须对仓库有什么权限"，这一点我没有查到出处，不引用。
- 共同点：**身份靠个人授权证明，安装靠 GitHub 自己的页面，绑定在对话里用一句话或一张卡片完成**，没有哪一步需要找运维。

## 3. 设计

### 3.1 唯一的通用改动：启动前检查可以回答"等一下"

#128 给 worker 加了启动前检查（`prepareStart`），它现在能回答三种：照常、不启动、绑定。加第四种：**等待**，带上已有的等待描述（等什么、给谁看什么卡片、到什么时候为止）。

等待挂在 Brain 已有的"等待中的请求"上，此时**还没有任务**：不写任务、不占名额、不起沙箱。发卡片、到期、取消、重查条件、卡片去重都是现成的。

现成的机制有三处不能直接用，要补（Codex 对着代码指出的）：

- **恢复入口。** 现在恢复一个等待中的请求，是把保存的工具调用重放给连接器工具。Brain 自己启动的 worker 没有这条路。要加一个专用的恢复入口：只执行当初保存下来的那一次交办（worker、仓库和选项、任务说明、标题、原消息的引用），不让模型重填参数。用最初那个请求的编号作为任务的幂等键，原调用重放、条件重复达成、再次进入等待，找到的都是同一份记录。
- **提出人。** 恢复时这一轮处理的是系统事件，不是人的消息；现在"谁提出的"取自当前这一轮的消息，恢复时会变成空，私聊借权限的判断就会当成普通任务。要从原消息重新核验出本人、来源会话和消息版本，一路传给启动前检查和任务归属；核验不成立就终止，不把系统唤醒当成人。
- **写任务前再确认一次。** 启动前检查要问外面，会花时间。回来之后、写任务之前，在同一步里确认：这份请求仍然有效、等待的条件没有换代、原授权没被撤回。取消和启动只有一个交接点：没写任务之前取消就是零任务，写了之后走已有的任务取消。

验收：同一个回调来两次、条件在入库之前就达成、等待中取消或改了原话、写完任务后重启、两个独立的请求共用一张授权卡。每份有效的原请求最多启动一次。

### 3.2 第一条路：私聊里没有授权

私聊里点名一个读不到的仓库、且本人没有有效授权时，回答等待，卡片是现有的 GitHub 授权卡片（措辞改为"读取仓库"）。授权完成后原来那件事自动继续：能读就启动，仍读不到就按 #129 的统一说法回复。

是否发卡片只取决于"本人有没有有效授权"，与仓库是否存在、是否接入无关：对不存在、没接入、读不到三种输入，看到的表现必须相同。

### 3.3 第二条路：内部群请求一个没绑定的仓库

绑定是在给这个群**现在和以后的所有成员**授予这个仓库的访问。所以：

- **谁能确认：仓库的管理员**（GitHub 的 Admin 角色；用他自己的令牌问 GitHub）。GitHub 自己的角色表里，决定"谁能访问这个仓库"的权力属于 Admin，普通的写权限没有。普通成员可以发起请求，但不能确认。
- **第一版只给群读取。** 推送留到以后。存储上要区分"只读绑定"和现在运维做的"读写绑定"，执行端按这个区分去借凭据：否则卡片上写着只读，实际借出去的还是能写的。
- **群里看不出差别。** 确认之前，群里对任何人、任何仓库名都是同一句话；现在等待机制在卡片送达成功、失败、不明时会往原会话写不同的回执，这类回执和等待、超时的提示在群里都要压掉，细节只发给本人。否则旁人能从"他收到了卡片"推断出仓库存在、以及他是管理员。
- **确认时再核对一遍**：是他本人、群仍是组织内部的群、仓库的数字编号没变、仍在本租户的安装之内。
- **确认后在群里公告**：哪个仓库、只读、谁授权的、怎么撤销。原来那件事自动开始。
- **授权的含义是"管理员代表组织授权"**，不依赖他以后是否还在：他离职不自动解绑。仓库或安装被移除、群变成有外部成员的群、有人撤销绑定时，立即停止借出，并拦住还在路上的结果发往这个群。
- **先保持一个群一个仓库。** 群已经绑了别的仓库时，明确告诉请求的人，保留原来的绑定。多个仓库以后再做。

### 3.4 之后：把 App 的安装接入租户

**安装本身不能替人做。** 而且"装了"不等于"归这个租户"：Codex 指出，GitHub 的安装事件只保证有一个操作者账号，并不保证这个人有权替组织决定"接入哪个租户"；一个账号只在一个租户里出现过，也不能证明他有这个意图。所以 v1 的"谁装的归谁的租户"不成立。

改为：

- **从租户这边发起。** 对话里遇到没接入的仓库时，回复里给出安装链接，同时记下一份短时、一次性的接入请求：哪个租户、谁发起的、期望的是哪个组织。
- **两边都要有人点头**：GitHub 那边有权装的人完成了安装（签名事件作证），租户这边发起请求的人确认"把这个组织的这些仓库接入这里"。同一个人两边都有权时，一次确认即可。确认页上写明接入的是哪个租户、哪些仓库。
- **只认领空位**：已经归别的租户的安装不动；同一个租户重复认领是同一件事。
- **卸载、暂停、移除仓库**之后按当前状态复核，旧事件和过期的卡片不能恢复授权。
- 上线前要拿到一次真实的"成员申请、管理员批准"的事件样本再定字段怎么认，不依赖文档没有承诺的含义。

这一步比前两条路复杂，放在它们之后。在它做好之前，接入安装仍由运维完成，回复里明确说这一步目前需要人工。

### 3.5 不变的

- 群里不借个人权限（#95B 的决定）。
- 令牌不进沙箱；每次请求前的复核；撤销时停任务（#129）。
- 管理接口都保留，作为运维兜底。

## 4. 实施顺序

1. 启动前检查的"等待"和专用恢复入口 + 私聊的授权卡片（§3.1、§3.2）。
2. 内部群由仓库管理员私下确认、只读绑定（§3.3）。
3. 安装接入租户（§3.4）。
4. 以后：一个群多个仓库、群里推送、安装在租户之间转移。

每一步单独一个 PR，先测试，过 Codex。

## 5. 请用户定的

1. **群绑定谁能确认**：仓库管理员（建议，按 Codex 的意见从 v1 的"写权限"改过来）；还是有写权限就行。
2. **群绑定第一版只读**（建议）；推送以后再开。注意：现在运维绑定的群是能推送的（需审批），自助绑定的群第一版不能。
3. **管理员离职后绑定是否保留**（建议保留，理由见 §3.3）。
4. **安装接入**放在第三步、在那之前仍由运维做（建议）；还是提前。

## 6. 不做

- 替人安装 App（GitHub 不允许）。
- 群里用个人权限读（另议）。
- 按读者过滤群里的输出。

## 7. 评审记录

### Codex 对 v1 的评审（2026-11-28）

赞成方向，要求改三处，v2 都已采纳：

- §3.1：等待的位置对（任务写入之前），但恢复入口、提出人的重新核验、写任务前的再确认这三处现有机制不够，要补。
- 安装归属：v1 的"谁装的归谁的租户"不安全（事件里的操作者不保证有组织级的决定权；一个账号只属于一个租户也不证明意图）。改为从租户发起、两边确认、只认领空位。
- 群绑定：门槛应是仓库管理员而不是写权限；第一版只读，执行端要真的区分读写；"只给有权限的人发卡片"本身会向旁人泄露信息，群里的回执要统一。
- 最小交付：先做私聊授权续办，再做内部群只读绑定；安装认领、多仓库、群里推送都往后。

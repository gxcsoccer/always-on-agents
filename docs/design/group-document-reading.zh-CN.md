# 在群里读飞书文档

状态：草案第二版。用户已定方向：**甲**（2026-11-24，“选甲”）。Codex 评审过第一版（见第 6 节），本版按它的意见修改；其中 4.5 的简化还要用户确认。

## 1. 现在的情况

- 读文档的工具 `feishu_read_document` 只在私聊里有。它以提问人本人的身份、用本人的授权去读。
- 群里没有这个工具。模型看到链接后会派一个沙箱去直接抓，沙箱的出站规则只放行模型服务和 github.com，所以返回 403（`src/workers/sandbox/outbound.ts:61`）。请求根本没到飞书。
- 用户的预期是：在群里发链接或回复一条带链接的消息，@ 机器人，就能读。

为什么当初只做私聊，代码里有三处把它限定死了：

1. `Runner.actingOn`（`src/brain/runner.ts`）：只有 scope 是个人、会话是私聊、消息带 `direct: true` 时，才认定"这次运行代表某个人"。否则没有工具。
2. 授权对象通知"授权好了"时，只通知这个人的私聊 Brain（`src/connectors/feishu-grant.ts:189`）。
3. 一次运行按会话取消息，群里一批消息可能来自几个人，没有"这批消息是谁的"这个概念。

## 2. 目标

在群里，一个人 @ 机器人问一篇他自己贴出链接的飞书文档，agent 用**这个人自己的授权**去读，并答复。

不做的：

- 不用机器人自己的身份读文档。机器人能打开什么，与此无关（和私聊一致）。
- 不借别人的授权。A 贴的链接，B 来问，用的是 B 的授权；B 没权限就读不了。
- 不读别人贴的链接里、提问人自己没有再贴一次的文档（见 4.3）。

## 3. 需要用户定的一件事：答复发到哪里

读是用提问人的授权读的，但群里其他人未必能打开那篇文档。答复发到群里，等于把文档内容给了全群。三种做法：

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| 甲 | 直接答在群里 | 最自然，和一个人把摘要贴到群里是一回事；实现最小 | 群里没权限的人也能看到内容 |
| 乙 | 先确认这个群有权看这篇文档，能确认才答在群里；否则在群里说一声，答案私聊发给提问人（Codex 的意见） | 不会把内容漏给没权限的人 | 见下 |
| 丙 | 一律私聊答复，群里只说"已私聊回复" | 最保守，实现也小 | 群里的人看不到结论，失去在群里问的意义 |

乙的代价，调研后比预想的大：

- 飞书**没有**"某个群能不能看某篇文档"的直接接口。判断当前调用者权限的接口（`permissions/:token/members/auth`）只能查调用者自己。
- 只能间接判断，两条路：
  - 查文档的链接分享设置（`drive/v2/permissions/:token/public`）：如果是"组织内获得链接的人可阅读"，且这个群没有外部成员，就可以认为全群可读。
  - 查文档的协作者列表（`drive/v1/permissions/:token/members`）：看这个群是不是协作者（`member_type: openchat`）。
- 两条路都要提问人**多授权一到两项权限**（`docs:permission.setting:read`、`docs:permission.member:retrieve`），已经授权过的人要重新点一次同意。
- 协作者列表这个接口，普通阅读者不一定调得通（取决于文档的"谁可以查看协作者"设置）。调不通时只能退回私聊答复，用户会觉得"时灵时不灵"。
- 知识库文档的权限是从空间继承的，协作者列表是否包含继承来的成员，文档没有写明，要实测。
- 每次读多两到三次接口调用。

**我的建议是甲，加一条便宜的限制：群里有外部成员（飞书的"外部群"）时，改为私聊答复。**

理由：

- 提问人是在群里、当着所有人的面、自己贴的链接、自己要求调研的。把结论发在群里是他明确要的结果，和他自己读完把摘要贴进群没有区别。责任在提问人，这和私聊里"他打不开的 agent 也打不开"是同一个原则。
- 乙为了一个保证付出的机制很重：两项新权限、三个接口、一套回退逻辑，而且回退会经常触发。这和上次追问功能的教训是同一类（当时的结论：保证本身要先拿出来让用户权衡，而不是默认加机制）。
- 外部群这一条便宜（群信息里一个字段），而且防的是最不该发生的情况：把内部文档内容发给组织外的人。

如果选乙，实现上先做"链接分享 + 非外部群"这一条路，协作者列表那条路实测后再定。

## 4. 方案

### 4.1 "这次运行代表谁"扩展到群里

`Runner.actingOn` 现在的判断是：个人 scope + 私聊会话 + 每条消息都是这个人写的普通消息 + 同一个来源。

改成两种情况都认：

- **私聊**：和现在完全一样。
- **群里**：这批消息全部是**同一个人**写的、明确对机器人说的普通消息（不是按钮、不是对审批问题的回答、不是转来的），来自同一个应用和组织。这个人就是这次运行代表的人。

"最近说过的话"（`recent`，用来找他之前贴的链接）在群里先按"同一个群会话、同一个人"过滤，再取一天之内的最近五十条。别人的消息不算。

贴过链接只是候选范围。是不是在问文档、问的是哪一篇，仍由模型根据这次的话判断，和私聊一样：几篇都可能时问他，昨天贴过链接不会让今天一句无关的 @ 变成读文档。

### 4.2 一批消息按人分开

群里一次运行现在可能把几个人的消息一起处理。读文档要求一次运行只代表一个人，所以在取批次时（`Runner.#batch`）加一条边界，和现有的"回复对象变了就另起一次运行"是同一种规则：

- 在群会话里，写消息的人变了，就另起一次运行。A、B、A 三条消息是三次运行，顺序不变。
- 不是人写的事件（定时器、任务回报、自动通知）和人写的消息分开；按钮点击、对审批问题的回答，和普通消息分开。否则两秒窗口里混进一条定时器或一次按钮点击，这一批就认不出"代表谁"，提问人会莫名其妙读不了文档。

这一步可以独立上线，不依赖后面。

### 4.3 读哪篇文档

规则和私聊一样，只是"这个人自己的消息"现在包括他在这个群里的消息：

- 这次请求里他贴的链接；
- 他在这个群里一天之内自己发的消息里贴的链接；
- 他回复的那条自己的消息里的链接。那条消息如果没有 @ 机器人，agent 没收到过，就用 PR #40 的机制取回来（只取他自己写的）。

第三种情况要补一处：PR #40 取回的是给模型看的文字，截到 1000 字，富文本里的链接是拼出来的。**用来认定文档的链接不能从这段文字里取**。取回时由 connector 从原消息的完整内容里提取文档链接（富文本以真实的链接地址为准），和文字一起存下（`quoted.documents`），认定文档时用它。

读文档的工具现在只在"最近说过的话"里按消息编号找被回复的那条，找不到就拒绝。改成：找不到时，用这条请求消息上由 connector 核实并存下的 `quoted.documents`。"被回复的消息里有几篇文档、这次又没说是哪篇，就不读、去问他"这条规则不变。

别人贴的链接不算他的选择。B 想问 A 贴的文档，要自己再贴一次链接。

群里还有一种私聊里没有的情况：他上一句贴了链接但没 @ 机器人，下一句直接 @ 机器人说"总结一下"，也没用"回复"。agent 没收到过上一句，不知道有链接。这时工具的提示要说清楚该怎么办："请回复那条带链接的消息并 @ 我，或者把链接再贴一次。"

### 4.4 授权、等待、接着处理

**授权卡片必须只发到提问人的私聊。** 第一版这里写错了：现在的代码把邀请发回"请求来的地方"（`Requests.wait` 用原消息的回复地址），私聊里这没问题，群里直接复用就会把授权卡片发到群里。改法：

- 等待什么由工具说明（现在就是），新增一项：这个邀请是给**谁本人**的。Brain 发邀请时，目的地是"这个人的私聊"，不是原消息所在的地方。
- 飞书 connector 的发送增加一种地址：按人发（open_id），和现有的按会话发并列。
- 群里由**系统**发一句固定的话（和现有的固定提示同一种机制，不由模型来说；现有规则本来就要求模型在等待时什么都不说）："需要你授权才能读，授权卡片已私聊发你。"这句话不含链接。

卡片进群的害处不只是暴露链接：回调会核对授权的人是不是提问人，别人点了不会授权成功，但会把这张一次性的邀请用掉，提问人自己就失效了。

**授权好了通知谁。** 现在只通知这个人的私聊 Brain。改成订阅：

- 请求开始等待时，在授权对象里登记"哪个 Brain 的哪个请求在等、等的是哪一代授权"。
- 授权完成后，逐个通知登记过的 Brain，各自确认、各自重试，互不影响。通知里只有引用，没有内容。
- 登记之后立刻回查一次状态（现有的 `hint` 已经这样做），覆盖"授权恰好在登记前完成"。
- 请求取消或过期时，清掉登记。登记本身也带过期时间和数量上限，不会因为一个人在很多群里用过而无限增长。
- 登记里只存"哪种 scope、哪个编号"，通知时由授权对象自己结合应用所属的租户拼出 Brain 的名字，不采信外面传进来的任意名字，避免通知到别的租户。

**接着处理。** 群 Brain 收到通知后，和私聊一样重新核对（同一个人、同一批消息、同一代授权、没过期），再把那一次读取做一遍。读取走的还是同一个工具，所以 4.5 的群类型检查会再做一次。答复发回群里原来那条消息下面。

**发出前的核对**：照旧（授权还在不在）。

### 4.5 外部群：不在群里读，请他私聊

第一版写的是"外部群里读完，答案改发私聊"。Codex 指出这需要群 Brain 和个人 Brain 之间交接：谁持有请求、谁发送、谁重试、谁记下说过的话，以及读之前就得移交，免得内容进了群的记录。这是一整套新机制。

**建议简化（待用户确认）：外部群里根本不读。** agent 回一句固定的话："这个群有外部成员，文档内容不在这里回复。请私聊我发链接。"他到私聊里问，那里的一切本来就能用，也本来就归个人 Brain 管。

- 不需要两个 Brain 之间交接，不需要群 Brain 往私聊发答案。
- 代价：他要在私聊里重新发一次链接，而不是自动收到答案。

判断方法：读文档的工具在群里被调用时，先查一次群信息（`GET /im/v1/chats/:chat_id` 的"是否是外部群"字段）。

| 查到的结果 | 做法 |
|---|---|
| 内部群 | 继续：查授权、读、答在群里 |
| 外部群 | 不读，回上面那句固定的话 |
| 查不到（接口失败、没权限） | 不读，如实说"现在无法确认这个群能不能回复文档内容，请稍后再试或私聊我"。不把"不知道"说成"有外部成员" |

接着处理（授权后重读）时工具会再被调用，所以这个检查会再做一次。

受影响的只有读文档这一个工具。外部群里不涉及文档的普通对话，照常在群里进行。

**有意不做的**（Codex 第一版意见里要求的，这里说明为什么不做）：

- 每次投递前再查一遍提问人和机器人是否还在群里、群是否变成了外部群。从提问到答复，最长是邀请的十分钟加上接着处理的一小时；在这段时间里提问人退群或群加入外部成员，答复仍会发到他当初提问的地方。这和他自己把摘要贴进群、随后有人进群是一回事，飞书本身也会把历史消息给新成员看。
- 群后来变成外部群时，约束 agent 复述以前的结论。那些话已经在群的聊天记录里。

这两条如果要做，都需要成员查询接口、更多权限和每次发送前的额外调用。用户选甲的出发点是不为这类保证加机制。写进 `docs/connectors` 作为已知的界限。

### 4.6 群里几个人各有请求时，互不干扰

现在"可取消的请求""问的是哪一个""答复先等这个人没处理的消息"这几处都按**会话**取，私聊里一个会话就是一个人，没问题。群里一个会话有很多人，直接复用会出错：B 可能看到 A 的请求，甚至取消它；别人在群里说话会一直压住 A 的答复。

改成：这几处在群里都再按**提问人**过滤。

- 列出、取消、替换、消歧：只涉及这次运行所代表的那个人自己的请求。
- "答复不抢在他还没处理的消息前面"：只看这个人自己的未处理消息，别人的不算。

### 4.7 读过之后群里留下什么

和私聊照搬：

- 读过文档的那次运行，记录清掉，只留一句"读过某链接"。
- 答复发在群里的，留作"自己说过的话"，群里后续任何人的追问都能看到。这和群里的人本来就能看到这条答复是一致的。现在的代码只在私聊会话里记"自己说过的话"（`Outbox.#isOwnPrivateMessage` 里写死了私聊），这里要放开到群会话里实际发到群里的、agent 自己写的消息。
- 读过文档之后，那次运行里能用的工具和私聊一样受限（不能再派任务、改记忆等）。后面的运行根据"说过的话"回答时不受限，这和私聊里用户已经定过的做法一致（"不限制"）。

追问：

- 同一个人追问：先根据说过的话回答，需要更多内容时用他的授权重读。
- 另一个人追问：可以根据群里说过的话回答。要重读原文，就得是他自己贴链接、用他自己的授权。

### 4.8 读不了的时候

工具对每种情况返回明确的原因，agent 照实说，不派沙箱去抓，也不建议"把内容贴过来"：

- 他没有授权并且没去授权：请求按现有规则等到邀请过期，悄悄结束。
- 他打不开这篇文档：说他没有权限。
- 文档类型不支持：说是什么类型。
- 外部群、查不到群信息：见 4.5。

另外在派任务工具的说明里补一句通用的话：沙箱打不开需要登录的链接。不为飞书写特例。

## 5. 分步交付

每步一个 PR，先写测试并看到失败，Codex 评审，用户发话后合并。

0. **实测**（不改线上行为）：群信息接口在"安溥"上能不能调通、外部群字段的实际取值、缺权限时返回什么。需要的权限是"查看群信息"一类（`im:chat:read` / `im:chat:readonly` / `im:chat` 任一）。
1. **按人分批**（4.2）。独立上线。
2. **请求按人隔离**（4.6）。对私聊无影响，可以先上。
3. **邀请发给本人、订阅式通知**（4.4）：connector 支持按人发送；授权对象登记并通知在等的 Brain。对私聊行为不变。
4. **群里代表个人 + 群类型检查**（4.1、4.3、4.5、4.7）：到这一步群里才真正能读。`quoted.documents` 也在这一步。
5. **文档和提示**（4.8、`docs/connectors`）。

部署：0–3 不改变群里的行为，可以随做随上；4 和 5 一起上。

上线群读之前要跑通的场景（Codex 列的，按简化后的方案取舍）：两个人同时有请求时互相取消不了；外部群里不读、不发授权卡片；内部群里授权卡片只到私聊；读不了时没有派任务；同一个人和另一个人的追问；等待中的请求过期后悄悄结束。

## 6. Codex 的意见

**初步意见（对最早的设想）**：支持在群里问；要求把内容发进群之前独立确认群有权看。用户看过后选了甲，没有采纳这一条。

**对第一版的评审（2026-11-24）**，四处：

1. 授权卡片和正文都有发错地方的路径：邀请现在发回原消息所在处，群里会进群。建议由个人 Brain 负责授权卡片和外部群的私聊答案。
   → 采纳前半（4.4：邀请发给本人）。后半用"外部群不读"绕开（4.5），待用户确认。
2. "读之前查一次"不够：等待、重试、以后复述时，成员和群类型可能已变。要求恢复前和每次投递前复核。
   → 部分采纳：恢复时会再查群类型（4.5）。每次投递前的成员复核和"群后来变外部"不做，理由见 4.5。
3. 取消、替换、消歧按会话取，群里会串人；别人的消息会压住答复；失败要有明确返回。
   → 采纳（4.6、4.8）。它还建议"从进入读文档流程起就限制工具"；本方案保持和私聊一致：读到内容之后才限制。
4. 按人分批可先做；贴过链接只是候选；从原消息提取结构化的文档链接；通知用持久订阅并在订阅后回查。
   → 采纳（4.1、4.2、4.3、4.4）。

**另一位评审对第一版的意见（用户转来，2026-11-24）**：四个缺口和三处细节，大部分与上面重合。它独有、已补进本版的：等待时群里那句话由系统发而不是模型说；别人点卡片会把邀请用掉；按人分批还要把非人事件和按钮点击分开；订阅要有过期、上限和租户校验；群里"上一句没 @"时的提示；"自己说过的话"现在只记私聊，要放开。

它建议查不到群信息时"按外部群处理、改私聊答复"。本版是"不读，并如实说是无法确认"，同样不会把内容发进群。它也建议在发往群之前再查一次群类型；本版只在读之前和接着处理时查，理由见 4.5。

## 7. 未决和风险

- 4.5 的简化（外部群请他私聊，而不是自动把答案发私聊）要用户确认。

# 在群里读飞书文档

状态：草案，等用户定方向，尚未与 Codex 过完整方案（只问过一次初步意见，见第 6 节）。

## 1. 现在的情况

- 读文档的工具 `feishu_read_document` 只在私聊里有。它以提问人本人的身份、用本人的授权去读。
- 群里没有这个工具。模型看到链接后会派一个沙箱去直接抓，沙箱的出站规则只放行模型服务和 github.com，所以返回 403（`src/workers/sandbox/outbound.ts:61`）。请求根本没到飞书。
- 用户的预期是：在群里发链接或回复一条带链接的消息，@ 机器人，就能读。

为什么当初只做私聊，代码里有三处把它限定死了：

1. `Runner.actingOn`（`src/brain/runner.ts`）：只有 scope 是个人、会话是私聊、消息带 `direct: true` 时，才认定"这次运行代表某个人"。否则没有工具。
2. 授权对象通知"授权好了"时，只通知这个人的私聊 Brain（`src/connectors/feishu-grant.ts:189`）。
3. 一次运行按会话取消息，群里一批消息可能来自几个人，没有"这批消息是谁的"这个概念。

## 2. 目标

在群里，一个人 @ 机器人问一篇他自己贴出链接的飞书文档，agent 用**这个人自己的授权**去读，并答复。

不做的：

- 不用机器人自己的身份读文档。机器人能打开什么，与此无关（和私聊一致）。
- 不借别人的授权。A 贴的链接，B 来问，用的是 B 的授权；B 没权限就读不了。
- 不读别人贴的链接里、提问人自己没有再贴一次的文档（见 4.3）。

## 3. 需要用户定的一件事：答复发到哪里

读是用提问人的授权读的，但群里其他人未必能打开那篇文档。答复发到群里，等于把文档内容给了全群。三种做法：

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| 甲 | 直接答在群里 | 最自然，和一个人把摘要贴到群里是一回事；实现最小 | 群里没权限的人也能看到内容 |
| 乙 | 先确认这个群有权看这篇文档，能确认才答在群里；否则在群里说一声，答案私聊发给提问人（Codex 的意见） | 不会把内容漏给没权限的人 | 见下 |
| 丙 | 一律私聊答复，群里只说"已私聊回复" | 最保守，实现也小 | 群里的人看不到结论，失去在群里问的意义 |

乙的代价，调研后比预想的大：

- 飞书**没有**"某个群能不能看某篇文档"的直接接口。判断当前调用者权限的接口（`permissions/:token/members/auth`）只能查调用者自己。
- 只能间接判断，两条路：
  - 查文档的链接分享设置（`drive/v2/permissions/:token/public`）：如果是"组织内获得链接的人可阅读"，且这个群没有外部成员，就可以认为全群可读。
  - 查文档的协作者列表（`drive/v1/permissions/:token/members`）：看这个群是不是协作者（`member_type: openchat`）。
- 两条路都要提问人**多授权一到两项权限**（`docs:permission.setting:read`、`docs:permission.member:retrieve`），已经授权过的人要重新点一次同意。
- 协作者列表这个接口，普通阅读者不一定调得通（取决于文档的"谁可以查看协作者"设置）。调不通时只能退回私聊答复，用户会觉得"时灵时不灵"。
- 知识库文档的权限是从空间继承的，协作者列表是否包含继承来的成员，文档没有写明，要实测。
- 每次读多两到三次接口调用。

**我的建议是甲，加一条便宜的限制：群里有外部成员（飞书的"外部群"）时，改为私聊答复。**

理由：

- 提问人是在群里、当着所有人的面、自己贴的链接、自己要求调研的。把结论发在群里是他明确要的结果，和他自己读完把摘要贴进群没有区别。责任在提问人，这和私聊里"他打不开的 agent 也打不开"是同一个原则。
- 乙为了一个保证付出的机制很重：两项新权限、三个接口、一套回退逻辑，而且回退会经常触发。这和上次追问功能的教训是同一类（当时的结论：保证本身要先拿出来让用户权衡，而不是默认加机制）。
- 外部群这一条便宜（群信息里一个字段），而且防的是最不该发生的情况：把内部文档内容发给组织外的人。

如果选乙，实现上先做"链接分享 + 非外部群"这一条路，协作者列表那条路实测后再定。

## 4. 方案（按甲写，乙的差别在 4.5）

### 4.1 "这次运行代表谁"扩展到群里

`Runner.actingOn` 现在的判断是：个人 scope + 私聊会话 + 每条消息都是这个人写的普通消息 + 同一个来源。

改成两种情况都认：

- **私聊**：和现在完全一样。
- **群里**：这批消息全部是**同一个人**写的、明确对机器人说的普通消息（不是按钮、不是对审批问题的回答、不是转来的），来自同一个应用和组织。这个人就是这次运行代表的人。

"最近说过的话"（`recent`，用来找他之前贴的链接）在群里相应地取：同一个群会话里、同一个人、一天之内、最多五十条。别人的消息不算。

### 4.2 一批消息按人分开

群里一次运行现在可能把几个人的消息一起处理。读文档要求一次运行只代表一个人，所以在取批次时（`Runner.#batch`）加一条边界，和现有的"回复对象变了就另起一次运行"是同一种规则：

- 在群会话里，写消息的人变了，就另起一次运行。

这样每个人的请求各自在自己的授权下处理，顺序不变。代价是几个人同时说话时，会分成几次运行、几条答复。这本来也更清楚。

### 4.3 读哪篇文档

规则和私聊一样，只是"这个人自己的消息"现在包括他在这个群里的消息：

- 这次请求里他贴的链接；
- 他在这个群里一天之内自己发的消息里贴的链接；
- 他回复的那条自己的消息里的链接。这条消息如果没有 @ 机器人，agent 没收到过，就用 PR #40 的机制取回来（已上线；只取他自己写的）。

别人贴的链接不算他的选择。B 想问 A 贴的文档，要自己再贴一次链接。这一条是为了保持"读哪篇是这个人自己指的"这个原则，也避免有人在群里贴一个链接，引别人的授权去读。

### 4.4 授权、等待、接着处理

- **授权卡片**：照旧只发到提问人的私聊（现在就是这样发的，不经过群）。群里 agent 说一句"需要你授权，已私聊发你"。
- **授权好了通知谁**：现在只通知这个人的私聊 Brain。改成：请求等待时，把"哪个 Brain 在等"登记在授权对象里；授权好了，通知所有登记过的 Brain（私聊的、各个群的）。
- **接着处理**：群 Brain 收到通知后，和私聊一样重新核对（还是同一个人、同一批消息、同一份授权、没过期），再把那一次读取做一遍，答复发回群里原来那条消息下面。
- **发出前的核对**：照旧。授权不在了就不发，换成固定的提示。

### 4.5 答复发到哪里

- **甲**：发在群里。读之前查一次群信息；是外部群就不在群里答，群里说"这个群有外部成员，答案已私聊发你"，答案发到提问人的私聊。
- **乙的差别**：把"是外部群"换成"无法确认全群可读"，判断方法见第 3 节；并在邀请授权时多要相应权限。

私聊答复这条路，两种方案都需要（外部群 / 无法确认），所以要做：群 Brain 把答复的目的地从"群里这条消息"换成"这个人的私聊"。

### 4.6 读过之后群里留下什么

私聊里现在的规则：读过文档的那次运行，记录被清掉，只留一句"读过某链接"；agent 发出去的答复另存，后面的追问可以看到自己说过的话。

群里照搬：

- 那次运行的记录同样清掉。
- 答复发在群里的，照样留作"自己说过的话"，群里后续任何人的追问都能看到。这和群里的人本来就能看到这条答复是一致的。
- 答复改发私聊的（外部群），**不**留在群的记录里，群里后续的运行看不到它。

追问：

- 同一个人追问：和私聊一样，先根据说过的话回答，需要更多内容时用他的授权重读。
- 另一个人追问：可以根据群里已经说过的话回答（那些话全群都看得到）。要重读原文，就得是他自己贴链接、用他自己的授权。

### 4.7 不再派沙箱去抓飞书链接

群里有了读文档的工具之后，模型一般不会再走沙箱。另外在派任务工具的说明里补一句通用的话：沙箱打不开需要登录的链接（不只是飞书）。不为飞书写特例。

读不了的时候（没授权且对方不授权、没权限、文档类型不支持），工具返回明确的原因，agent 照实说，不建议"贴内容过来"之类没有根据的办法。

## 5. 分步交付

每步一个 PR，先写测试并看到失败，Codex 评审，用户发话后合并。

1. **第 0 步，实测**（不改线上行为）：群信息接口里外部群的字段和所需权限；如果选乙，再测两个权限接口在"普通阅读者"身份下的表现、知识库继承。
2. **按人分批**：群会话里换人就另起一次运行（4.2）。独立可上，不依赖后面。
3. **群里代表个人**：`actingOn` 认群里的情况，`recent` 取法，读哪篇的规则（4.1、4.3）。此时群里已能读已授权者的文档。
4. **等待和接着处理**：授权对象登记并通知在等的 Brain（4.4）。
5. **答复目的地**：外部群改发私聊（4.5），以及读后记录的处理（4.6）。
6. **文档和提示**：`docs/connectors`，派任务工具说明（4.7）。

第 3 步上线前，第 5 步必须一起上，否则外部群里会直接答出内容。所以实际部署是 2 单独一次，3–6 一起一次。

## 6. Codex 的初步意见（2026-11-24，对一个更简单的设想给的）

- 支持在群里问。
- 请求要绑定：核实过的人、组织、应用、原文档、群/话题、消息，再去私聊要授权。
- 用这个人的授权；链接取自他自己的原文，或核实过是同一作者的被回复消息。
- 把内容发进群之前，要**独立确认群有权看**；提问人的授权加上他贴了链接，不足以说明这一点。确认不了就群里说一声、私聊答复。
- 私有内容和由它得出的内容，不进群的模型历史、任务交接、日志、可重放的已发消息记录。
- 接着处理和发出前，重新核对身份、目的地、取消/过期、当前权限。
- 每个不同的人追问，各自要有自己的请求和授权。
- 403 要直接处理，不要让模型派沙箱去抓。

本方案与它的差别只有一处：第 3 节建议甲（外部群才私聊），它要求乙（确认不了就私聊）。其余都采纳了。这一处由用户定；定了之后再把完整方案发给 Codex。

## 7. 未决和风险

- 外部群的判断依赖群信息接口的一个字段，所需权限和字段名要在第 0 步实测确认。
- 群里换人就分批，会让"几个人接力补充同一件事"变成几次运行。模型仍能从会话历史看到前面的话，只是工具权限按当次的人算。
- 话题群（每个话题一个会话）里的回复关系和普通群不同，PR #40 的取回机制没有覆盖话题，这里同样先不覆盖。
- 选甲意味着接受：内部群里，没权限打开某文档的同事，可以通过别人的提问看到它的摘要。这是有意的取舍，写进 `docs/connectors`。

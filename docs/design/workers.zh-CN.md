# 把 worker 做成一个统一的概念

状态：定稿，2026-11-25（用户同意）。分步实现，每步一个 PR。第 1、2 步已合并部署（#60、#61）；第 3 步见其 PR。

第 3 步实现时的一处取舍：以本人名义的 worker 没有另写一套 `start` / `look`，而是由原来的 connector 工具承载（worker 写 `tool`，工具写 `hands_to`），授权、等待、接续、投递前复核全部沿用工具已有的那一套；`allowed` 钩子因此没有单独加，撤权后的复核仍在工具和等待请求里。统一工具对模型是同一个入口。

## 1. 现在的样子

agent 能把事情交出去做的地方有两处，是两套互不相干的机制：

| | 沙箱 | 豆包工作 |
|---|---|---|
| 模型看到的 | `dispatch_task` / `task_status` / `cancel_task` | 一个 connector 工具 `doubao_ask` |
| 记录在哪 | Brain 的 `tasks` 表 | connector 自己的 Durable Object 里 |
| 结果怎么回来 | worker 主动汇报，成为收件事件 | Brain 的"等待中的请求"定时去问 |
| 接着做 | 没有（设计见 [task-continuation](task-continuation.zh-CN.md)） | 有，靠这个工具自己的一套规则 |
| 能不能换 | 写死，类型只有 `sandbox` | 在 connector 列表里加减，按聊天应用配对启用 |

后果是真实使用里见到的：先让豆包调研，紧接着追问，模型把追问派给了沙箱。在它眼里这是两个无关的工具，"上一件事是谁做的、追问该找谁"不是它能统一去想的问题。每加一个能干活的地方，就要再写一套记录、一套等待、一套接续规则。

## 2. 目标

- 一个概念：**worker**，能接一件事、过一阵子给出结果的地方。**全部可插拔**（用户 2026-11-25 的要求）：Brain 不内置任何一种，沙箱也只是列在部署配置里的一个 worker；加一个、去掉一个、换一个，只改配置，不动 Brain。
- 一份记录：每件交出去的事（**工作**）由 Brain 统一记着：交给了谁、替谁、在哪个对话里、现在怎样、接的是哪一件。
- 一组工具，一套接续规则：模型看到"有哪些 worker、各自擅长什么""这个人最近交出去过哪些事"，由它决定交给谁、接哪一件。代码只保证下限。

## 3. 方案

### 3.1 worker 的契约

```ts
interface Worker {
  name: string;                 // "sandbox"、"doubao"
  description: string;          // 给模型看：擅长什么、不能做什么
  /** 以谁的名义做事。"person" 的要本人授权，并且只在本人自己的对话里可用。 */
  acts_as: "agent" | "person";
  /** 这条消息的作者在这里能不能用它（比如运营方是否为这个聊天应用配对过）。 */
  offered?(env, event): Promise<boolean>;
  /** 这个 worker 自己的参数（比如沙箱的 `repository`），和工具的参数一样写成 schema。 */
  options?: Record<string, unknown>;
  /**
   * 开始一件事，或接着 `from` 那一件做。四种回答：开始了；需要本人先授权；明确没接
   * （可以如实说"没发"）；发出去了但不知道对方接没接（不能再开一单）。
   */
  start(context, work: { id; brief; options?; from?: WorkRef }): Promise<Started | NeedsAuthorisation | Refused | Uncertain>;
  /** 没有人会来汇报的 worker：Brain 到时候来问。会主动汇报的不实现。问的途中也可能要本人重新授权。 */
  look?(env, work: WorkRef): Promise<{ state: "not_yet"; again_in_ms } | { state: "done"; result } | { state: "gone" } | NeedsAuthorisation>;
  /**
   * 以本人名义的 worker 必须实现：这件工作所依据的授权现在还在不在（复用现有的 `holds` 复核）。
   * Brain 在把这件工作列给模型、回答状态、投递结果之前都问它；不在了，这件工作就不再出现。
   */
  allowed?(env, work: WorkRef): Promise<boolean>;
  /** 会向人提问（比如要审批）的 worker 才实现：把人的决定传回去。 */
  answer?(env, work: WorkRef, decision): Promise<void>;
  /** 能停的才实现。说清是远端停了，还是只是这里不等了。 */
  cancel?(env, work: WorkRef): Promise<"stopped" | "no_longer_waited_for">;
}
```

**什么算 worker，什么不算。** 只有"收一段自然语言的交代、过一阵子做完、给回结果、可以接着问"的才是 worker（沙箱、豆包工作，以后的别的 agent）。要结构化参数、当场给结果的能力（读文档、查日历、操作工单）继续做 connector 的工具，不为了统一把表单塞进 `options`。守住这条，`options` 就一直很薄（现在只有沙箱的 `repository`）。

`start` 是幂等的：同一个工作编号再调一次，得到的是同一次提交。`WorkRef` 对 Brain 不透明，指向的是一次提交（同一个远端会话里可以有多次追问），不只是会话号。

worker 在部署配置里列出，和 connector 并列：

```ts
// src/agent.config.ts
const config = {
  connectors: [consoleConnector, githubConnector, feishuConnector, doubaoConnector],
  workers: [sandboxWorker, doubaoWorker],
  trusted: [...],
};
```

- 沙箱是 `sandboxWorker`，和别的 worker 走同一个契约；不列它，这个部署就没有沙箱，Brain 照常工作。
- 一个 worker 需要的回调、管理接口、授权（比如豆包的 OAuth 回调）仍由它配套的 connector 提供；worker 本身只管接活和给结果。
- Brain 里不出现任何具体 worker 的名字：工具说明、提示里的 worker 列表、名额和并发的数法，都从配置里列出的 worker 来。
- 一个 worker 都没列时，交出去做事的那组工具不出现。

### 3.2 Brain 这一侧

- 一张通用的工作记录表（新表，不复用 `tasks`，原因见第 4 节第 2 步）：工作编号、`worker`、对话、`person`、状态、`parent`（接的是哪一件）、`ref`（worker 自己那边的指向，比如豆包的会话）、授权条件和代次。每件工作只结束一次，接着做永远是一件新的工作，指向它的上一件。沙箱自己的 `tasks` 表照旧，由沙箱这个 worker 用。
- 两种取结果的方式并存，都落到同一条记录上：会汇报的走现有的 worker 事件；要去问的走现有的"等待中的请求"（截止、重试、过期提示都已经有了）。
- 工具合成一组：`hand_over(worker, title, brief, options?, continue_from?)`、`work_status`、`cancel_work`。`options` 按所选 worker 自己声明的 schema 核对：沙箱的 `repository` 就在这里，传给不认它的 worker 直接报错。不为某个 worker 在工具上加专属参数。
- **工具的参数是按当前可用的 worker 拼出来的。** 现有工具全部是严格 schema（`strict: true`、不许多余的键），放不进一个自由的对象。所以每次给模型组装工具时：`worker` 是一个枚举，只列这个人在这个对话里此刻可用的 worker；`options` 的键是这些 worker 各自声明的参数合在一起，每个都可为空，说明里写清归哪个 worker；没有任何 worker 声明参数时不出现 `options`。Brain 里仍然没有任何 worker 的参数名。各 worker 的说明并排放在这一个工具里，谁能做什么、不能做什么在同一处对比。
- 和现在的 `dispatch_task`、以及一切会对外做事的工具一样：读过外部文字的运行不能再 `hand_over`。审批问题（`answer_task`）不变，只有会提问的 worker 用到。
- **同一件事只有一个编号、一组工具**：交给 worker 的事，不管正在等本人授权还是等远端结果，在提示里只出现在"工作"列表里，不再同时出现在"等待中的请求"里；取消用 `cancel_work`，它在内部结束对应的等待。`cancel_request` 只留给不是 worker 的等待（比如读文档的授权）。
- **以本人名义做的事，结果不进工作记录**：`acts_as: "person"` 的工作在记录里只有索引和状态，没有正文。它的结果仍走现在"外部文字"的那条路：给模型和投递之前复核授权，用完按原有时机清掉。`work_status` 对这类工作只回状态，不回远端内容。
- 提示里给模型两样东西：可用的 worker 和各自的说明；这个人在这个对话里最近的几件工作（编号、交给了谁、标题、状态）。追问接哪一件、交给谁，由模型判断。

### 3.3 代码保证的下限（不靠提示）

- 接着做：只能接同一个对话、同一个 worker 的工作，上一件的审批和授权不带过来。
- 谁能看、能查、能取消、能接，按 `acts_as` 分：
  - `acts_as: "person"`：严格只有本人，只在本人自己的对话里。
  - `acts_as: "agent"`（沙箱）：照现在的规则，按对话和现有的决定人/审批归属，不收窄。群里甲发起乙查进度、代码仓库里由事件发起而没有请求人的任务，都和现在一样。没有请求人的不补猜归属。
- `acts_as: "person"` 的 worker：开一件新的事要本人在这条消息里说了要交给它（"说了"怎么认由 worker 自己在 `start` 里判断，它拿得到本人的原话；Brain 不维护各个 worker 的别名表）；接着做要么本人回复的就是那件事的答复，要么本人写这句话时看到的最后一条答复就是它（PR #54 的规则，原样搬过来成为通用规则）。
- 本人标了引用就不猜；分不清就不发。

## 4. 分步

每步一个 PR，测试先行，Codex 复核。按 Codex 的意见切得更小：先适配、再记索引、最后才换模型看到的工具；worker 自己那边的记录先不搬。

1. **薄适配**：加 `Worker` 契约和配置里的 `workers` 列表，沙箱的启动和取消真正改走这条路（Brain 不再直接碰沙箱的绑定）。以本人名义的 worker（豆包）等到有调用方的那一步再接，不提交没人调用的代码。旧工具、审批链（`answer`、回执丢失后按问题编号复核）原样保留，仍找原来的沙箱。行为不变，测试不变。配置里停用沙箱的含义先定为：不再接新的，已有任务的审批、汇报、取消走完。
   - 紧接着的一个小 PR：**启动回执丢了也能收尾**。现在启动没收到回执时会试着取消，取消也没回音就直接记失败、放掉名额、让人重试，而远端可能已经在跑。改为用提交前就落库的工作编号找回同一次启动（`start` 幂等）；确认停了才放名额；确认不了就如实说"不知道它有没有开始"。验收：模拟"远端已接单，启动和取消的回执都丢了"，恢复后只执行一次，并且能收尾。
2. **工作索引，独立的一张表**：每件交出去的事在 Brain 里有一行，用稳定的工作编号幂等更新，关联到 worker 那边原有的记录。**不往 `tasks` 里写**：旧代码会把那里的每一行都当成沙箱任务（算进沙箱名额、列进提示、放弃运行时标成失败），回滚到旧版本后也一样。独立的表旧版本直接看不见，所以整步可回滚。执行和投递仍走各自原来的路。只写不读。豆包那边的提交去重、阶段、远端消息号、授权代次留在原处。
   - "一件事"的编号：恢复、重新授权沿用最初那次请求的编号；重复的请求被折叠后，用实际留下来的那个；同一个远端会话里真正新的一次追问另起一行。等授权或等启动回执时，远端的指向可以先空着，之后只补不改。
   - 验收：一次重新授权加一次进程重启之后，一行索引、一次实际提交、一份最终回执。
3. **一组工具和统一接续**：向模型开放 `hand_over` 等三个工具，提示里列出 worker 和最近的工作。旧工具名留作内部别名，给在途请求的重放和已送达答复的引用用；不能只凭"当前没有在跑的"就下线。从这步起用户看到的行为才变。
4. **Brain 里不再有具体 worker 的名字**：沙箱专属的东西（并发名额的数法、按仓库派活的参数、审批提问）移到 `sandboxWorker` 自己那边或契约的可选部分；验收是配置里去掉沙箱后全部测试（除沙箱自己的）照过。
5. **之后再定**：要不要把 worker 那边的记录搬进 Brain；沙箱的接着做（[task-continuation](task-continuation.zh-CN.md) 的快照方案）独立做，接在同一个 `continue_from` 上。

### 4.1 每步都要守住的

- **一件事只交一次**：`start` 对同一个工作编号重试，找回的是同一次提交；发出去没收到回执，要能说"对方接没接不知道"，不能当成拒绝再开一单。
- **结果只投递一次**：tasks 记的是给用户看的工作，等待请求（continuations）只管某一次等待的授权、期限和投递，两者用工作编号关联。指定唯一的结果投递者，不让任务事件和等待请求各发一遍。停止等待之后迟到的结果不再发。
- **授权复核不绕过**：读结果、给模型、投递之前的授权复核照旧；`work_status` 不能变成绕过复核读结果的入口。
- **撤权后不泄露，靠问出来而不是靠记着**：工作记录里存着这件工作所依据的授权条件和代次（第 2 步加这两列）。列给模型、回答状态、投递结果之前，以本人名义的工作都用 `allowed` 问一遍；撤权、换配对之后它就不再出现，迟到的结果不发。
- **可见性一致**：最近工作的列表、状态查询、取消用同一套过滤（见 3.3，按 `acts_as` 分）；模型给的 `continue_from` 由执行器核对：同一个对话、同一个 worker、确实送达过、当前授权一致，以本人名义的还要是本人。
- **取消说清楚**：区分"远端已经停了"和"这里不等了，远端可能还在跑"。
- **名额不串**：每个 worker 的并发上限只数它自己的工作。按仓库派沙箱的参数和同仓限制保留，作为那个 worker 自己的参数。

### 4.2 验收重点

- 同一对话里两件工作的结果各归各的。
- 对方已接单但回执丢了，重放只开一单。
- 取消和结果同时到，只通知一次。
- 撤权之后，工作列表、状态、迟到的结果都不泄露。
- 升级前发出的答复，升级后仍能正确追问。
- 第 3 步上线前，用真实模型跑一组专门找茬的对话，把每个 worker 的说明调准：调研后追问、写代码后追问、两个 worker 交替追问、没点名时会不会误选以本人名义的 worker。另用固定调用验证话实际发到了哪里。

## 5. 不做

- 不做多个 worker 之间的编排、互相转交。
- 不做通用任务队列；并发上限、沙箱名额照旧。
- 不改审批、不改授权模型。

## 6. 代价和要定的事

- 模型的工具从"每个 worker 各一个"变成"一个工具选 worker"。好处是加 worker 不加工具、接续规则只有一套；代价是 worker 的说明要写得让模型选得准，需要真实使用来调。
- 第 1、2 步之后有一段时间新旧两套并存（旧工具在用，索引只写不读），这是为了每步都能退回。
- **已定（用户，2026-11-25）：合成一组工具。** 这个决定可以退：第 1、2 步之后骨架已经通了，第 3 步上线后如果某个 worker 确实需要自己的工具名，在同一个契约上再套一个薄入口即可。
- 选错 worker 的后果有代码兜底：把新的事交给以本人名义的 worker 而本人没点名，会被拒绝，模型当场改派；追问时最近工作的列表里写着每件事是谁做的。
- 已定或已做：PR #54（追问不点名也接到原会话）已合并，它的规则在第 3 步成为通用规则；沙箱的接着做排在第 3 步之后，直接落在统一的 `continue_from` 上，不先改旧的 `dispatch_task` 再迁一次。
- 已定：worker 全部可插拔，沙箱不特殊（用户，2026-11-25）。

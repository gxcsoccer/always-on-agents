# 设计：以本人的 GitHub 身份做事

状态：草案（v4），2026-11-26。按一份对照代码和 GitHub 文档写的书面评审改过（见 §7）；Codex 评审过 v2，结论和要改的地方在 §8，其中与正文不同的以 §8 为准。尚未实现。RFC 在 issue #95。

这份文档回答一个问题：一个人在聊天里让 agent 去 GitHub 上做一件事（改他自己的私有仓库、提一个 issue），agent 用谁的权限、怎么拿到、边界在哪。

---

## 1. 两个真实的场景

- **私聊里改私有仓库。** 让 agent 在自己的私有仓库里改 README，沙箱克隆时 GitHub 要求登录，任务失败。
- **群里让它提 issue。** "把我们刚才的讨论在某仓库里提个 issue"，agent 答："我目前没有可用的 GitHub 身份授权或创建 Issue 的工具"，只能把标题和正文贴出来让人自己去提。

两件事缺的是同一样东西：这个人对 GitHub 的授权。第二件还缺工具。

## 2. 现状

GitHub connector 现在只有一个方向：GitHub 把事件推进来（issue、PR、评论），形成"仓库自己的会话"，agent 用 App 的安装凭据在那个仓库里回复、评审。

凭据只借给两种任务（`TaskSandbox.githubToken`）：仓库自己的会话发起的，和管理员绑定了该仓库的群里发起的。其余一律不借。这是有意的："身在租户里，不等于能访问租户接入的全部代码。"

另外两个 connector 已经有"以本人名义"的做法，可以照着做：

- 读飞书文档：`FeishuGrant` 按人保存授权，工具答"还不行"（`Waiting`），Brain 把授权卡片发给本人，授权完成后请求自己接着做。
- 以本人名义交办给另一个 agent：一个插在聊天 connector 上的 connector（`serves`、`offers`），自己没有入口，只添一件事。

## 3. 提议

### 3.1 权限：GitHub 自己的交集

GitHub App 代表用户取得的令牌（user access token），只能访问"这个用户有权限，并且 App 也被安装到"的资源。官方文档原话："A GitHub App user access token only has permissions that both the user and the app have."

所以不需要我们维护"谁能看哪个仓库"：

- App 没装到的仓库，谁也碰不到。
- 装到了但这个人没权限的仓库，用他的令牌碰不到。
- 用他的令牌做的事，在 GitHub 上记在他名下，带 App 的标记。

已核对（GitHub 官方文档）：

- 令牌默认 8 小时过期，刷新令牌 6 个月（要开启"令牌会过期"）。刷新令牌用一次就换，而且"用过之后，那个刷新令牌和旧的用户令牌都不再有效"。
- 有网页授权（建议 PKCE）和设备码两种流程。
- **可以直接用于 HTTPS 的 git**：App 有 `Contents` 权限即可（要改 `.github/workflows` 另需 `Workflows`），凭据形式和现在安装令牌用的一样：`x-access-token:<令牌>`。出口代理不用改写法。
- **提交的作者和提交者不因令牌而变**：它们是容器里 `git commit` 写的（现在由任务固定成 agent 的名字和地址）。用户令牌只影响 GitHub 侧的权限判断和"这次推送是谁做的"。

**不用 `repository_id` 限定单仓库**（v1 曾倾向这么做）：它只能在"用授权码换令牌"时给，刷新时不能给，所以每换一个仓库就得让人重新授权一次；而且文档写明"App 或用户访问不了那个仓库时，这个参数会被忽略"，也就是会悄悄退回成不受限的令牌。

单仓库的边界本来就不靠它：令牌从不进容器，容器发往 GitHub 的每个请求都经过出口代理，而出口代理只放行 git 的那几个端点，并且只给"这件任务所在的那个仓库"加凭据（`Outbound.#github`）。所以做法是：按人保存一个可刷新的通用令牌，留在授权对象里；出口按仓库放行；再加上下面的租户核对。

### 3.1.1 租户的边界：交集还不够

同一个 GitHub App 可以被多个租户安装（Registry 记着"哪个安装属于哪个租户"），现有的不变量是：一个租户的任务碰不到另一个租户的仓库。只看"用户与 App 的交集"会破掉它：一个人同时在两个装了这个 App 的组织里，或者给自己的个人账号也装了，他就能在租户甲的聊天里，用租户甲的沙箱和额度，去拉租户乙或他个人的仓库。

所以借出之前要核对：**目标仓库属于当前租户名下的某个安装**（用 App 的身份查这个仓库的安装，和 Registry 里该租户的安装比对）。要不要允许私聊里访问个人账号安装的仓库，做成租户级的显式开关，默认关。

### 3.2 授权放在 GitHub connector 里

新增一个按人保存 GitHub 授权的对象，做法与 `FeishuGrant` 相同：

- 一人一个，名字是"他是谁"的哈希；令牌用部署的 `GRANTS_KEY` 加密保存。
- 邀请由它生成，卡片在发送的那一刻才做出来，链接不经过模型，也不留在 Brain。
- 换新令牌只在这里做，一次一个；结果不确定就作废，重新请本人授权。
- 作废会开启新的一代，之前发出去的邀请和在途的回调都不能再装进令牌。

这个人是聊天 connector 认证的身份；他对应哪个 GitHub 用户，以授权时 GitHub 说的为准，记下来。

GitHub App 的凭据（client id、client secret）是部署时由运营方设置的，和现在的 App id、私钥一样，代码里不写任何具体的 App。

**是否抽出公共的授权对象**：这是第三个"按人保存 OAuth 授权"的对象。前两个已经共用了一组加解密和 PKCE 的函数（`feishu-grant.ts` 导出）。是照样再写一个，还是现在抽出一个通用的基础，请评审时一起看。倾向：先照样写，行为稳定后再抽，避免为了抽象去动已经在线上的两个。

### 3.3 Brain 这边的工具：以本人名义

GitHub connector 增加给"聊天里的人"用的工具（`serves` 聊天 connector，`effect: "act"`，没授权时答 `Waiting`，授权后自己接着做）：

| 工具 | 做什么 | 第一版 |
|---|---|---|
| `github_create_issue(repo, title, body)` | 以本人名义建 issue | 做 |
| `github_comment(repo, number, body)` | 以本人名义评论 | 做 |
| `github_read(repo, number)` | 读一个 issue / PR 及其状态 | 做（只读，也是 #87 需要的） |
| 建 PR、合并、改标签 | — | 不做，另议 |

建 issue 和评论是对外的动作。沿用现有的规矩：只有本人自己发起的那一轮才能用；读过外部文本的那一轮不能用。

### 3.4 沙箱这边：凭据由 connector 决定

`TaskSandbox.githubToken` 里"借不借"的判断挪到 GitHub connector，按顺序：

1. 仓库自己的会话、管理员绑定的群：App 的安装令牌（不变）。
2. 否则，私聊里、任务有唯一明确的交办人、他有有效的授权、仓库过了 3.1.1 的租户核对：他的用户令牌。
3. 否则：没有凭据，只能读公开仓库（不变）。

令牌仍然只在出口代理里加到发往 GitHub 的请求上，沙箱里看不到；任务结束即停止出借（不变）。推送照旧要审批。

**授权在启动沙箱之前要，不在沙箱里等。** 沙箱一启动就占租户的名额、开始计启动时限、同步去克隆；让容器空等一个人去点卡片，白占名额，还得在任务里另造一套等待和卡片。所以分两段：

- **启动前**（Brain 这边）：交办私有仓库而本人没有授权时，不建任务、不占名额，走现有的"还不行"机制（`Waiting`、邀请卡片、条件达成后接着做），和读文档、以本人名义交办是同一套。授权完成后才真正启动。
- **运行中**（出口代理）：每次要凭据都向授权对象现取（它自己负责换新，一次一个）；任务里不长期缓存用户令牌。中途令牌被撤销，请求直接失败，不把容器挂起来等新的授权。

怎么知道一个仓库要不要授权：交办前不带凭据探一下 git 的端点；公开的直接放行，不弹授权。读不到（私有或不存在）才走授权，而且不告诉对方"这个私有仓库存在不存在"。

**只借给本人指过的仓库。** 和读文档"只读本人贴出链接的那篇"同理：用本人令牌去克隆的仓库，必须是他本人在这次或最近的话里明确提到的。防止模型猜错，或被上下文里的文字引去克隆他别的私有仓库。

**接着做（`continue_from`）也要复核。** 接续时沙箱跳过克隆，直接恢复上一件的工作区。上一件若是用本人的 GitHub 授权拉的私有仓库，接续之前要再确认他的授权还有效，否则撤权之后一天内仍能凭快照继续读写那份代码。

### 3.5 群里

- **以本人名义建 issue、评论**：可以，群里和私聊里一样。内容是他要公开发到仓库里的，动作记在他名下。授权卡片只给他本人看（和群里读文档一样：卡片只给提问的人看，答复照常发在群里）。
- **把本人的仓库权限借给沙箱任务**：第一版只在私聊里借，群里不借。代码的泄露面比一篇文档大得多；而沙箱任务在群里是"会话的"：进度、快照、接续、审批问题都按群共享，就算把结果私下发给发起人，别人仍可能通过接续或任务上下文碰到那份代码。把整套沙箱拆成群里一人一份，代价大而且容易漏。
- **管理员绑定群的做法保留**，两者互补：私聊的个人授权给个人处理自己的仓库；绑定的群给一个项目的人围着一个仓库协作，不必人人授权，也没有"借了某人的权限给群里别人看"的问题。

### 3.6 身份怎么对上

聊天里的人和 GitHub 用户没有共同的编号，授权时浏览器里登录的可能是另一个账号（测试号、别人的）。三条约束：

1. **认数字编号，不认登录名**（登录名可以改）。
2. **已经对上过的要一致**：这个人之前绑定过某个 GitHub 用户，再授权回来的必须是同一个，否则拒绝并提示换账号；同一个 GitHub 用户已经被本租户另一个人绑定，也拒绝。换绑要先显式解绑。登记放在 Registry 已有的身份表里。
3. **说出来**：授权成功的页面和第一次确认的消息里写明"已绑定 GitHub 账号 @某某"。

### 3.7 提交的署名

保持现状：作者和提交者都是 agent（由任务固定，模型和人都改不了），在提交说明里加一行 `Co-authored-by` 或 `Requested-by` 指向本人。这样如实反映"这是 agent 在沙箱里做的提交"。

如果某些仓库的规则要求作者必须是已验证的组织成员，备选是作者写本人（用 GitHub 给的 noreply 地址，从他的账号读出来，不让模型或人自己填），提交者仍是 agent。第一版不做。

### 3.8 撤销

- **本人说取消**：授权对象作废（开启新的一代，清掉令牌和没用完的邀请），同时尽力调 GitHub 的接口把这个人对 App 的授权删掉。正在用他凭据跑的任务一并停掉（和"撤权即止"的一贯做法一致）。触发方式尽量是固定的指令或卡片，不靠模型从一段外来文字里"理解"出要撤销。
- **本人在 GitHub 上撤销**：GitHub 会推 `github_app_authorization` 事件（App 不能不订阅它）。收到就清掉对应的授权，不等下一次用到才发现。
- **换新时的并发**：刷新令牌用一次就换，旧的用户令牌同时失效。同一个人同时跑两件任务时，不能各自拿着旧令牌：都从授权对象现取；碰到 401 先看是不是"刚被另一次换新顶掉的旧令牌"，是就重取一次。

## 4. 前提

- 需要一个真实的 GitHub App：开启"令牌会过期"，设置回调地址，记下 client id 和 client secret（和现有的 App id 不是同一个值），装到要用的仓库或组织。权限尽量收紧：用户令牌能做的事以 App 的权限为上限。这一步要运营方在 GitHub 上操作。
- `github-app.ts` 开头写着"尚未在真实的 GitHub App 上验证"。这次要一并验证。

## 5. 实施顺序

按 Codex 的建议，第一步缩到最小，先跑通一条完整的线：

1. **在群里明确点名一个仓库，建一个 issue。** 只要 App 的 Issues 写权限。包括：授权对象（单写，复用现成的 PKCE、加密和测试约定）、`github_create_issue`、租户的安装核对、身份绑定、给合适的人看的回执。验收："明确要求建 issue → 本人授权 → 只建一次 → 原会话收到回执"；授权回调重复仍然只有一个 issue；租户甲解绑时，租户乙的同一个 GitHub 用户照常可用。
2. **`github_read`**（`effect: "read"`，和 #87 共用一个读的适配器）和 **`github_comment`**。
3. **私聊里的私有仓库沙箱**：启动前授权接到交办上（§8.1）；运行中现取；接续和快照恢复时复核；撤销时停任务。
4. 评测：没授权时让它提 issue → 走授权而不是贴正文；授权后 → 直接建；群里让它读本人才看得到的仓库 → 结果转到私聊。

每步一个 PR，测试先行，真实环境实测。第 1 步之前先用一个真实的 App 走一遍授权、换新、撤销。

## 6. 请评审重点看

1. 用户令牌只凭"用户与 App 的交集"作边界，够不够；有没有 App 权限配置不当时会放大的情况（比如 App 装到了整个组织）。
2. 沙箱拿到的是用户令牌：任务里的 agent 能用它做 App 权限范围内、这个人能做的一切（不只是当前仓库，除非限定 `repository_id`）。限定到单仓库是否足够；出口代理现有的"按仓库放行"是否还成立。
3. 没授权时"拒绝交办 + 让模型去调授权工具"的两步，会不会别扭；有没有更顺的做法而不引入"任务等授权"的新状态。
4. 群里的两条规则（动作可以、借仓库权限不行）是否自洽，有没有绕过的路。
5. 身份对应：聊天里的人 ↔ GitHub 用户，以授权时 GitHub 的回答为准，是否需要和已有的身份登记（`linkIdentity`）核对。
6. 第三个授权对象：照写还是抽公共基础。
7. 第一版工具的范围是否合适；`github_read` 与 #87 的只读工具是否应当是同一组。

## 7. 评审记录

一份对照代码和 GitHub 文档写的书面评审（针对 RFC 和 v1），我逐条核对了它引用的文档和代码，属实，v2 按它改了：

- 核实了两件 v1 标为"没核对"的事：用户令牌可以直接用于 HTTPS 的 git，凭据形式不变；提交的作者和提交者不受令牌影响（§3.1）。
- **不用 `repository_id`**：刷新时不能带，访问不了时还会被悄悄忽略。改为通用令牌留在授权对象里，靠出口代理按仓库放行（§3.1）。
- **租户边界**：只看"用户与 App 的交集"会让一个人跨租户拉代码；借出前核对仓库属于当前租户的安装（§3.1.1）。
- **授权前置**：不在沙箱里等授权；启动前走现有的等待机制，运行中每次现取（§3.4）。v1 的"拒绝交办再让模型去调授权工具"去掉了。
- 接续时复核授权；只借给本人指过的仓库；公开仓库不弹授权（§3.4）。
- 群里第一版不借仓库权限，并更正了对"群里读文档"的描述：是卡片只给提问人看，答复仍在群里（§3.5）。
- 身份按数字编号对上，与已有绑定核对（§3.6）；署名保持 agent（§3.7）；撤销的三条路径和换新的并发（§3.8）。

## 8. Codex 的评审（v2）

结论：赞成授权放在 GitHub connector、在启动沙箱之前完成。建议先交付"群里明确点名仓库建一个 issue"，私聊私有仓库的沙箱等下面的边界写清再接。它没有用真实的 App 做过授权、推送或建 issue。

### 8.1 启动前授权怎么接到交办上

现在有两条路：通过 connector 的工具交办的 worker 才会处理"还不行"；沙箱是 Brain 直接启动的。而且等待的请求恢复时，是原样重放原来那次工具调用，新的一轮模型只能说话。所以"单独一个授权工具，授权完模型再交办"是接不上的。

做法：保留一个入口。在"worker 和 options 已校验、还没启动"的位置接一个内部操作"授权后交办原来那件沙箱任务"：有授权就直接启动；没有就用现有的等待机制把原来的标题、内容、仓库、接续对象、发起人的证据和原会话存下来，回调只重放这一个操作。

- 启动者始终是 Brain。
- 用原请求的编号作为任务的幂等编号（恢复时调用编号每次会变）。
- 原发起人由等待机制复核后传进去，不靠新的一轮从消息里找人。
- 取消、超时：启动零次。回调或启动回执重放：只有一件任务。
- 沙箱的名额、排队、审批照旧，不为了接等待机制把沙箱改成 connector 的 worker。

### 8.2 安装核对管所有用本人凭据的地方

沙箱和建 issue、读、评论用同一个判断：用 App 的身份查目标仓库此刻的安装，按仓库的数字编号、安装编号、App 编号和 Registry 里的当前租户核对，再看本人的实际权限。

仓库换主、改名后被同名仓库顶替、安装移出租户或被暂停之后，待执行的动作、实际的推送、接续、同一任务从快照恢复，都要重新过这一关。匿名读公开仓库保留；限流和断网不该触发授权。

**删掉"允许个人账号的安装"这个开关。** 开关证明不了归属。运营方已经把某人的个人安装登记到这个租户，就按同一条规则走；否则拒绝。以后要开例外，得核对安装的所有者就是当前授权的人，而且没绑到别的租户。

### 8.3 最大的风险：结果发给谁

私聊里的沙箱限制是对的；但"群里让它读本人才看得到的私有 issue"还没回答。卡片私下发只保护了卡片，正文、仓库名、链接、报错照样会进群的记录。

第一版：群里只对公开的、或已绑定给该群的目标回传结果，其他私有的转到本人的私聊。群里建 issue 要有明确的目标和明确同意发出去的内容：拿到授权不等于同意把整段群聊发出去。创建的请求发出去了但回执不明，保留为待核对，不盲目重发。

### 8.4 撤销和身份的两个坑

- GitHub 的"删除授权"会删掉这个 GitHub 用户对这个 App 的**所有**令牌，不能用它实现"只解除这个租户的绑定"。本地解绑：先让本租户的授权和任务失效。GitHub 上的全局撤销另说清影响，并让所有相关租户的绑定失效。
- Registry 的 `linkIdentity` 是会覆盖的写入，表只按租户、来源、外部编号唯一。自助授权要有单独的原子绑定和冲突检查，不能覆盖管理员做的映射。用 GitHub 的数字编号；一次性的绑定还要验证点卡片的人就是发起授权的那个人。

### 8.5 可以晚做的，和要改的措辞

- 第三个授权对象先单写，不抽公共基础。
- `github_read` 标成只读；定时器（#87）用它时按自己的发起人、仓库、受众和期限取权。
- 署名保持 agent。**默认不加 `Co-authored-by`**：委托或批准不等于共同创作；要追溯用内部的任务回执。（§3.7 里写的"加一行"作废。）
- "GitHub 上带 App 的标记"只适用于相应的接口动作，不要说普通的 git 提交上也有。
- GitHub 另有按仓库和权限收窄令牌的接口，沙箱阶段可以验证要不要用，不妨碍先做建 issue。

## 9. 第二份书面评审（针对 v1）

它评的是 v1，其中和 v2、v3 已经改掉的重合的不再列（`repository_id`、租户边界、授权前置、身份、撤销、换新并发）。我核对了它引用的代码，属实。新增的四点写在这里，以本节为准：

### 9.1 建 issue、评论要能重放

工具可能在中断后被重放，契约要求"跑两次也安全"（`ConnectorTool` 的说明）。读是天然安全的；`POST` 一个 issue 或一条评论不是：发出去了、回执没拿到，重放就是第二个 issue。

做法照 GitHub connector 现有的评论投递：正文末尾带一个由这次调用编号决定的隐形标记，重试之前先按标记查有没有已经建好的（并核对是不是这个账号发的，别人引用了标记的不算）。发出去了但查不清的，保留为待核对，告诉模型"可能已经建了"，不盲目再发。

### 9.2 读的工具不绑死在个人授权上

#87 要的是定时器醒来查 CI、PR、issue 的状态，而定时器那一轮没有"本人"（`actingFor` 为空），以个人名义的工具它用不了。仓库自己的会话和绑定的群本来就有 App 的安装令牌，也没理由让人先做个人授权才能读。

所以 `github_read` 和 #87 是同一组只读工具，用 §3.4 的同一条凭据链，只是定时器和没有本人的轮次只走其中两档：

1. 仓库会话、绑定的群：安装令牌。
2. 有明确的本人、他有授权、过了租户核对：他的令牌（群里见 9.3）。
3. 公开仓库：匿名。

第一步（建 issue）先把这条凭据链写成一个函数，接口对"有本人"和"没有本人"都成立，免得做 #87 时推倒重来。

### 9.3 群里的规则补齐

- **群里读私有的东西**：第一版群里的 `github_read` 不借个人令牌，只走安装令牌和匿名。某人在群里查自己才看得到的 issue，内容发进群里就等于给了全群；这类请求转到他的私聊（与 §8.3 一致）。
- **群里以本人名义写**：别人在群里说的话，对这个人来说是不可信的输入。"把刚才的讨论提个 issue"是用他的名义对外发布一段主要由别人写的内容，而且没有审批这一步。约束：目标仓库必须是他本人明确说的；外部群里不做；发出去之前把标题和正文给他看，他确认了才建（这一条是否需要，见下面要定的事）。
- **授权卡片只给他本人看**，不发到群里：别人点了会把一次性的邀请用掉。

### 9.4 把公用的小函数挪出来

第三个授权对象照旧单写。但加密、解密、PKCE、随机数、密钥、期限这几个无状态的函数现在住在 `feishu-grant.ts` 里，第二个授权对象已经在反过来引用它。挪到一个独立的文件，三处都从那里引用。只挪函数，不抽状态机。

用本人令牌能调的 GitHub 接口用白名单写死（建 issue、评论、读 issue / PR / 检查状态），不做成"任意请求"。

## 10. 要用户定的

1. **群里建 issue 之前要不要先给本人看一眼再发。** 多一步确认，换来的是：内容主要来自别人的发言时，不会在他没看过的情况下以他的名义发出去。私聊里他自己说的内容可以直接建。
2. **第一步是否就按"群里明确点名仓库建一个 issue"来做**，私有仓库的沙箱放在后面。
3. **GitHub App**：需要建一个，或者沿用已有的；第一步只需要 Issues 的读写权限。

# 设计：以本人的 GitHub 身份做事

状态：草案（v1），2026-11-26。待评审，尚未实现。RFC 在 issue #95。

这份文档回答一个问题：一个人在聊天里让 agent 去 GitHub 上做一件事（改他自己的私有仓库、提一个 issue），agent 用谁的权限、怎么拿到、边界在哪。

---

## 1. 两个真实的场景

- **私聊里改私有仓库。** 让 agent 在自己的私有仓库里改 README，沙箱克隆时 GitHub 要求登录，任务失败。
- **群里让它提 issue。** "把我们刚才的讨论在某仓库里提个 issue"，agent 答："我目前没有可用的 GitHub 身份授权或创建 Issue 的工具"，只能把标题和正文贴出来让人自己去提。

两件事缺的是同一样东西：这个人对 GitHub 的授权。第二件还缺工具。

## 2. 现状

GitHub connector 现在只有一个方向：GitHub 把事件推进来（issue、PR、评论），形成"仓库自己的会话"，agent 用 App 的安装凭据在那个仓库里回复、评审。

凭据只借给两种任务（`TaskSandbox.githubToken`）：仓库自己的会话发起的，和管理员绑定了该仓库的群里发起的。其余一律不借。这是有意的："身在租户里，不等于能访问租户接入的全部代码。"

另外两个 connector 已经有"以本人名义"的做法，可以照着做：

- 读飞书文档：`FeishuGrant` 按人保存授权，工具答"还不行"（`Waiting`），Brain 把授权卡片发给本人，授权完成后请求自己接着做。
- 以本人名义交办给另一个 agent：一个插在聊天 connector 上的 connector（`serves`、`offers`），自己没有入口，只添一件事。

## 3. 提议

### 3.1 权限：GitHub 自己的交集

GitHub App 代表用户取得的令牌（user access token），只能访问"这个用户有权限，并且 App 也被安装到"的资源。官方文档原话："A GitHub App user access token only has permissions that both the user and the app have."

所以不需要我们维护"谁能看哪个仓库"：

- App 没装到的仓库，谁也碰不到。
- 装到了但这个人没权限的仓库，用他的令牌碰不到。
- 用他的令牌做的事，在 GitHub 上记在他名下，带 App 的标记。

已核对：令牌默认 8 小时过期，刷新令牌 6 个月（要开启"令牌会过期"）；有网页授权（建议 PKCE）和设备码两种流程；可以带 `repository_id` 把令牌限定到一个仓库。

**没核对**：这种令牌能否直接用于 HTTPS 的 `git clone` / `git push`（现在安装令牌用的是 `x-access-token:<token>` 的基本认证），以及推送时提交怎么署名。要查文档并在真实 App 上实测。

### 3.2 授权放在 GitHub connector 里

新增一个按人保存 GitHub 授权的对象，做法与 `FeishuGrant` 相同：

- 一人一个，名字是"他是谁"的哈希；令牌用部署的 `GRANTS_KEY` 加密保存。
- 邀请由它生成，卡片在发送的那一刻才做出来，链接不经过模型，也不留在 Brain。
- 换新令牌只在这里做，一次一个；结果不确定就作废，重新请本人授权。
- 作废会开启新的一代，之前发出去的邀请和在途的回调都不能再装进令牌。

这个人是聊天 connector 认证的身份；他对应哪个 GitHub 用户，以授权时 GitHub 说的为准，记下来。

GitHub App 的凭据（client id、client secret）是部署时由运营方设置的，和现在的 App id、私钥一样，代码里不写任何具体的 App。

**是否抽出公共的授权对象**：这是第三个"按人保存 OAuth 授权"的对象。前两个已经共用了一组加解密和 PKCE 的函数（`feishu-grant.ts` 导出）。是照样再写一个，还是现在抽出一个通用的基础，请评审时一起看。倾向：先照样写，行为稳定后再抽，避免为了抽象去动已经在线上的两个。

### 3.3 Brain 这边的工具：以本人名义

GitHub connector 增加给"聊天里的人"用的工具（`serves` 聊天 connector，`effect: "act"`，没授权时答 `Waiting`，授权后自己接着做）：

| 工具 | 做什么 | 第一版 |
|---|---|---|
| `github_create_issue(repo, title, body)` | 以本人名义建 issue | 做 |
| `github_comment(repo, number, body)` | 以本人名义评论 | 做 |
| `github_read(repo, number)` | 读一个 issue / PR 及其状态 | 做（只读，也是 #87 需要的） |
| 建 PR、合并、改标签 | — | 不做，另议 |

建 issue 和评论是对外的动作。沿用现有的规矩：只有本人自己发起的那一轮才能用；读过外部文本的那一轮不能用。

### 3.4 沙箱这边：凭据由 connector 决定

`TaskSandbox.githubToken` 里"借不借"的判断挪到 GitHub connector，按顺序：

1. 仓库自己的会话、管理员绑定的群：App 的安装令牌（不变）。
2. 否则，任务有唯一明确的交办人、他有有效的授权：他的用户令牌，限定到这个仓库。
3. 否则：没有凭据，只能读公开仓库（不变）。

令牌仍然只在出口代理里加到发往 GitHub 的请求上，沙箱里看不到；任务结束即停止出借（不变）。推送照旧要审批。

**没授权时怎么办**：沙箱任务不是"等一下再接着做"的请求，不能像工具那样答 `Waiting`。第一版：交办前由 worker 看一眼这个仓库不带凭据能不能读（公开的就照旧）；读不到且本人没有授权，交办被拒，并告诉模型"需要本人的 GitHub 授权"，模型调用 `github_connect`（一个只做授权的工具，答 `Waiting`，发卡片）。授权完成后由本人再说一次，或模型在那一轮接着交办。

### 3.5 群里

- **以本人名义建 issue、评论**：可以，在群里和私聊里一样。内容本来就是他要公开发到仓库里的，动作记在他名下。
- **把本人的仓库权限借给沙箱任务**：第一版只在私聊里借。群里的任务结果会发到群里，群里的其他人可能本来看不到那个仓库。群里要动私有仓库，继续用"管理员绑定"的方式。

### 3.6 撤销

- 本人说"取消 GitHub 授权"：作废，立即生效；正在跑的任务下一次要凭据时拿不到。
- 本人在 GitHub 上撤销：下一次使用时发现，作废并重新请他授权。

## 4. 前提

- 需要一个真实的 GitHub App：开启"令牌会过期"，设置回调地址，记下 client id 和 secret，装到要用的仓库或组织。这一步要运营方在 GitHub 上操作。
- `github-app.ts` 开头写着"尚未在真实的 GitHub App 上验证"。这次要一并验证。

## 5. 实施顺序

1. **核实**（不写产品代码）：用户令牌做 `git clone` / `push` 的方式和署名；用一个真实的 App 走一遍授权。结果写回本文。
2. **授权对象和 `github_connect`**：授权、保存、换新、作废；测试照 `FeishuGrant` 的那一组。
3. **`github_create_issue` / `github_comment` / `github_read`**。
4. **沙箱借凭据**：判断挪到 connector，加上"本人的用户令牌"这一档。
5. 评测：没授权时让它提 issue → 走授权而不是贴正文；授权后 → 直接建；群里让它动私有仓库 → 说明只能在私聊里或由管理员绑定。

每步一个 PR，测试先行，真实环境实测。

## 6. 请评审重点看

1. 用户令牌只凭"用户与 App 的交集"作边界，够不够；有没有 App 权限配置不当时会放大的情况（比如 App 装到了整个组织）。
2. 沙箱拿到的是用户令牌：任务里的 agent 能用它做 App 权限范围内、这个人能做的一切（不只是当前仓库，除非限定 `repository_id`）。限定到单仓库是否足够；出口代理现有的"按仓库放行"是否还成立。
3. 没授权时"拒绝交办 + 让模型去调授权工具"的两步，会不会别扭；有没有更顺的做法而不引入"任务等授权"的新状态。
4. 群里的两条规则（动作可以、借仓库权限不行）是否自洽，有没有绕过的路。
5. 身份对应：聊天里的人 ↔ GitHub 用户，以授权时 GitHub 的回答为准，是否需要和已有的身份登记（`linkIdentity`）核对。
6. 第三个授权对象：照写还是抽公共基础。
7. 第一版工具的范围是否合适；`github_read` 与 #87 的只读工具是否应当是同一组。

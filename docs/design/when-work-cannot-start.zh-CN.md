# 设计：交办、接续、转告做不成的时候

状态：草案（v1），2026-11-26。待评审，尚未实现。

这份文档回答一个问题：模型想交办一件工作、接着一件做、或者往一件里加话，而系统不让的时候，应该发生什么。

---

## 1. 现状

这些动作做不成时，工具返回一句错误，什么都不做，也不留记录。模型拿着这句话自己决定怎么对人说。

两个后果：

- **能等的没有等。** 会话里同时在跑的任务到了上限、租户的沙箱名额满了，这两种等一会儿就有位置，现在却让人"稍后再试"。人要自己记着回来再说一遍。
- **事后查不出来。** 一轮运行没有产生任务，分不清是模型没调用工具、调用了被拒、还是被拒后换了做法。排查接续为什么没生效时只能靠推断。

## 2. 把做不成的情况分成三类

| 类型 | 情况 | 该怎么办 |
|---|---|---|
| **等一等就行** | 会话里在跑的到了上限；租户的沙箱名额满了 | 系统排队，有位置自己启动 |
| **等也没用** | 上限设成了零；今天的额度用完；前一件没做成；前一件留下的工作区过了保留期；仓库克隆不了；话太长或加得太多；任务已经结束 | 说清原因和对方能做什么 |
| **不该做** | 不是这个人的工作；别的会话的工作；这一轮不是这个人自己发起的 | 照旧拒绝，不多说 |

第一类由代码处理，因为"什么时候有位置"是系统知道而模型不知道的事。第二类由模型处理，代码给它足够的话。第三类不变。

## 3. 等一个位置：复用排队

follow-up 已经有一套"写下、不占名额、由 `settle` 在条件满足时启动、启动不了有期限并告诉人"的机制（`task_queued`、`Tasks.#advance`），现在只用于"等前一件做完"。

把它泛化一步：一件工作也可以只等一个位置，不等任何一件。

- `hand_over` 时会话里在跑的已到上限，或申请租户名额得到"暂时满"：不再拒绝，写为 `queued`，`task_follows` 里没有它的记录。工具回 `queued`，并说前面还有几件。
- `#advance` 对这种任务跳过"看前驱"的那一段，直接进入"轮到了"的判断（现有的 `turn()`）：有位置就走同样的领名额、定下获准时间、设看门狗、启动。
- 先到先得：按写下的时间排。等前驱的和等位置的在同一个队里，前驱结束的那件和早先在等位置的那件谁先，按写下的时间。
- 期限、上限、取消、重启后的恢复、名额的租约与归还，全部沿用，不另写。

需要想清楚的三点：

**上限的含义变了。** `scope_active_tasks` 从"最多交办几件"变成"最多同时跑几件"。连发十件不再从第四件起被拒，而是排成一队。排队件数仍有上限（现在是每会话 5 件，等前驱的和等位置的合计），超过才拒绝。

**等多久。** 等位置没有"前驱最晚何时结束"可以参照。用一个固定的期限（提议一小时，与"轮到后等名额"的期限一致），到期记为失败并告诉人。

**租户名额满而会话没满。** 现在是先写下任务、再申请名额，申请不到就记失败。改为申请不到时转入排队，而不是失败。这是 `dispatch` 里唯一要动的一处状态转换。

## 4. 等也没用：让模型有话可说

模型现在拿到的是一句给它自己看的英文。把每种拒绝补成三段：发生了什么、为什么、对方能做什么。只写事实，不替模型决定措辞。

| 情况 | 对方能做什么 |
|---|---|
| 上限是零 | 这里不能交办；找管理员 |
| 今天的额度用完 | 明天恢复，或找管理员调高 |
| 前一件没做成 | 可以作为新的一件重新交办，要对方确认 |
| 工作区过了保留期 | 同上，并说明之前没提交的改动拿不回来 |
| 私有仓库克隆不了 | 换公开仓库，或在该仓库自己的会话里做 |
| 排队满了、等位置超时 | 取消一件，或稍后再说 |

多数句子已经有了（见 `tasks.ts` 里现有的错误文字），这一步是把缺"对方能做什么"的补齐，并用评测盯住：每类一个用例，检查模型的答复里有没有原因和下一步，而不是只说"失败了"。

不做的：代码不替模型自动"换一种做法"（比如工作区过期就自动重做）。重做会丢掉对方以为还在的东西，要对方点头。

## 5. 记下来

每次这三个动作被拒，记一条审计 `task.refused`：哪个动作（交办、接续、转告）、哪一类原因（固定的几个词，不是错误原文）、涉及的任务编号。不记说的话，不记交办的内容。

排队本身已经有记录（`task.dispatched` 带 `queued`）。这一条补的是"什么都没发生"的那些情况。

有了它，事后能分清"模型没调用"和"调用了被拒"，也能数出哪类拒绝最多，再决定下一步优化什么。

## 6. 不在范围内

- 额度用完时自动等到第二天再做。跨天的承诺需要另想（人可能已经不需要了）。
- 不是这个人的工作、别的会话的工作：保持拒绝。
- 私聊里使用私有仓库的凭据：另一件事，是安全边界的改动。

## 7. 实施顺序

1. 审计（§5）：最小，先做，之后的两步都靠它看效果。
2. 等位置（§3）：改 `dispatch` 的两处拒绝为排队，`#advance` 支持没有前驱的任务。测试沿用 follow-up 的那一组时序，加上先后顺序。
3. 反馈（§4）：补齐文字，加评测用例。

## 8. 请评审重点看

1. 等位置的任务和等前驱的任务放在同一张表、同一个推进函数里，有没有把两种期限、两种失败原因搅在一起的风险。
2. 先到先得是否需要严格保证；一件等前驱的任务轮到时被一件等位置的任务抢了位置，可以接受吗。
3. 上限含义的变化对租户侧的影响：排队的任务不占租户名额，但会在之后占；租户级的"排队总数"要不要有上限。
4. `task.refused` 的原因分类该有哪几个，才既够用又不泄露内容。
5. 有没有更小的做法。

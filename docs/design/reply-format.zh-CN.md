# 回复的格式：提及人、Markdown 渲染、告诉模型这里能写什么

状态：v3（用户定了范围，见 §7、§8）。对应 RFC #96。

## 1. 现象和现状

在飞书里看到的两种不好看的回复（#96）：

1. 让 agent "结束以后 @ 我一下"，发出来的是一串字面的 `@ou_…`，没有真正提及，对方收不到提醒。
2. `**适用场景：**让现有脚本…` 原样显示成星号。

对着代码看，现在是这样：

- 模型只有一个出口 `send_message(text)`。飞书连接器把它作为富文本（`post`）里的一个 `md` 节点发出，超过 30 KB 时退回纯文本（`feishu.ts` 的 `deliverFeishu`）。
- 提及被一刀切禁掉：模型写的所有 `<at …>` 都被改成不生效的写法（`quiet()`）。这是有意的，防止模型凭一段文字去通知任何人，甚至全体。代价是它完全不能提及人，而它手里只有对方的 id，就把 id 写了出来。
- 提示词里没有任何一句告诉模型"这个地方能渲染什么、怎么提及人"。
- 连接器的契约里没有"把模型写的话变成当地格式"这一层的说法，每个连接器在自己的 `deliver` 里各做各的。

加粗不渲染的原因不在飞书，在 Markdown 的规则本身：CommonMark 规定，结束的 `**` 前面是标点、后面紧跟文字时，不算结束标记。中文里 `**小标题：**正文` 正好是这种情况（全角冒号是标点）。这是规范里一个至今没解决的问题（commonmark-spec#650）；飞书文档对此只有一句"若加粗效果未显示，请确保加粗语法前后保留一个空格"。

## 2. 业界怎么做

（2026-11 查的公开文档；由一个子任务阅读原文后汇总，引用处给了出处，措辞未必逐字。）

| | 中性形式 | 提及 | 告诉模型 |
|---|---|---|---|
| Vercel Chat SDK | 标准 Markdown，解析成 mdast 树，各适配器从树渲染；Slack 直接走原生的 `markdown_text` | 不在消息模型里；开发者自己拼平台的写法 | 文档里没有提示词一侧的指导 |
| Slack | 新增 `markdown` 块和 `markdown_text`，专为 LLM 输出，直接收标准 Markdown | `<@U…>` 按 id；没有放行名单，靠转义 | 未见 |
| Teams | `textFormat: extendedmarkdown`，说明是为了更好地支持 LLM 输出 | **必须声明两次**：正文里的 `<at>` 加上 `entities` 里对应的一条，否则不算提及 | 未见 |
| Discord | Markdown | **`allowed_mentions`**：发送方声明这条消息里哪些提及可以真的通知到人，由服务端执行；`parse: []` 全部不通知 | 未见 |
| Telegram | 纯文本加 `entities` 列表，或带转义规则的 MarkdownV2 | `entities` | 未见 |
| Hermes Agent | 适配器里有格式化一步 | 有人报告过它的转义漏掉了全体提及（未经官方确认） | 按平台往系统提示里加一句（"你在 Slack 上，回答紧凑，避免宽表格"），可按平台覆盖 |
| OpenClaw | Markdown 解析成中间表示，分块，再按渠道渲染；表格有按渠道的降级方式 | | 只见渲染一侧 |

反复出现的做法：

- **中性形式就是标准 Markdown**，由连接器渲染成当地的样子。平台自己也在往"直接收标准 Markdown"靠（Slack、Teams、飞书的 `md` 节点）。
- **提及是结构化的数据，不是正文里的字**：Teams 的 entities、Discord 的 `allowed_mentions`、Telegram 的 entities。名字从不靠从正文里猜，发送方给 id。
- **提及安全在发送这一层执行**（放行名单、转义、平台权限），不靠模型自觉。有记录的事故：有人花几小时诱导一个 AI 机器人去 @everyone。
- **渲染是必做的，提示是可选的第二层**，而且提示说的是风格（长短、别用宽表格），不是让模型去写平台的语法。
- 长消息按渲染后的大小在段落处拆开，不拆开代码块和表格。

没能核实的：飞书里提及一个不在群里的人会怎样；卡片消息能不能被引用回复。

## 3. 提议

三样东西，都放在已有的结构里，不新起一层。

### 3.1 提及：模型说要提醒谁，能不能提醒由代码判

用户定的（2026-11-27）：可以提醒提出这件事的人，也可以提醒别人。

- `send_message(text, notify)`：`notify` 是可选的一组"要提醒的人"。每一项是下面两种写法之一，都是模型在对话记录里原样看得到的：
  - 一个人的 id（记录里写着"message from … (person, id ou_…)"）；
  - 一个提及的名字，照提出人消息里出现的样子写（`@张三`）。
- **能不能提醒由 Brain 判，不由模型判。** 一项只有落在下面三类人里才生效：
  1. **提出这件事的人**。这一轮是他的消息起的；或者是他交办的任务结束了；或者是他设的定时器到点了（定时器要加上"谁设的"）。
  2. **提出人在这次请求里用平台的提及点了名的人**（"做完提醒一下 @张三"）。是谁，取自平台随消息给的名单（连接器在消息到达时记下名字和 id），不从正文里的字猜。同一个名字对上两个人的，不算。
  3. **在这个会话里对 agent 说过话的人**。Brain 自己的收件记录里有。
- 三类之外的（没说过话也没被点名的群成员、别的群的人、应用、全体）没有任何写法能提醒到。
- **私聊里不提及**：只有一个人。`notify` 被忽略。
- 生效的人随消息记进发件记录，连接器发送时写成当地真正的提及，放在正文开头。飞书是 `<at user_id="ou_…"></at>`。
- 模型写在**正文里**的提及标记照旧一律失效（`quiet()` 不动）。
- 工具的回答只说生效了几个、没生效几个，不逐个说明谁在不在、为什么。

第 3 类是 Codex 不赞成的：在一个地方说过话，不等于同意以后被任何人借 agent 反复提醒。用户知道这一点后仍然要它。不靠收窄范围还能做的约束，这次一并做：

- **一个事件对一个人只提醒一次**（见下）。同一个结果里模型再怎么调，也不会对同一个人提醒第二次。
- **一件事最多提醒有限的几个人**（定为 5 个），不管分成几条消息发；多出来的不生效。按"一条消息"算的话，被诱导着连发几条就能把说过话的人轮番提醒一遍。
- 周期性的定时器每次触发是一个事件，频率是设它的人定的（"提醒过一次就停"的见 §3.1a 第 6 条）；被提醒的若是别人，这就是"一个人定时提醒另一个人"。这次不加退出的办法，如实写在这里；被提醒的人可以让设定时器的人或管理员停掉它。

**在哪一步核对什么**（Codex 复核 v2 时要求落实的两处）：

- **提醒的人和发到哪，在写进发件记录时对一遍。** 一个会话的投递目标会被后来的消息更新，所以不能假定"这条消息要去的地方"就是"提出这件事的地方"。任务和定时器建立时记下：谁提出的、他点了名的人、在哪个群和话题（`session_key`）、通过哪个账号。写发件记录时，等最终的投递目标定下来，和这几样对照：同一个账号、同一个群和话题，才带提及。目标变成了私聊、别的群，或者提出的人确定不了，正文照发，不带提及。不比对每条消息都不同的回复消息编号。
- **一个事件对一个人只提醒一次，按事件算，不按调用算。** 模型为同一个结果调两次 `send_message`，是两个调用编号。所以提醒按（起因的事件，被提醒的人）占位：任务按任务编号和它的完成事件，定时器按定时器编号和原定的触发时刻，本人的消息按那条消息。写发件记录时原子地占下；同一个事件里第二条想提醒同一个人的消息照发，但不再提及他。

**周期性的定时器**：每次触发是一个事件，可以各提醒一次，那是设它的人自己定的频率。"每十分钟检查一次，通过了再提醒我"和"每十分钟提醒我一次"是两种要求：前一种模型只在通过的那一次带 `notify`，后一种每次都带。两种都不会超过每次触发一次。

这是 Discord `allowed_mentions` 的思路走到头：能不能通知到人，完全由不受模型控制的一层决定，模型只表达"要不要"。

### 3.1a 实现约定（Codex 复核 v3 时要求写明的）

1. **"谁点了谁"绑在那一条原始消息上。** 连接器只从经平台验证的、本人发的那条消息里取平台原生的提及，记下文本里的名字和稳定的身份（`data.mentioned`）。平台说明是人的才记；说不清是不是人的（机器人、应用）跳过。同一个名字落到两个身份上的，这个名字无效；同一个人被点两次算一个。已有的 `data.handles` 是从文字里取的，不作这个用途。引用、转发、任务说明、模型的参数都不能补这个名单。
2. **"说过话"只认直接对 agent 说的普通消息的作者**：同一个账号、同一个群、同一个话题里，连接器确认是本人直接发给 agent 的。按钮、别人代转的、引用里的作者不算。收件记录过期后来源数据会被清掉；没有来源数据的旧记录不能只凭还留着的发送人编号放行。
3. **任务和定时器建立时由 Brain 记下**：谁提出的、他点了名的人、起因的事件、在哪个会话。之后恢复、重放都用记下的，不从"最近的消息"里补人。一轮里合并了同一个人的几条消息时，点名的名单只取这一轮自己的这几条，不往前找。
4. **话题怎么比**：不用给投递地址另加话题键。话题在会话键里（群里的话题是 `thread:<话题编号>`，主会话是 `chat`），一条消息是在它所属的会话里入队的，这个会话的投递目标只会被同一会话里后来的消息更新。所以比的是：起因事件的会话键，和这条消息入队时所在会话的会话键。两个话题在同一个群里也是两个会话键。
5. **在哪一步定名单**：消息最终可以投递的那一步，等它要去的地方定下来之后。按 `notify` 里的顺序解析成合格且不重复的人，去掉这个事件里已经提醒过的，取到这个事件的总数满 5 个为止；名单、（事件，人）的占位、发件记录三样在同一个事务里写。普通发送在入队时做；接续请求的答复是草稿，可能被改写或丢掉，在最后一版草稿转成待发时做，没发出去的旧草稿不占名额，草稿被系统的通知替换时名单一并清掉。重试用原名单。
5a. **等过的请求，它的答复是另一件事。** 请求提出时说的那句（"需要你先授权"）和它最后的答复，各算各的：前者按那条消息算，后者按这个请求算。否则提出时提醒过一次，结果出来时就提醒不到了。
3a. **一件事分几步做，每一步都带着同一份记录。** 定时器触发、任务结束起的那一轮里没有人的消息；它再建的定时器和任务，沿用起因那个定时器或任务上记着的提出人、点名名单和位置。否则"数到 10，完了提醒我"这种要十个定时器接力的请求，从第二环起就不知道是谁的了。已取消的定时器、"提醒一次就停"且已经提醒过的定时器、没有记录的旧定时器和任务、任务的进度事件，不往下传。任务"算在谁名下"（审批、接着做的权限）是另一回事：没有人说话的一轮里交出去的任务仍然不算在任何人名下。

   已知的两点，不为此另做处理：其一，任务的结果里可能有读来的不可信内容，被它诱导着设下去的定时器也会带着这份记录，一次提醒可能被拉成几轮；能提醒到的仍只有提出人和他点名的人，每一轮仍过全部检查，定时器有总数上限、在群里看得见也能取消。以后要收紧，可以给这份记录加一个传递的步数上限。其二，"提醒一次就停"的定时器在同一轮里先建了下一步、后发提醒的，下一步仍会带着记录。

5b. **任务的结束、定时器的触发，凡是记着谁提出的，各自单独成一轮。** 否则两个任务同时结束、或者任务的进度和结果挨着到，会被并进同一轮，说不清这一轮是哪一件事，谁也提醒不了。
6. **"每隔一阵检查，第一次通过了提醒我"**：每次到点是一个新的事件，连着两次都通过的话，只按事件去重会提醒两次。所以设定时器时可以说明"提醒过一次就停"（`set_timer` 的一个选项）。带这个选项的定时器，第一条真的带了提醒的消息入队时，在同一个事务里把定时器标成结束。没带这个选项的周期定时器，每次到点各算各的。

### 3.2 渲染：只修确定没有形成强调的写法

模型继续写标准 Markdown，不学任何平台的语法。连接器在发送时修正，第一批只有一条，就是现象 2。

**只修按 CommonMark 的规则确定没有形成强调的情况**，别的一律原样：

- 结束的 `**` 前面是全角标点、后面紧跟的既不是空白也不是标点：`**小标题：**正文`。这时它按规则不算结束标记。改成 `**小标题**：正文`。
- 开始的 `**` 后面是全角标点、前面紧挨的既不是空白也不是标点：`正文**（注）**`。改成 `正文（**注**）`。
- **本来就有效的不动**：`**提示：** 下一步`（后面是空格，规则下已经是强调）保持原样，强调的范围不变。

不碰的地方：代码块、行内代码、反斜杠转义过的星号、链接的文字和地址、成对的引号或括号只有一半在强调里的、相邻或嵌套的强调。拿不准就不改。

第一版只处理两个星号的加粗（`**`）。单个星号的斜体和列表符号、乘号难以区分，留待以后。

代码块只认一种：围栏顶格开始的。它不在任何引用或列表里，结束位置是确定的。遇到别的样子的围栏（有缩进的、在引用或列表里的），或以 `<` 开头的行，从那里到文末全部不动——这类围栏在哪里结束取决于它所在的容器，不在这里推算。裸地址一直算到下一个空白，紧贴其后的文字不动。

按段落处理：一段里有闭合不了的行内代码、或有不是"文字加地址"这种完整写法的方括号（引用式链接、链接的定义、嵌套超过一层的），整段不动；缩进四格以上的行（在列表下可能是代码）不动。标记外侧的字符按完整的字符判断（表情这类占两个编码单位的符号算一个）。

已有的 `markdown.ts` 的 `prose()` 只把代码块分出去，行内代码仍然交给回调，而且会改写 `suggestion` 围栏的名字。这里不直接用它，另写一个只做这一件事的小函数，自己跳过行内代码。

验的时候直接比较渲染结果：原有加粗的范围、代码的字面内容、链接真正指向的地址。只比"去掉星号后的文字相同"会漏掉对代码和链接的破坏。另外验四样：改前改后去掉强调标记的可见文字完全相同；强调的范围只在标点那一个字符上有出入；链接的地址不变；再处理一遍不再变化。

不引入 mdast 这类语法树：业界用树是因为要把 Markdown 转成另一种语法。飞书的 `md` 节点和 GitHub 都直接收标准 Markdown，我们没有要转的目标。

### 3.3 告诉模型这里是什么地方：连接器给能力，宿主写句子

连接器不往提示词里写话。它只回答几个固定的问题（`channel.shows`）：这里显示 Markdown 吗；能提醒人吗。由 Brain 按答案生成固定的短句放进这一轮的提示词：

- 显示 Markdown："这里显示 Markdown。"否则："这里只显示纯文字，不要用 Markdown。"
- 能提醒人："正文里写 @ 或 id 只是文字，不会提醒任何人；要提醒谁，把他放进 `notify`。"否则只说"`notify` 这个参数在这里不起作用"——不说"这里提醒不了任何人"，因为有的地方（GitHub 的普通评论）正文里的 @ 仍会通知到人。

问的是这条消息实际要去的地址，和发件队列选地址的顺序一致：接续请求的答复问原请求的地址，普通回复问会话的地址；落到 scope 的兜底地址时一律按不能提醒算。

会话的标题、外面读来的内容、平台返回的值，都不进这句话。没有 `shows` 的连接器什么都不加。

更细的风格（"这个群里回答尽量短"）已经有地方放：每个 scope 自己的 `instructions`。

### 3.4 超长时怎么办，和重试

现在超过 30 KB 的回复退回纯文本发。带提醒的消息退回时，提及写成纯文本消息里的原生写法（飞书的纯文本同样认 `<at user_id="…"></at>`），所以提醒不因为退回而变成一串字。连接器做不到的，就明确只送正文，不把一串字当作提醒过了。

一条消息入队时定下要提醒的人，第一次发送时定下用哪种编码，都记在发件记录上；是否退回纯文本不另记，它由正文、要提醒的人和编码三样决定，每次算出来都一样。重试发的是同一份内容、同一个幂等键。被取消了的消息不再重发，也不换个格式另发一条。接续请求的答复草稿同样带着这三样。

## 4. 不做

- 卡片。agent 自己的话继续用富文本。卡片更好看，但能否被引用回复没核实，转发后提及不通知，表格只显示 5 行。需要按钮的场合（审批、授权）已经是卡片，不在此列。
- 长消息拆分。现在超过 30 KB 退回纯文本，丢格式但不丢字。业界的做法（按渲染后的大小在段落处拆，不拆代码块和表格）是对的，但它要改"一条消息对应一条发件记录"这个前提，另起一步。
- 正文中间的提及；@全体；富媒体。
- 连续回复同一条消息时的合并（RFC 里的第 5 点），是另一类问题。
- Markdown 语法树。

## 5. 和已有东西的关系

- **GitHub 一侧的提及**：评审意见（`send_review`）和以本人名义发布的 issue、评论过 `inert()`，其中以本人名义发布时"只有本人手打的 @ 才生效"，是同一个原则。agent 在 GitHub 上的普通回复（`send_message`）现在**不过** `inert()`，正文原样发出，里面的 `@login` 会通知到人。这次不动它，如实记在这里；`notify` 在 GitHub 上暂时没有作用（提醒只在聊天连接器上实现）。`channel.shows` 做出来后，GitHub 连接器按它的实际情况回答。
- **`quiet()`** 保留，作用不变：正文里的提及标记一律失效。
- **发件的编码版本**（`outbox.wire`）：提醒不需要新的编码——要提醒的人单独记在发件记录旁边，有就写、没有就不写，旧消息没有这条记录，发出去和以前一样。修标点（第二步）才改变正文怎么写出去，那一步把编码升到 2：已经开始发送的旧消息按它开始时的编码重发，每次重试发出去的是同一份。

## 6. 验收

1. 提醒：群里某人让 agent 做完后提醒他，飞书收到的消息以对他的提及开头；让它提醒他点了名的另一个人、或一个在这里说过话的人，同样生效；没说过话也没被点名的人的 id、别处的 id、应用、全体，都不生效；同名对上两个人的不生效；一件事提醒超过 5 个人的（不管分成几条消息发），多出的不生效；同一个结果调两次带 `notify` 的发送，只有一条带提及；投递目标在此期间被别的消息改到了另一个群或私聊，正文照发、不带提及；"每十分钟检查，通过后提醒我"在条件连着两次为真时也只提醒一次、之后定时器结束，"每十分钟提醒我"每次触发提醒一次；同一个群的两个话题里，起因在一个话题、消息却在另一个话题入队的，只发正文；以**收件人真的收到一次平台的通知**为准，出站的内容和接口返回成功只是中间证据。任务结果起的那一轮提醒交办的人；定时器起的那一轮提醒设它的人；几个人的消息合在一轮、或取不出人时不提醒、正文照发；私聊里不带提及；模型在正文里写的提及标记仍然失效；没有任何输入能让它提及全体。
2. 一条消息重试时发出的内容逐字相同（含提及）；超长退回纯文本时提及仍是原生的；被取消的不重发。
3. 标点：`**小标题：**正文`、`正文**（注）**` 被修正（只修两个星号的加粗，斜体不修）；`**提示：** 下一步`、代码块、行内代码、转义、链接、英文标点、嵌套和相邻的强调不被改动；有闭合不了的行内代码或边界不明的链接的段落整段不动；验法见 §3.2。
4. 提示词：能显示 Markdown、能提醒人的会话里各有那一句；不能的没有；句子里没有任何来自会话或外部的文字。
5. 旧编码的消息（部署时在途的）照原样发。

## 7. 用户定的（2026-11-27）

1. **能提醒谁**：可以提醒其他人。落成 §3.1 的三类：提出人、提出人点了名的人、在这个会话里说过话的人。
2. **长消息拆分**：这次不做。超长时按 §3.4 退回纯文本并保留提醒。
3. 提及放在消息开头。

## 8. v1 之后改了什么（Codex 的评审）

- 提及从"说过话的人都可以、模型给 id"收到"只有提出这件事的人、模型只给真假值"。定时器要记下是谁设的。第三个人的提及和重复催办不做。
- 工具的回答不逐人说明谁没提醒到。验收以收件人真的收到通知为准。
- 标点的修正只针对确定没形成强调的写法，有效的保持原样；不用 `prose()`。
- 连接器只给能力值，句子由宿主写。
- 新增 §3.4：超长退回时提醒不丢；要提醒的人和编码选择记在发件记录上，重试不变。

v3（用户定了"可以提醒其他人"之后）：§3.1 从"只有提出人、模型只给真假值"改成"三类人、模型给 id 或提出人写过的提及名字"；加了每条消息最多几个人、一个事件对一个人只提醒一次；连接器要在消息到达时记下提出人用平台提及点了名的人。Codex 不赞成的第 3 类保留，是用户的决定。

实现第一步（PR #107）时又定的，来自三轮评审：一件事（不是一条消息）最多提醒 5 人；等过的请求的答复单独算一件事；记着提出人的任务结束和定时器触发单独成轮；连接器把一条消息点到的人连名字全部记下，名字指不指向唯一的人由 Brain 在整个请求的名单上判断；只记和写消息的人同一组织的人，不记"全体"；提醒放在正文前，正文以标题、列表、引用、表格、代码块开头时另起一行；发送这一步再拦一次（只在群里、给所有人看的消息、是人的编号、不是全体）。

一个已知的前提：连接器只记同一组织的人，不记别的组织的成员和应用。同一条消息里若同时点了一个本组织的人和一个与他同名的外部成员或应用，Brain 只看得到前者，这个名字会被当成只指他一人。提醒到的只可能是被记下的那个人，而他确实被点了名，所以不为此另做处理。

上线前要在真实的群里看的两件事：被提醒的人真的收到通知；提醒一个已经退群的人时，平台是拒收整条消息还是只是不通知（拒收的话这条消息就发不出去，要另外处理）。

# GitHub：沙箱里读，Brain 以本人名义评论，以及两者之间怎么接

状态：v1 草稿，待 Codex 评审、用户定夺。接在《以本人的名义用 GitHub》（`github-as-the-person.zh-CN.md`）第一步之后。

## 1. 起因

第一步上线后的第一次真实使用，用户在群里说的是：

> 帮我看看 <仓库链接> 有没有相关的 issue，如果没有就提一个，如果有可以追加你的评论

结果什么都没做成。查下来缺三样：

1. **读不了。** Brain 没有读 issue 的工具，于是派了沙箱任务去查；沙箱的出网只放行 `github.com` 上的 git 和模型接口，`api.github.com` 被拒（`outbound.ts`）。
2. **评论不了。** 第一步只做了建 issue，评论当时列为晚做。
3. **接不上。** 即使沙箱查到了，结果回到 Brain 时起的是一轮新的 run，它的起因是"任务结束"而不是某个人的消息。`actingOn` 要求起因全是本人的消息，否则这一轮不代表任何人，connector 的工具一个都没有。所以"查完接着以本人名义建或评论"这条路在结构上不通。

另外这次暴露出一件事：要发的正文是沙箱此前整理的草稿，不是用户的原话。真实用法里，正文本来就常常是 agent 的工作成果。第一步里"标题和正文只写本人说的话"这条要求挡不住也不该挡这种用法，要管的是别的东西（见 §5）。

## 2. 业界怎么做（2026-11 查的公开文档）

| | 沙箱里读 GitHub | 以谁的身份写 |
|---|---|---|
| GitHub Copilot 云端 agent | 内置 GitHub MCP server，专门限定的令牌，只读，只限当前仓库 | 自己的身份 |
| Cursor 云端 agent | 沙箱令牌带 issues 读；内置令牌不能建或改 issue | 触发的人自己的 OAuth 身份（论坛里员工的说法） |
| OpenAI Codex 云端（旧版设置页） | 默认断网；可开域名白名单加方法限制，受限档只放行 GET、HEAD、OPTIONS | 文档未讲清 |
| Claude Code 网页版 | 凭据不进沙箱，外面的代理核对操作内容后才换上真令牌（只讲了 git） | 未讲 |
| Devin | 组织级 App 的权限，不跟随发起人的个人权限 | 默认 App；可绑定个人账号 |

能抄的：只读按方法限制；范围限到当前仓库；真令牌留在代理里。没有现成答案的：读过外部内容之后再以本人名义发，中间怎么管。Codex 的文档点名的风险正是这个场景（读到被人动过手脚的 issue，然后把东西发出去）。

## 3. 读：沙箱可以对 `api.github.com` 发只读请求

改 `Outbound`，新增一条和 `#github` 并列的路：

- **方法**：只放行 `GET` 和 `HEAD`。于是 GraphQL（全是 POST）不可用，这是有意的。
- **路径**：`/repos/{owner}/{repo}` 及其下的一切，和 `/search/issues`。别的不放行。
- **凭据**：和 git 同一条规则，不新增。请求的是任务所在的仓库、并且这个任务本来就借得到令牌（仓库自己的会话，或运营者把群绑定给了这个仓库）时，带上那个只发给这个仓库的安装令牌；其余一律匿名，所以读不到没交给它的私有内容。`/search/issues` 只在借得到令牌时带令牌，令牌本身只看得见那一个仓库。
- **令牌不进沙箱**：和现在一样，由代理换上；沙箱自己带来的 `authorization` 头一律丢掉。
- **重定向**：`redirect: "manual"`，凭据不跟着跳到别的主机。
- **任务结束后**：和现在一样，什么都不放行。

匿名请求和别的部署共用出口地址，GitHub 对匿名的限额很低，读公开的别人家仓库时可能被限流。这次不处理，返回什么就是什么。

Worker 怎么知道能读：交办时给它的固定说明里加一句（可用 `curl` 只读访问本仓库的 GitHub REST 接口，不能写，GraphQL 不可用）。不装 `gh`。

读回来的内容是外部内容。任务结果回到 Brain 时，记为"读过外部内容"（见 §5）。

## 4. 写：`github_comment`

和 `github_create_issue` 同一套东西，不另起：同一个 `GithubGrant`、同一张授权卡片、同一个确认页、同样的群内规则、同样的"仓库必须由本人说全"。

- 参数：`repo`、`number`、`body`。issue 和 PR 的会话评论是同一个接口（`POST /repos/{repo}/issues/{number}/comments`），所以也能评论 PR；逐行的评审意见不在范围内。
- 防重复：和建 issue 一样，正文末尾带本次调用的标记；`Op` 多一个 `kind`（issue | comment）和 `number`；结果不明时按标记在这条 issue 的评论里找（按本人账号、时间），找到算已发，找不到如实说不确定，不重发。
- `number` 必须是本人说过的，或者是为这次请求做的任务查出来的（见 §5 的确认）。

## 5. 接：任务的结果回来，还算在为那个人办事

### 5.1 让那一轮代表发起人

规则：**一个任务是在代表某人的一轮里交办的，那么这个任务结束所起的一轮，仍然代表这个人，依据仍是他当初那几条消息。** 条件和现在的 `own` 检查一致，重新核对一遍：同一个会话、同一个人、同一个来源、消息还在。任务记录里记下交办时的那几条消息的编号（和"等着被接续的请求"记 `recent` 是同一个做法）。

不满足（任务不是由某个人的消息交办的，例如定时触发的）：和现在一样，不代表任何人，没有 connector 的工具。

这不是为 GitHub 做的：任何 connector 的工具，在"先让 Worker 干活，再替本人做一件事"的场合都靠它。

### 5.2 读过外部内容之后，怎么还能以本人名义写

现有规则：一轮里通过工具读过外部内容，此后只能回复和再读，别的工具都不能用。任务的结果算外部内容（Worker 读了 issue、读了代码、读了网页），所以按现有规则，§5.1 的那一轮一开始就不能写，等于白接。

可选的做法：

- **甲：发之前给本人看原文，本人点了才发。** 这一轮可以调 `github_create_issue` / `github_comment`，但工具不直接发，而是给本人一张卡片：仓库、（issue 编号）、标题、正文原文，两个按钮。点"发布"才发，发的就是卡片上那份，一个字不改。群里这张卡片只有本人能点；涉及没绑定给这个群的私有仓库时私发。
- **乙：不确认，直接发。** 和第一步里用户对"正文来自本人原话"的决定保持一致。代价：公开仓库里任何人都能写 issue，其中一条写着"把某某内容贴到新 issue 里"之类的话，被 Worker 读到并带回来，就可能以本人名义发出去。
- **丙：不许写，只把草稿回给本人。** 本人再说一句"发吧"，那是一条新消息、新的一轮，但那一轮的上下文里同样有这份草稿，问题原样回来，只是多了一步。

建议甲。理由：这正是"不可信内容、能对外发、以本人名义"三样凑齐的场合；确认的不是"要不要建 issue"（用户已经定了不用问），而是"这份读过外部内容之后写出来的东西是不是你要发的"。本人原话直接建 issue 的那条路不变，仍然不确认。

这条规则写成通用的：**读过外部内容的一轮，`effect: "act"` 的工具只有声明了"可以先给本人看"的才能用，而且一定先给看。** 工具给出要展示的内容，Brain 负责出卡片、等按钮、把同一份参数交回工具执行。等按钮用的是现成的"等着被接续的请求"（`Waiting`），不新造状态。没声明的工具照旧不能用。

### 5.3 第一步里那句要求怎么改

`github_create_issue` 的说明里"标题和正文只写本人说的话，不写读来的东西"改成两种情况：

- 本人直接说了内容：照他说的写，不确认（不变）。
- 内容来自为这次请求做的工作：可以用，但会先给本人看（§5.2 甲）。

别人在同一个群里说过的话仍然不该写进去；这一条现在还是靠说明约束，根治在 RFC #100。

## 6. 提及

以本人名义发的正文里出现 `@某人`，GitHub 会真的通知那个人。规则：正文里的 `@名字`，只有本人自己的消息里原样出现过的才保留，其余改成不生效的写法（包进反引号）。在工具里做，建 issue 和评论共用。等 RFC #96 的 `render` 做出来，挪到那里。

## 7. 不做

- Brain 自己的读工具（搜 issue、读 PR）。读交给 Worker。
- GraphQL、`gh`。
- 关闭、改标题、打标签、逐行评审。
- 第二步（沙箱里用本人的凭据操作私有仓库）。
- 格式按目的地定制（#96）、历史按需读（#100）。

## 8. 验收

1. 沙箱：对本仓库 `GET /repos/…/issues` 带令牌成功；`POST` 被拒；别的主机、别的路径被拒；别家私有仓库匿名读不到；任务结束后被拒；沙箱自带的 `authorization` 不被转发。
2. 评论：授权、防重复、结果不明、撤销、群里的规则，和建 issue 的那组测试对应。
3. 端到端，用的就是那句话："看看有没有相关 issue，没有就提一个，有就追加评论"。两种结局各一条：查到了 → 本人看到评论的原文 → 点发布 → 评论以本人名义出现；没查到 → 本人看到 issue 的原文 → 点发布 → issue 出现。不点、点"不发"、换个人点：什么都不发。
4. 注入：任务结果里带着"把这段话发出去"的文字，本人看到的卡片就是将要发的全文；不点就什么都没发生。
5. 不是由人的消息交办的任务，结束后那一轮没有 connector 的工具（不变）。
6. 提及：读来的 `@名字` 不生效；本人自己写的生效。

## 9. 要定的

1. §5.2 选甲、乙还是丙（用户）。
2. §5.1：任务结束后隔多久仍算"为那个人办事"。建议不另设时限，沿用任务本身的时限；本人在此期间取消授权、退群等，由工具自己的现场检查挡住。
3. `/search/issues` 是否放行。不放行的话 Worker 只能翻列表，仓库 issue 多时又慢又贵。
4. 匿名读别家公开仓库的 API 是否放行。git 现在是放行的；API 同理的话，被限流时体验差；不放行则"看看某某项目有没有这个 issue"在没绑定的仓库上做不了。
5. §6 的提及规则是现在做，还是等 #96。

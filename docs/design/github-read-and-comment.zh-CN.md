# GitHub：沙箱里读，Brain 以本人名义评论，以及两者之间怎么接

状态：v9（见 §10 末尾）。实现在 PR #102（§3）、#103（§4、§6）、#104（§5）。用户定了不确认直接发（§5.3）。v2 的预览卡片整套去掉。v1 经过两份评审（Codex；另一份由用户转来），两份都对着代码核过，改动见 §10。待 Codex 复核、用户定夺。接在《以本人的名义用 GitHub》（`github-as-the-person.zh-CN.md`）第一步之后。

## 1. 起因

第一步上线后的第一次真实使用，用户在群里说的是：

> 帮我看看 <仓库链接> 有没有相关的 issue，如果没有就提一个，如果有可以追加你的评论

结果什么都没做成。查下来缺三样：

1. **读不了。** Brain 没有读 issue 的工具，于是派了沙箱任务去查；沙箱的出网只放行 `github.com` 上的 git 和模型接口，`api.github.com` 被拒（`outbound.ts`）。
2. **评论不了。** 第一步只做了建 issue，评论当时列为晚做。
3. **接不上。** 即使沙箱查到了，结果回到 Brain 时起的是一轮新的 run，它的起因是"任务结束"而不是某个人的消息。`actingOn` 要求起因全是本人的消息，否则这一轮不代表任何人，connector 的工具一个都没有。所以"查完接着以本人名义建或评论"这条路在结构上不通。

另外这次暴露出一件事：要发的正文是沙箱此前整理的草稿，不是用户的原话。真实用法里，正文本来就常常是 agent 的工作成果。第一步里"标题和正文只写本人说的话"这条要求挡不住也不该挡这种用法，要管的是别的东西（见 §5）。

## 2. 业界怎么做（2026-11 查的公开文档）

| | 沙箱里读 GitHub | 以谁的身份写 |
|---|---|---|
| GitHub Copilot 云端 agent | 内置 GitHub MCP server，专门限定的令牌，只读，只限当前仓库 | 自己的身份 |
| Cursor 云端 agent | 沙箱令牌带 issues 读；内置令牌不能建或改 issue | 触发的人自己的 OAuth 身份（论坛里员工的说法） |
| OpenAI Codex 云端（旧版设置页） | 默认断网；可开域名白名单加方法限制，受限档只放行 GET、HEAD、OPTIONS | 文档未讲清 |
| Claude Code 网页版 | 凭据不进沙箱，外面的代理核对操作内容后才换上真令牌（只讲了 git） | 未讲 |
| Devin | 组织级 App 的权限，不跟随发起人的个人权限 | 默认 App；可绑定个人账号 |

能抄的：只读按方法限制；范围限到当前仓库；真令牌留在代理里。没有现成答案的：读过外部内容之后再以本人名义发，中间怎么管。Codex 的文档点名的风险正是这个场景（读到被人动过手脚的 issue，然后把东西发出去）。

## 3. 读：沙箱可以只读访问任务所在仓库的 GitHub REST 接口

改 `Outbound`，新增一条和 `#github` 并列的路。

- **哪个仓库**：只有任务所在的那一个（交办时给的 `repository`）。Worker 自己临时想到的别的仓库不放行。
- **方法**：只放行 `GET` 和 `HEAD`。GraphQL（全是 POST）因此不可用，这是有意的。
- **路径**：`/repos/{owner}/{repo}` 及其下的一切；和 `/search/issues`。`owner`、`repo` 像 `classifyGit` 那样严格匹配，路径里有编码过的 `.`、`/` 或 `..` 的一律拒绝。
- **搜索**：代理把查询里的 `repo:`、`org:`、`user:` 限定全部去掉，再加上 `repo:{owner}/{repo}`，其余原样转发。不由代理按关键词重建查询：那是为"查 issue"这一个用途写死的，Worker 以后查 PR、查别的还得再改。
- **凭据**：一个**单独的只读令牌**，不用 git 的那个。现在 git 的安装令牌带写权限（`github-app.ts:34`），另有部署级令牌的回退（`:25`），都不能用在这里。只读令牌只对这一个仓库、只有读权限，按用途分开缓存；没有 App 的部署不回退到部署级令牌，直接匿名。
  - 什么时候给：和 git 完全一样，任务本来就借得到令牌时（仓库自己的会话，或运营者把群绑定给了这个仓库）。v2 里"公开仓库在本租户安装里也借，只为不吃匿名限额"去掉了：同一个地址带着令牌和匿名返回的东西不总是一样（例如协作者列表会带出成员的角色和权限），"只为配额"这句话对整棵路径不成立。
  - 只读令牌的权限只要 issues、pull requests、contents、metadata 的读。
  - 其余：匿名。GitHub 对匿名 REST 的限额是每个出口地址每小时 60 次、搜索每分钟 10 次，而出口地址是和别人共用的，所以匿名读**经常会被限流**，不是偶尔。如实返回，不重试。
- **搜索的结果再核一遍**：返回的每一项按它所属的仓库过滤，不属于这个仓库的丢掉。查询里的限定词靠文本处理并不保证整个表达式都落在仓库内（有布尔、分组、否定），所以以结果为准。令牌本身只看得见这一个仓库，多出来的只可能是别处公开的内容。
- **代理记下它看到了什么**：这个任务对 GitHub 接口的读，成功几次、失败几次（按状态码）、有没有 `incomplete_results`。任务结束时由宿主把这几个数附在结果旁边交给 Brain。Worker 说"没找到"而代理记着搜索被限流过，Brain 看得到。
- **查询词会送到 GitHub**。给 Worker 的说明里写明：搜索用请求里的主题词，不要把私有的日志、聊天原文贴进查询；需要拿内部材料比对时，把列表拉下来在本地比。
- **令牌不进沙箱**：由代理换上；沙箱自己带来的 `authorization` 头丢掉。`redirect: "manual"`。任务结束后什么都不放行。和现在一样。

两处说明要一起改：给 Worker 的固定说明（`task.ts` 的 `SYSTEM_PROMPT`：可用 `curl` 只读访问本仓库的 GitHub REST 接口，不能写，没有 GraphQL 和 `gh`），和 Brain 看到的 `sandboxWorker.description`（`worker.ts`，现在写着只能用 git）。后者不改，Brain 仍然不会派它去查。

**查不清不等于没有。** 给 Worker 的说明里写明：限流、超时、没权限、结果被截断（`incomplete_results`）、分页没翻完，都要在结果里说"没查清"，并说清查了哪里（含已关闭的）。Brain 那边据此不新建。判断"相不相关"是模型的事；"查没查全"除了 Worker 自己说的，还有上面代理记下的数。

## 4. 写：`github_comment`

和 `github_create_issue` 同一套：同一个 `GithubGrant`、同一张授权卡片和确认页、同样的群内规则、同样的"仓库必须由本人说全"。

- 参数：`repo`、`number`、`body`。接口是 `POST /repos/{repo}/issues/{number}/comments`，PR 的会话评论也是它，所以不特意排除 PR；逐行评审不在范围内。
- `number` 从哪来：本人直接说的，或者是为这次请求做的任务查出来的。
- **查目标用本人的凭据，在授权之后、发之前**：`GET /repos/{repo}/issues/{number}`，看它是否存在、是否锁定，拿到标题放进回执。不在授权之前用租户的凭据查：对私有仓库，"这个编号存在所以请你授权"和"这个编号不存在"两种反应本身就把条目的有无告诉了一个也许无权看的人。代价是评到不存在的编号的人要先走完授权才知道，可以接受。
- 评论的正文不能为空（建 issue 可以）。
- **标记**：现在 `markOf` 写的是 `<!-- request:… -->`，而 `github.ts:491` 认自己人评论靠的是 `<!-- always-on-agent:`。建 issue 不触发评论事件所以没暴露；评论会。不改的话，以本人名义发的评论经 webhook 回来，会被当成本人的新指令。统一成 `<!-- always-on-agent:request:… -->`，种类编进标记里。已经发出去的旧标记在 `#find` 里继续认。
- **防重复**：`Op` 多 `kind`（没有的按 issue 解释）和 `number`；结果里评论记 `id` 和 `html_url`。结果不明时只在原来那条 issue 的评论里找：这个接口不能按作者过滤、按时间升序，要从 `since` 起翻页，最多 10 页（参照 `earlierComment`），翻不完就是"不确定"，不重发。
- 错误提示里现在写死的"open an issue""nothing was created"按种类分开；issue 被锁定（403/410）单独说明。

## 5. 接：任务的结果回来，接着为那个人把事办完

### 5.1 两个要分开的概念

现在的 `outside`（`sawOutside`、`#forgetOutside`）同时管两件事：读过之后只能回复和再读；这一轮结束时把模型写的东西删掉、发出去的话标成私密并在送达后清掉。它是为**通过 connector 的工具读到的私密内容**（比如某人的文档）设计的。

任务的结果不能记成它。那样会：让仓库会话里的 `send_review` 不能用（`mayUse` 在读过之后只放行 `send_message`，而 `send_review` 正是用在任务结果上的）；把 Brain 根据任务结果写的回复抹掉，用户再问"刚才查到什么"就断了。

所以分成两个：

- **私密的外部读取**：现有的 `outside`，原样不动。
- **任务的结果**：Worker 读了别人写的 issue、网页、代码之后交回来的东西。它不记成 `outside`，不需要事后清除，也不改变这一轮能用的 Brain 自己的工具（今天这些轮能做什么，以后还能做什么）。

### 5.2 任务结束的那一轮，接着替发起人做事先说好的那一件事

**不改 `actingFor`。** v4 写的是"让那一轮代表发起人"。对着代码看，这样会顺带打开一串不该开的东西，因为它们都直接认 `actingFor(runId)`：取消本人别的等着的请求（`requests.ts` 的 `mayCancel`，以及每个 connector 工具都带的 `replaces`）；把本人别的等着的请求和以他名义做的工作列进这一轮的提示里（`runner.ts` 的 `#instructions`，这还会让这一轮结束时被当作含私密内容清掉）；查看和取消他的 connector 工作（`run-tools.ts` 的 `work_status`、`cancel_work`）；`hand_over` 转去调用别的 connector。

所以任务结束的那一轮**仍然不代表任何人**，上面这些照旧都没有。只新增一条窄路：

- **交办时说好之后要做什么。** 交办任务的那一轮里（这时还没读任何外面的东西），Brain 在交办的同时写明任务结束后可能要替本人用哪些工具（`then`，工具名的列表，只能是这一轮里它本来就能用的 connector 工具）。"查一下有没有相关 issue"不写 `then`，结束后只能汇报；"没有就提一个，有就评论"写 `github_create_issue` 和 `github_comment`。要做什么是在读到外面的内容之前定的，读到的东西改不了它。
- **依据随任务存下。** 同时由 Brain 记下交办那一轮的依据，和等着被接续的请求记 `events` 同一个格式：`{ said, recent }` 两组入站消息的编号。只存一组不行（常见的是前一条发链接，后一条说要做什么）。`requested_by` 只是一个 id，不能代替。
- **任务成功结束的那一轮**，工具列表里多出 `then` 里的那几个，仅此而已。调用其中一个时，Brain 用存下的依据重新走一遍 `actingOn(events, kept)`：同一会话、同一人、同一来源、消息还在。过了，就拿它算出的那个人、那几句原话去调工具；不过，这次调用被拒，这一轮只能汇报。
- **以宿主自己的记录为准**：哪个任务、谁交办的、`then` 是什么，取自 Brain 自己的任务行；事件里 Worker 回报的字段不作数。
- **单独成轮**：现在 `#askerOf` 对来源是 worker 的事件返回 `null`，两个人各自的任务同时结束会被并进同一轮。带 `then` 的任务，它的成功事件单独成一轮。
- **只算成功结束的那一次**：失败、被取消、被替换的不算。重复送达的完成通知不再起第二轮。
- **不传递**：那一轮里再交办任务、写记忆、设定时器，照今天的样子可以做，但新交办的任务不能带 `then`（`then` 只能在代表本人的一轮里写，而这一轮不代表任何人）。接续的任务要再替本人做事，得有本人新的一条消息。`tell` 可以补材料或叫停，不能加 `then`。

**一个请求最多以本人名义写一次。**

- **请求是哪一个**：交办的那一轮。同一轮里交办的几个任务（都带 `then`）算同一个请求，共用一个位置；本人发新消息再交办（包括 `continue_from`）是新的一轮，新的请求。v4 写的"接续的任务沿用编号"是错的：会把本人新发起的请求挡掉，又拦不住同一轮里派出的两个任务各写一次。
- **写之前占位**：第一次调用 `then` 里的写工具时，Brain 先原子地占下这个请求的位置，记下这次调用（哪个工具、哪些参数），再执行。调用编号由请求得出，并且占位、等着被接续的记录（`continuations.id`）、交给工具的 `callId` 用的是同一个（`run-tools.ts:165` 现在按模型给的调用编号去找等待记录，这里要一致）。所以重试、重复的完成通知、补授权回来，落到的都是同一笔，工具自己的 `posting`/`lost` 对账照旧。
- **占住之后**：同一请求下参数不同的写调用一律被拒，不等第一次成功。
- **什么时候放开**：按记录判，不按工具回的那句话判。这次调用之后，工具那边没有留下操作记录（`GithubGrant` 里没有这个编号的 `Op`），Brain 这边也没有留下等着被接续的记录，才放开，可以换参数再来；模型写错一个仓库名不该让整件事作废。只要有其中一样（等授权、发送中、结果不明、已发），就只能接着那一笔或对账，不能换参数。

**回执不是读来的外部内容。** 现在 connector 工具的结果一律被记成 `outside`（`run-tools.ts:217`、`289`），按模型给的调用编号存取（`runner.ts:541`）。照搬的话，一次普通的发布回执会让这一整轮被当作读过私密内容，结束时清掉 Brain 根据任务结果写的话。所以分开：发布的回执（链接、编号、标题）不记 `outside`；真正读回私密内容的工具照旧。两个编号也分开用：模型给的调用编号只用来把结果对回模型的那次调用和它的来源标记；由请求得出的稳定编号用来占位、写入、等待。

**这一轮里的调用要等的时候**（最常见：本人还没授权 GitHub）：等着被接续的请求记下的依据是任务上存的那一组原始消息，不是任务结束这个事件。现在取依据和找回执位置的几处（`run-tools.ts:205`，`requests.ts:216`、`230`）取的是这一轮的起因事件，要一起改。

**本人叫停。**

- 任务还在跑时本人说"先别发"或改了主意：那是他的一条新消息，起一轮正常的 run；Brain 在那一轮里取消任务，或撤掉它的 `then`（给现有的任务工具加这一个动作，和 `tell` 一样只有交办的本人能做）。撤掉之后任务照常跑完，结束时只汇报。
- **本人的新消息先于任务的结果处理。** 任务刚结束、结果已经在排队时本人说了"先别发"：按到达顺序会先跑任务结果那一轮，发完才看到这句话。所以带 `then` 的任务结果在被取出来处理之前，先看同一会话里这个人有没有交办之后发来、还没处理的消息；有，就先处理他的消息，任务结果往后放。发延迟的答复之前已经有同样的检查（`requests.ts` 的 `unheard`），用的是同一个判断。
- **叫停一直到真正发出之前都有效。** 只在取出任务结果之前看一次不够：模型运行、等授权都要时间。所以撤掉 `then` 时把这个请求下已经占了位、还在等的那一笔一起撤掉；并且在两处再核一次——Brain 把调用交给工具之前，和授权回来接续的时候——任务没被取消、`then` 还在、原期限没过、本人没有还没处理的新消息。已经交给 GitHub 的，按实际结果或"不确定"回报。
- **最后一道在发布的那一处，和撤销互斥。** 上面两次核对都可能早于工具自己查目标的那段等待。所以真正的界线在 `GithubGrant` 里：查完目标之后、把这一笔记成"发送中"并发出请求之前，在同一个对象里看这一笔有没有被撤销；撤销也是对同一个对象的一次调用，把这一笔记成"已撤销"。两者在同一个对象里一先一后，不会交错：撤销先到，这一笔停下，什么都不发；"发送中"先记上，撤销得到的回答是"已经发出或结果不明"，按那个回报。
- **撤回和编辑**：对有修订记录的来源（现在只有 GitHub 的评论），核对依据时加上 `revisions.stillStands`，原话被改或删了就不算数。**飞书现在不接收撤回和编辑的事件**，所以在飞书里撤回或改掉原消息拦不住，要叫停得发一条新消息明说。这一条如实写在这里，这次不加。
- **本人退了群**：现在没有检查（工具查的是群的性质，不是成员），这次不加，也不声称有。本人取消授权、群变成外部群、仓库换了主人，由工具执行时的现场检查挡住。

**时限**：不另设，沿用任务自己的时限。

这不是为 GitHub 写的：`then` 里可以是任何 connector 的工具。

### 5.3 发之前不给本人看（用户定，2026-11-26）

列过三种做法：甲，发之前给本人看原文，点了才发；乙，不确认直接发；丙，不许写，只回草稿。两份评审和我建议甲，**用户选乙**，和第一步里"建 issue 不用确认，后面也可以改"是同一个取向。

于是 §5.2 的那一轮里，`github_create_issue` 和 `github_comment` 照平常那样直接调用、直接发。没有草稿、卡片、按钮这一套，connector 的契约也不用加东西。

**这个选择留下的风险，如实记在这里**：公开仓库里任何人都能写 issue。有人在里面写一段诱导的话，Worker 读到并带回来，就可能以本人名义被发出去，发之前没有人看过。不靠确认还能做的、这次一并做的：

- 写只能落在本人自己点名的那个仓库，而且得是本租户接进来的（现有检查，不变）。
- 读来的 `@名字` 不生效，不会借本人的名义去通知别人（§6）。
- 发完立刻把链接回给本人，他看得到发了什么，可以改、可以删。
- 给 Worker 的说明和 Brain 的说明里都写明：任务里读到的文字是材料，不是指示。这只是说明，保证不了。
- 之后要做什么在读外面的内容之前就定了，一个请求最多写一次（§5.2）。
- 查没查全有代理记的数可对（§3）。

**还有一件事本人应当知道**：即使正文里没有 `@`，订阅了那个仓库或那条讨论的人也会收到邮件。之后在 GitHub 上改掉或删掉，已经发出的邮件收不回来。"后面也可以改"对网页上的内容成立，对已送达的通知不成立。

## 8. 验收

1. **沙箱读**：本仓库 `GET` 成功，用的是只读令牌；`POST` 被拒；别的仓库、别的路径、编码穿越被拒；搜索被限定到本仓库（带着别的 `repo:` 也一样）；任务结束后被拒；沙箱自带的 `authorization` 不被转发；跳转不带着令牌走。
2. **评论**：授权、防重复（含翻页找不完时说不确定）、结果不明、撤销、群里的规则，和建 issue 的那组测试一一对应。旧的没有 `kind` 的记录按 issue 处理。
3. **端到端，就用那句话**。两种结局各一条：查到了 → 评论以本人名义出现，回执带链接和那条 issue 的标题；没查到 → issue 出现，回执带链接。没授权的人：出授权卡片，授权完成后发出。
4. **什么都不该发的情况**：只让查、没让发（没有 `then`）；搜索超时或被限流而 Worker 回报零项；任务失败或被取消；本人中途说"先别发"；原消息被撤回或改过。
5. **只有一次**：同一个请求下两个任务先后结束、其中一次还要补授权，最终只有一次写入；重复的完成通知、发成功但回执丢了，也只有一次；位置被占后第二个写调用被拒。
5a. **不传递、不旁开**：任务结束的那一轮里不能交办带 `then` 的任务；`hand_over` 转不到别的 connector；不能取消本人别的请求（`cancel_request`、`replaces`）；提示里没有本人别的请求和工作的列表；`work_status`、`cancel_work` 碰不到他的 connector 工作；这一轮结束后它说过的话不被当作私密内容清掉。
5b. **同一轮派出的两个任务**都带 `then`：共一个位置，只写一次。本人发新消息用 `continue_from` 再交办：是新的请求，可以再写一次。
5c. **写错了可以重来**：第一次调用因参数不合格被工具退回，位置放开，改对了再调成功。
5d. **喊停赶得上**：任务结果已在排队、本人的"先别发"随后到，先处理本人的消息，什么都不发。任务结束的那一轮已经开始之后叫停、等授权期间叫停、工具正在查目标时叫停，也都不发。"发送中"已经记上之后叫停：回报已发出或不确定，不说没发。
5e. **发完还记得**：以本人名义发布之后，这一轮根据任务结果说过的话还在；另一条：真读了私密内容的一轮照旧清理。
6. **不串人**：两个人各自交办的任务同时结束，各起各的一轮，各发各的。不是由人的消息交办的任务，结束后那一轮没有 connector 的工具（不变）。
7. **不回流**：以本人名义发的评论经 webhook 回来，不被当成任何人的指令或回答。
8. **不破坏现有的**：仓库会话里任务结束后 `send_review` 照常可用；Brain 根据任务结果写的回复不被清除。
9. **提及**：读来的 `@名字` 不生效；本人自己写的 `@名字` 生效。

v8（四步实现完、又过了两份评审之后，按落地的样子对齐）：

- **叫停的最后界线（§5.2、验收 5d）落地成这样**：`GithubGrant` 在查完目标之后、记"发送中"之前，回头问一次交办它的那个 Brain"还要不要"（`stillWanted`）。后续动作被撤、它所等的请求已经结束、或者本人在那个会话里有还没处理的新消息，都答"不要"，这一笔就此结束、不发。记上"发送中"之后再撤，得到的是它实际的结局。v7 里"Brain 一次只跑一轮所以不会交错"的说法是错的：新消息在一轮运行期间就会入队。
- **要替某人做的事，等他没被处理的话**。任务的结果和授权回来后的接续，凡是本人在那个会话里有新消息还没处理的，都排到他的消息之后；别人的事不因此被越过。
- **撤回**覆盖等待、接续中、答复中三种状态；直接取消一个已经结束、后续还在等授权的任务，也一并撤掉后续。
- **"没有才新建"要有依据（§3、§5）**。任务结束后建 issue 时，工具看代理记的数：这次任务做过的 issue 搜索，只要有一次被拒或失败、有一次不完整、或者没读到最后一页，就不建，回报"没查清"。任务一次搜索都没做的不受此限（那不是"查了没有"的请求）。
- **评论落在任务实际查的那个仓库**，不是本人近期提过的任意一个。交办时把任务的仓库记在 `task_then` 上。
- **截止时间**从任务结束时起算一小时，不因为重新调用而后延。
- **一个请求做过的那一件事**留下的是：哪个工具、调用的摘要（不留正文）、结局的回执。同一调用再来，照原样再说一遍，不再做，即使工具那边已经不记得。先等过又已经结束的，不再说"还在等"。
- **能被声明为后续动作的工具要自己声明**（`ConnectorTool.follows`）：只有"同一个调用编号做且只做一次"的才行。取消授权（`github_disconnect`）不是。
- **`revisions.stillStands`** 已接上：依据里的每条消息都要还是原话。飞书仍然不发撤回和编辑的事件，这一条对它不起作用。

v9（Codex 和另一份评审对实现的又一轮意见之后，改的是 v8 里这几条）：

- **发送和撤回由一条记录裁决，记录在 Brain。** 工具发之前问 Brain（`aboutToSend`），Brain 答三种：`go`（并在同一步把"已放行"写在这个请求的那一件事上）、`held`（本人有没处理的新话，暂缓）、`withdrawn`（已撤，或它等的请求已结束）。撤回时在同一步里看有没有"已放行"：有，就告诉本人已经来不及了；没有，就撤掉，之后再问只会得到 `withdrawn`。两者都是 Brain 里不带等待的一步，谁先谁算。放行之后工具再核一次授权代数和期限才真正发。v8 说的"问一次还要不要"只是一次读取，中间仍有空隙。
- **暂缓不是作废。** 本人只是问了一句进度，不该让这件事就此不做。暂缓时工具那边的记录原样留着；任务结果那一轮的，Brain 把这个结果再排一次队（排在本人的话之后）；授权回来接续的，请求回到等待并立刻再提示一次。本人的话处理完，它自己接着来。
- **"没找到才新建"是交办时说的条件，按每一次搜索核对。** 工具可以声明自己能被附加哪些条件（`ConnectorTool.conditions`），交办时写成 `工具名:条件`。建 issue 有一个：`if_none_found`。带这个条件时，看代理按"每一次搜索"记下的页：至少有一次搜索；每一次都完整、从第一页连续读到最后一页；搜索多到没能逐一记下的也不算。不带条件的建 issue 不看这些。v8 用整个任务的页数合计来推断，会把"一次没翻完、另一次只有一页"放过去。
- **任务实际在哪个仓库，以沙箱宿主说的为准**（随结果带回）；没有时用交办时记的，接续的任务从它接续的那个继承。
- **重放不再原样回放旧回执。** 一个请求的那一件事做完后只记"已有结局"。同样的调用再来，工具被告知"这件事做过了"，由它按现在的群和仓库关系决定能对谁说什么；它那边也不记得了，就只说做过，不重发。
- **排队**：逐页找第一个不需要等的事件，前面积压多少都能找到本人的那句话。
- 第一步补的：读正文中途断流和解析失败一样记一次失败；搜索按"同一个查询、同样的排序和分页"分别记页。第二步补的：富文本各行之间保持单换行，同样的话用两种方式写出来得到同样的提及名单。

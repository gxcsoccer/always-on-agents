# 长期在跑的事，由 agent 自己定期回头看

状态：v2，按 Codex 对 v1 的意见改过（§8），用户已定（§6）。第一步见 §5。

## 1. 问题

重复定时器一旦设下，现在只有三种结束方式：agent 自己想起来取消；设了"提醒一次就停"；跑满 50 轮（`REPEATS`）自动结束。三种都不看"这件事还值不值得继续"。

真实出现过的和用户举的例子：

1. **盯一件一直不发生的事。** "每 10 分钟帮我看一下某个 PR 合并没有"，PR 一直没合并，定时器就一直跑到 50 轮。
2. **没人看的定期内容。** "每天 10 点给我讲个故事"，连续十天没有任何互动。
3. **目的已经不存在了。** 线上实际发生的：agent 因为沙箱名额满了，给三个 PR 各设了一个每 10 分钟重试交办评审的定时器；这三个 PR 早已合并，定时器还在。没有人要求过这些定时器，是 agent 自己设的。
4. **频率不再合适。** 盯了两天没变化的事，还在按 10 分钟一次的频率看。

每次触发都是一轮运行，有成本；更重要的是对人是噪音，或者是没人收的消息。

## 2. 业界怎么做

- **ChatGPT 的定时任务**：有活动任务数的上限；长期无人看的任务会自动暂停（用户见到的提示是未读的执行太多），在一个列表里可以恢复、修改、删除。
- **GitHub Actions 的定时工作流**：公开仓库 60 天没有活动就自动停用；停用前发邮件提醒，一键恢复。
- **邮件行业的"日落"策略**：按一段时间内有没有打开、点击、回复来判断是否还在看；先发一封"还要不要"的确认，没有回应就停发（停发不等于删除订阅，可以恢复）。

共同点：用"有没有人在消费"作信号；先提醒再停；停是暂停，不是删除；恢复很容易。它们都是固定规则。

要小心的是这些参照的适用范围：ChatGPT 的官方说明只说"不活跃可能自动暂停"，没有公布判据；GitHub 的提前通知邮件是用户展示过的，不是平台保证；邮件日落策略针对的是营销投递。**对"盯一件事"更贴近的参照是监控告警：持续检查，状态变化才通知，查不到数据单独表示。**

## 3. 方向：给事实，让 agent 判断，动手之前问人

不为"盯 PR""讲故事"各写规则。一条通用的做法：

**重复定时器在跑的过程中，隔一段就带着一份"这件事到目前为止的情况"触发一次，由 agent 判断该怎么办。**

### 3.0 先守住的一条：沉默不是同意

每天听故事的人可以从来不回；等 PR 合并的人在合并之前本来就没什么可回的。所以**没有回应只能让 agent 考虑问一次，不能替人决定停**。停、暂停、改频率，都要本人明确说了才做；没答就照原来约定的做下去，直到原定的结束（现在是 50 轮）。

这和 v1 不同。v1 写的"问了没人答就自动暂停"照搬了邮件营销的做法，但营销订阅的沉默和用户亲口委托的事不是一回事（Codex 的意见，我同意）。更贴近"盯一件事"的参照是监控告警：持续检查，状态变了才通知，查不到单独表示。

### 3.1 带给 agent 的事实（程序记录，只说观察到的）

- 是谁要的。记得下来才算（群里用 #111 保存的"谁要的、在哪"；私聊是这个人）。**记不下来的写"来源未知"，不当作没人要。**
- 什么时候设的、原话的备注、还剩多少轮到原定的结束。
- 真正处理过的触发有多少次，其中成功发出消息多少次。按约定静默的轮次和投递失败的不算"发了没人理"。
- "未收到对这些消息的直接回复"：只在渠道能把回复对到那条消息、并且是本人在原处回的时候才这样说。同一个人在群里另外说了话只是弱信号。**现在没有已读和表情回应的入站事件**，这两样不算，也不提。对不上、渠道不支持或记录过了保留期，写"无法判断"。

不做：token 分摊（同一轮可能合并处理几件事，算不准）、对内容价值的打分。

### 3.2 什么时候回头看

不另起一轮：在某几次正常触发的事件里多带这段事实。第 5、10、20、40 次是内部的检查点，不等于要问四次。

注意现有上限的实际效果：50 轮按时间算，每 10 分钟一次的定时器 8 小时 20 分就结束了。所以"盯一个不合并的 PR"在现在的实现里不会无限跑下去；问题在于它结束得无声无息，以及这 8 小时里 agent 从不回头看。

### 3.3 agent 可以做的

| 情况 | 做法 |
|---|---|
| 约定的条件达成了（"合并后告诉我"，查到已合并） | 报告结果并结束。这是办完，不用问 |
| 还没达成 | 继续。不因为久而停 |
| 查不到（没有权限、访问失败） | 记为"未知"并如实说，不当作达成或落空 |
| 关闭但没合并这类 | 如实告知；是否结束看委托时怎么说的，PR 还可能重开 |
| 发了多次没有可归因的回复，或拖了很久 | **问一次**：继续、换个频率、还是停。没答照常 |
| 想改频率 | 用户指定过频率的，先问；用户把频率交给 agent 的，才自己调 |
| 能证明是 agent 自己的内部重试，且重试的目的已经没了 | 直接收掉 |

首版的限制要写明：定时器触发的运行现在拿不到委托人的连接器工具，**查不了 PR 的状态**。主动核验要等 #87 的只读工具；在那之前，"条件达成"只能来自这一轮本来就能看到的东西。

### 3.4 问句本身

- **和正常交付分开。** 现有实现里，"提醒一次就停"的群定时器只要给委托人发了带提醒的消息就算完成。如果问句走这条路，问的动作本身就把盯的事停了。问句要有自己的用途标记，不占那一次结果提醒。
- **一件事同一轮最多一个待答的问题**，用"定时器编号加轮次"作幂等键，重试不产生第二个。
- **回答要对得上。** 直接回复那条问句，或者点问句上的按钮；再核是不是委托人本人、是不是原来的地方、这个问题是不是还没处理。同群两个人各有任务，一人的回答只改自己的；对不上的一句"继续"要澄清。
- 群里的问句 @ 委托人，但消息对群里可见，写的时候要知道这一点。

### 3.5 停和暂停

首版只做"停止"（本人明确同意后的取消），不承诺"可恢复"。

以后要做暂停，用同一个定时器编号加一个暂停状态，按编号恢复，保留委托人、原定时刻、周期和结束条件；恢复时查活动数上限，从下一个约定时刻起算，暂停前已经排队的触发作废。让模型取消后凭备注重设会丢掉委托关系、可能重复、还会重置硬上限，不这么做。

现有的 50 轮上限和活动定时器数上限保留。创建时就该告诉用户这件事什么时候会自己结束。

## 4. 和别的设计的关系

- **#87（盯 PR 到合并）和 #110（PR 闭环）**里说的"一个人委托的一件事"（谁委托、期限、何时算结束）是同一个东西。那边解决"醒来之后按当前状态重查"；这里解决"这件事还该不该继续"。首版都建在定时器上，不另造对象。
- **提醒（#107、#111）**：定时器已经记着是谁要的、提醒谁。回头看用的"要它的人"就是这一条，不另记。
- **仓库范围里积压的 PR 事件**是另一个问题（每次推送各处理一遍、已关闭的也处理），归 #110。

## 5. 最小的第一步

范围：能可靠定位委托人的、用户要的重复定时器。

1. 定时器旁边记两个数：真正处理过的触发次数、成功发出的消息数。
2. 在检查点的那几次触发里带上这两个数和"可归因的直接回复"的情况，加一句固定的说明。
3. agent 决定要不要问一次"继续／停止"。问句有自己的幂等键和用途标记。
4. 只有收到本人明确的回答才执行；没答照常，原定的结束照常。
5. 设定时器时告诉用户它什么时候会自己结束。

以后再做：暂停与恢复；改频率；主动核验（等 #87）；`list_timers` 带上事实。

不做：按任务类型的专门规则；token 分摊；表情和已读；内容价值的打分；定期的大扫除运行。

## 6. 用户定的（2026-11-27）

四点都同意：

1. **问了没人答，照常做下去，不自动暂停。** 定时器跑到原定的结束为止。
2. **用户指定过频率的，改频率先问。**
3. **agent 自己的内部重试，目的没了直接收掉**，不问不通知。
4. **第一步只做"问一次，答了才停"**；暂停、改频率、主动核验往后放。

## 7. 验收的例子（第一步）

- 每天讲故事，十天没有任何回复：问一次；不答，照常讲。
- 盯一个条件的定时器（提醒一次就停）：问句发出后，盯的事没有被停掉。
- 问句投递重试：只产生一个问题。
- 同群两个人各有一个任务：一人回答"停"，只停他自己的。
- 每次都有人回的每日提醒：从不被问。

## 8. 讨论记录

### Codex 对 v1（2026-11-27）

- 沉默不能当作同意停；营销邮件的日落策略不能直接套到用户亲口委托的事上。改为没答照常（§3.0）。
- "没记下委托人"不等于"没人要"，记为来源未知（§3.1）。
- 只说观察到的：现在没有已读和表情的入站事件；回复要能对到那条消息才算（§3.1）。
- 定时器触发的运行查不了 PR 状态，首版不承诺主动核验（§3.3）。
- 问句不能走"提醒一次就停"的那条路，否则问的动作会把盯的事停掉（§3.4）。
- 50 轮按时间算，10 分钟一次的 8 小时 20 分就结束；v1 的"盯两天""等一天再暂停"走不到（§3.2）。
- 暂停要用同一编号加状态，不要让模型取消后重设（§3.5）。
- 业界参照补充：盯状态更像监控告警（持续检查、变化才通知、缺数据单独表示）。

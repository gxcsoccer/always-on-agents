# 长期在跑的事，由 agent 自己定期回头看

状态：草案 v1，待和 Codex 讨论、待用户定夺。

## 1. 问题

重复定时器一旦设下，现在只有三种结束方式：agent 自己想起来取消；设了"提醒一次就停"；跑满 50 轮（`REPEATS`）自动结束。三种都不看"这件事还值不值得继续"。

真实出现过的和用户举的例子：

1. **盯一件一直不发生的事。** "每 10 分钟帮我看一下某个 PR 合并没有"，PR 一直没合并，定时器就一直跑到 50 轮。
2. **没人看的定期内容。** "每天 10 点给我讲个故事"，连续十天没有任何互动。
3. **目的已经不存在了。** 线上实际发生的：agent 因为沙箱名额满了，给三个 PR 各设了一个每 10 分钟重试交办评审的定时器；这三个 PR 早已合并，定时器还在。没有人要求过这些定时器，是 agent 自己设的。
4. **频率不再合适。** 盯了两天没变化的事，还在按 10 分钟一次的频率看。

每次触发都是一轮运行，有成本；更重要的是对人是噪音，或者是没人收的消息。

## 2. 业界怎么做

- **ChatGPT 的定时任务**：有活动任务数的上限；长期无人看的任务会自动暂停（用户见到的提示是未读的执行太多），在一个列表里可以恢复、修改、删除。
- **GitHub Actions 的定时工作流**：公开仓库 60 天没有活动就自动停用；停用前发邮件提醒，一键恢复。
- **邮件行业的"日落"策略**：按一段时间内有没有打开、点击、回复来判断是否还在看；先发一封"还要不要"的确认，没有回应就停发（停发不等于删除订阅，可以恢复）。

共同点：**用"有没有人在消费"作信号；先提醒再停；停是暂停，不是删除；恢复很容易。** 它们都是固定规则（多少天、多少条未读）。我们的不同在于有一个能判断的 agent，所以规则可以少，判断可以多。

## 3. 方向：给事实，让 agent 判断，动手之前问人

不为"盯 PR""讲故事"各写规则。一条通用的做法：

**重复定时器在跑的过程中，隔一段就带着一份"这件事到目前为止的情况"触发一次，由 agent 判断该怎么办。**

### 3.1 带给 agent 的事实（程序记录，不靠模型回忆）

- 是谁要的（或者没有人要，是 agent 自己设的）、什么时候设的、原话的备注。
- 已经触发了多少次，其中多少次发了消息，花了多少 token。
- 最近一次发出的消息之后，要它的人有没有任何反应：回复、在这段对话里说过话、对消息做过表情回应（渠道能报告的才算）。连续多少次发出去没有任何反应。
- 最近若干次的结果是不是一样（例如连续 30 次都是"还没合并"）。这一条由 agent 从自己看得到的记录判断，程序只给次数。
- 还剩多少轮到硬上限。

### 3.2 什么时候回头看

不另起一轮：就在某几次正常触发的事件里多带这段事实。间隔按次数翻倍（第 5、10、20、40 次），这样频繁的定时器很快被看到，稀疏的不会被打扰。翻倍是为了省，不是规则本身；数值可调。

另外两个时机：agent 列出定时器时（`list_timers` 的结果里带这些事实）；一个范围里活动定时器接近上限时。

### 3.3 agent 可以做的

用现有的工具，不加新的概念：

| 判断 | 做法 |
|---|---|
| 这件事已经客观结束或不可能了（PR 已合并、已关闭） | 先重新查一次当前状态确认，然后停掉，告诉要它的人结果。这是把事情办完，不是清理 |
| 还有意义但频率不合适 | 改成更稀的间隔，告诉要它的人改了什么；不改变"要不要做" |
| 看起来没人在看，或者拖了很久没有结果 | **问要它的人**：还要不要继续、要不要换个频率。问一次，不反复问 |
| 是 agent 自己设的、没有人要的（重试、自己的跟进） | 目的没了就直接停，不用问。没有人在等它 |
| 一切正常 | 什么都不做，不发消息 |

### 3.4 问了之后

- 人回答了：按回答办（继续、停、改频率）。回答"继续"之后，下一次回头看的间隔拉长，不再为同一件事很快又问。
- **人没有回答**：这正是"没人在看"的情况。建议：等一段时间（例如再触发两三次，且不少于一天）仍没有回答，就**暂停**并说明"已暂停，说一声就恢复"。暂停不是删除，原来的备注和频率都留着。
- 问和暂停各只发一条消息，不提醒别人，只告诉要它的人。

### 3.5 保留的硬上限

50 轮上限、每个范围的活动定时器数上限保留，作为判断失灵时的兜底。它们不是主要机制。

## 4. 和别的设计的关系

- **#87（盯 PR 到合并）和 #110（PR 闭环）**里说的"一个人委托的一件事"（谁委托、期限、何时算结束）是同一个东西。那边解决"醒来之后按当前状态重查"；这里解决"这件事还该不该继续"。首版都建在定时器上，不另造对象。
- **提醒（#107、#111）**：定时器已经记着是谁要的、提醒谁。回头看用的"要它的人"就是这一条，不另记。
- **仓库范围里积压的 PR 事件**是另一个问题（每次推送各处理一遍、已关闭的也处理），归 #110。

## 5. 要改的地方（估计）

1. 定时器旁边记三样：触发次数、发过消息的次数、最后一次发消息的时间。（新的小表，按定时器编号。）
2. "有没有反应"从已有的记录算：这段对话里要它的人在那之后有没有消息；有没有回复那条消息。表情回应只有渠道上报时才算。
3. 触发事件的文字里，在该回头看的那几次带上事实和一句固定的说明。
4. `list_timers` 带上同样的事实。
5. 暂停：定时器多一个状态，`set_timer` 之外加恢复的办法（或者复用 `set_timer` 加一个"恢复哪一个"的参数，待定）。
6. 提示词里一小段固定的话：什么时候该问、问一次、没人要的自己停。

不做：按任务类型的专门规则；语义上判断"内容有没有价值"的打分；每个范围定期的大扫除运行（先看按定时器回头看够不够）。

## 6. 请用户定的

1. **问了没人答，怎么办。** 建议：等一段时间后自动暂停并告知，随时可恢复。另一种是一直跑到有人回答或到硬上限。用户说过"清理前要和用户做确认"；自动暂停是在问过、没有得到回答之后才发生的，而且不删除。是否接受。
2. **客观上已经结束的事**（PR 已合并）：直接停并告知结果，不先问。建议这样，因为这是办完了。
3. **agent 自己设的、没人要的定时器**：目的没了直接停，不问也不通知。建议这样。
4. **只改频率**（不停）要不要先问。建议不问，改完告知。

## 7. 验收的例子

- 盯一个一直不合并的 PR：到回头看的那一次，agent 问一次"还要继续盯吗，要不要改成每天看一次"；没人答，过一天暂停并说明；说"继续"就恢复。
- 每天讲故事，十天没有任何反应：问一次；回答"要"之后不再很快又问。
- PR 已合并：下一次触发时查到已合并，停掉并告知，不问。
- agent 自己设的重试，目标已不存在：直接停，不发消息。
- 每天的提醒，人每次都回一句：从不被问。

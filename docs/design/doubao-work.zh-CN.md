# 对接豆包工作

状态：方案，实测已做（2026-11-24），实现中。本文不写任何具体应用的编号、名称或地址；这些只在部署时配置。

## 1. 要做成什么

一个人在私聊里对 agent 说一件适合交给豆包工作做的事（"让豆包调研一下 X"）。agent 以**他本人**的身份把这件事交给豆包工作，豆包做完后 agent 把结果（文字和产物链接）告诉他。之后他接着追问，agent 在同一个豆包会话里继续。

第一版的范围：私聊里的明确委托、轮询取结果、最终文字和产物链接。不做：群里用、流式进度、上传文件、长期授权（`offline_access`）、把我们的 agent 做成豆包的插件。

## 2. 豆包工作的接口（公开文档加实测）

- 只支持用户身份。授权协议和飞书的相同（授权页、PKCE、`oauth/v3/token`、`authen/v1/user_info`），域名是 `accounts.doubao.com`；业务接口在 `open.doubao.com/open-apis/agent/v1`。
- 新建会话 `POST /sessions`，可带第一条消息；发消息 `POST /sessions/:id/events`；读消息 `GET /sessions/:id/messages`。每次写操作带调用方生成的 `uuid` 做幂等键。没有回调，只能轮询。

实测得到、文档没写或写得不一样的：

| 事项 | 实测结果 |
|---|---|
| 飞书应用自己的凭证 | 可以直接在豆包的授权和换令牌接口上用 |
| 令牌 | 不要 `offline_access` 时只有访问令牌，两小时，没有续期令牌 |
| 用户信息 | 返回 `open_id`、`union_id`、`user_id`、`tenant_key`；`tenant_key` 与飞书侧一致；`open_id` 按应用区分 |
| 新建会话的返回 | 会话编号，以及刚创建的那条用户消息（带编号） |
| 回复 | 是另一条消息，`role` 为 `assistant`，`reply_id` 等于用户消息的编号；自己的 `status` 为 `completed` / `failed` / `cancelled` 时结束 |
| `turn_status` | 回复已完成后仍是 `running`，**不能用来判断结束** |
| 同一个 `uuid`、同样内容再发 | 返回 200 和同一个会话（文档写的是 409）。可以用来找回没收到的回执 |
| 同一个 `uuid`、不同内容 | 409，错误码 3440009 |

## 3. 决定记录

用户离开期间由我和 Codex 决定的事都记在这里。

| # | 决定 | 谁定的 | 理由 |
|---|---|---|---|
| D1 | 对接代码作为通用连接器放在仓库里，不含任何具体应用的信息；应用、密钥、和哪个聊天应用配对，全部在部署时通过管理接口配置 | 用户 | "不要暴露任何 bot 相关的信息到 GitHub" |
| D2 | 做成插件：一个独立的连接器 `doubao`，不改飞书连接器的行为。它没有消息入口和出口，只贡献一个工具，给"经另一个连接器来的人"用 | 我 | 用户要求插件化；现有的"连接器"就是插件单位，只缺"给别的连接器来的人提供工具"这一点 |
| D3 | 聊天用的应用和调豆包用的应用**可以不是同一个**。身份按 `tenant_key` 加 `union_id` 核对：聊天消息里飞书给出的发送者 `union_id`，必须等于豆包令牌对应的 `union_id`。配置里也可以选按 `open_id` 核对（两边是同一个应用时） | 我 | 调豆包的应用可能是别的产品也在用的生产应用，不能让本服务去接它的消息事件。`union_id` 在同一开发者的应用之间相同；两个应用不属于同一开发者时核对会失败，授权不生效，这种情况下只能换成同一个应用 |
| D4 | 豆包的授权单独用一个对象 `DoubaoGrant` 保存，不去把现有的飞书授权对象参数化 | 我 | 飞书授权已在线上使用，改它的风险大于重复一小部分代码；两边互不影响，也符合"插件"的边界 |
| D5 | 第一版不申请 `offline_access`：令牌两小时，过期后重新授权 | 我 | 加这项权限要给生产应用发版，需要用户明确同意 |
| D6 | 是否结束只看助手回复那条消息自己的 `status`，用 `reply_id` 对上用户消息 | 我 | 实测 `turn_status` 不可靠 |
| D7 | 提交之后没收到回执：用同一个 `uuid` 和同样的内容再发一次找回；仍对不上就记为"可能已提交"，告诉对方去豆包里看，不换编号重发 | 我 | 实测同内容重放返回同一个会话 |
| D8 | 默认关闭。合并部署后不配置就什么都不变 | 我 | 和读群文档的开关同一做法 |

## 4. 方案

### 4.1 连接器可以给别的连接器来的人提供工具

现在一个连接器的工具，只给"经这个连接器来的人"用。加一项声明：

```
Connector.serves?: string[]      // 这个连接器的工具，也给经这些连接器来的人用
```

- 取"某个人能用哪些工具"时，把声明了 `serves` 的连接器的工具并进去。
- 工具执行时拿到的上下文不变（谁、来源、他说过的话）。连接器另外拿到聊天连接器核实过的身份标识（见 4.3）。
- "条件还成立吗"（`holds`）和"授权卡片长什么样"先问这些插件连接器：不是自己的条件就不回答，再轮到原来的连接器。

### 4.2 工具 `doubao_ask`，一种新的效果 `act`

```
doubao_ask(text, session)     // session 为空则新建会话
```

- 效果是 `act`：它以这个人的身份在外部系统里做事。和 `read` 一样只在本人私聊、只由本人的话引起的运行里提供；**一次运行读过外部内容之后不能再用**（现有规则是读过之后只允许 `read`，不变）。这样文档里藏的指令不能借 agent 去指挥豆包。
- 豆包的回复是外部内容，按现有规则处理：之后这次运行受限，原文在运行结束时清掉，agent 发给他的话留在历史里。
- 要有他明确的委托：工具说明里写明只在他明确要求交给豆包时使用。

### 4.3 身份和授权

- 飞书连接器在消息上多带一项飞书核实过的发送者 `union_id`（和 `origin` 一样取自验签后的事件）。
- 管理接口配置一对：哪个聊天应用可以用豆包、调豆包用哪个应用的凭证、按什么核对身份（默认 `union_id`）。
- 没授权时工具返回等待，卡片发在私聊里；回调地址是 `/v1/doubao/oauth/callback`。
- 回调时：换令牌，查 `user_info`，`tenant_key` 和 `union_id`（或 `open_id`）必须和发起请求的人一致，否则什么都不保存。授权范围只要这次需要的那几项，多了少了都拒绝。
- 令牌加密保存在这个人自己的 `DoubaoGrant` 对象里，模型和日志里都没有。收回授权：管理接口删除。

### 4.4 一次委托怎么走

连接器为每次调用存一条**操作记录**（在这个人的 `DoubaoGrant` 里）：要发的文字（不可变）、阶段、幂等键、会话编号、用户消息编号。

1. **没授权**：等授权（有卡片）。授权后接着办，回到下一步。
2. **提交**：先把操作记录写成"提交中"，再调豆包（新会话带第一条消息，或往已有会话发消息），`uuid` 由调用编号导出。成功后记下会话和用户消息编号，阶段改为"已提交"。然后返回等待，条件是"这条消息的回复结束了"，**没有卡片**；模型在这一轮告诉他"已经交给豆包了"。
3. **轮询**：Brain 问"条件成立了吗"，连接器去读消息：找到 `reply_id` 对得上的助手消息且到了终态，就成立；否则回答"还没有，过多久再问"（开头 5 秒，逐步到 60 秒）。
4. **取结果**：条件成立后接着办，同一次调用再跑一遍。这次阶段是"已提交"，只读取、不再提交，把回复的文字和产物（名称、类型、链接）交给模型。失败或被取消就如实说明。
5. **找回**：阶段停在"提交中"（上次没收到回执）时，用同样的 `uuid` 和内容再发一次；拿到同一个会话就继续，冲突或对不上就结束为"可能已提交"。
6. **取消**：他说"算了"，现有的取消机制结束请求；连接器对已知的会话发一个打断。
7. **期限**：等授权和等回复共用一个总期限（一小时），不延长。

为此对等待机制做两处通用的扩展：
- 等待可以**没有卡片**（`interaction` 可选）。
- `holds` 回答"还没有"时可以带"过多久再问"（`again_in_ms`），Brain 据此安排下一次询问。现在只有问不到时才会安排。

### 4.5 追问

工具结果里带会话编号；模型追问时传回。连接器核对这个会话确实是这个人通过本工具建的（操作记录里有），不接受任意编号。

### 4.6 配置

```
POST /v1/admin/doubao/apps
{ "for": { "connector": "feishu", "app_id": "<聊天应用>" },
  "app_id": "<调豆包的应用>", "app_secret": "…", "match": "union_id" }
DELETE /v1/admin/doubao/apps/<聊天应用>
GET/DELETE /v1/admin/doubao/grants/<聊天应用>/<tenant_key>/<open_id>
```

没有配置的聊天应用，私聊里没有这个工具。

## 5. 为什么这样仍然安全

| 关注点 | 怎么处理 |
|---|---|
| 以谁的身份 | 只以私聊里这个人本人的身份，用他自己授权的令牌 |
| 授权的是不是本人 | 回调时核对 `tenant_key` 和 `union_id`（或 `open_id`）；对不上不保存 |
| 谁能触发 | 只有他本人在私聊里直接说的话；定时器、群消息、文档内容、别人都不行 |
| 被读到的内容指挥 | 读过外部内容的运行不能再调用 |
| 豆包的回复 | 当作外部内容 |
| 重复执行 | 幂等键来自调用编号；已提交的接着办时只读不发 |
| 应用信息 | 只在部署的存储里；仓库、日志、模型输入里都没有密钥 |

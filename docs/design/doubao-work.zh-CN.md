# 对接豆包工作

状态：第 1–3 步已实现（分支 `doubao`），待部署后在真实环境验证。本文不写任何具体应用的编号、名称或地址；这些只在部署时配置。

## 1. 要做成什么

一个人在私聊里对 agent 说一件适合交给豆包工作做的事（"让豆包调研一下 X"）。agent 以**他本人**的身份把这件事交给豆包工作，豆包做完后 agent 把结果（文字和产物链接）告诉他。之后他接着追问，agent 在同一个豆包会话里继续。

第一版的范围：私聊里的明确委托、轮询取结果、最终文字和产物链接。不做：群里用、流式进度、上传文件、长期授权（`offline_access`）、把我们的 agent 做成豆包的插件。

## 2. 豆包工作的接口（公开文档加实测）

- 只支持用户身份。授权协议和飞书的相同（授权页、PKCE、`oauth/v3/token`、`authen/v1/user_info`），域名是 `accounts.doubao.com`；业务接口在 `open.doubao.com/open-apis/agent/v1`。
- 新建会话 `POST /sessions`，可带第一条消息；发消息 `POST /sessions/:id/events`；读消息 `GET /sessions/:id/messages`。每次写操作带调用方生成的 `uuid` 做幂等键。没有回调，只能轮询。

实测得到、文档没写或写得不一样的：

| 事项 | 实测结果 |
|---|---|
| 飞书应用自己的凭证 | 可以直接在豆包的授权和换令牌接口上用 |
| 令牌 | 不要 `offline_access` 时只有访问令牌，两小时，没有续期令牌 |
| 用户信息 | 返回 `open_id`、`union_id`、`user_id`、`tenant_key`；`tenant_key` 与飞书侧一致；`open_id` 按应用区分 |
| 新建会话的返回 | 会话编号，以及刚创建的那条用户消息（带编号） |
| 回复 | 是另一条消息，`role` 为 `assistant`，`reply_id` 等于用户消息的编号；自己的 `status` 为 `completed` / `failed` / `cancelled` 时结束 |
| `turn_status` | 回复已完成后仍是 `running`，**不能用来判断结束** |
| 同一个 `uuid`、同样内容再发 | 返回 200 和同一个会话（文档写的是 409）。可以用来找回没收到的回执 |
| 同一个 `uuid`、不同内容 | 409，错误码 3440009 |

| D2 | 做成插件：一个独立的连接器 `doubao`，不改飞书连接器的行为。它没有消息入口和出口，只贡献一个工具，给"经另一个连接器来的人"用 | 我 | 用户要求插件化；现有的"连接器"就是插件单位，只缺"给别的连接器来的人提供工具"这一点 |

| D4 | 豆包的授权单独用一个对象 `DoubaoGrant` 保存，不去把现有的飞书授权对象参数化 | 我 | 飞书授权已在线上使用，改它的风险大于重复一小部分代码；两边互不影响，也符合"插件"的边界 |
| D5 | 第一版不申请 `offline_access`：令牌两小时，过期后重新授权 | 我，Codex 同意 | 加权限需要应用发版，要用户明确同意；先用短期令牌把流程跑通 |
| D6 | 是否结束只看助手回复那条消息自己的 `status`，用 `reply_id` 对上用户消息 | 我 | 实测 `turn_status` 不可靠 |
| D7 | 提交之后没收到回执：用同一个 `uuid` 和同样的内容再发一次找回；仍对不上就记为"可能已提交"，告诉对方去豆包里看，不换编号重发 | 我 | 实测同内容重放返回同一个会话 |
| D8 | 默认关闭。没有配对的聊天应用，模型的工具列表里**没有**这个工具；群里也没有 | 我，按 Codex 意见 | 消息到达时由插件连接器说"这条消息的发送者可以用哪些可选工具"，记在消息上（`data.offered`），别的连接器自己写的不算 |
| D9 | 必须是本人在**这一次**的消息里提到了豆包（"豆包"或"doubao"），或者这条消息是在回复一份豆包结果的答复；否则工具拒绝、什么都不发。以前提到过不算。这只是下限：是不是真的在委托（比如"别交给豆包"）仍由模型判断，拿不准就问 | 我；Codex 要求以当次明确委托为准（第一版按"最近一天提到过"实现，被它否决后改） | 工具说明只是引导模型，不能当作"他委托了"的证据 |
| D10 | 追问传 `carry_on: true`，不传会话编号。接哪一次委托：他回复的那条答复是依据哪次委托写的，就接那一次（沿用"答复依据什么写成"的现有记录）；没有回复时，最近一天只有一个会话就接它，有多个就不猜，让模型去问 | 我；Codex 要求绑定到原请求（第一版按"最近一个会话"实现，被它复现出接错后改） | 外部工具的结果在下一轮会从模型的上下文里清掉，模型留不住会话编号；"最近一个"会接错 |
| D11 | "已经交给豆包"这句话由系统发固定的一句，不由模型说 | 我，按 Codex 意见 | 授权后接着办的那次运行里，模型写的话算作请求的最终答复、不会马上发出；由系统发才能在两种路径下都只说一次 |
| D12 | 一次委托只有一个截止时间（首次调用起一小时），记在操作记录里；等授权、等回复、重新授权都不重新计时。过了就不再向豆包发任何请求（每次外发前都查），本地直接结束，并由系统告诉他一次"没有在时限内完成，那边可能还在继续" | 我，按 Codex 意见 | 两个阶段各算一小时会让总时长不可控 |
| D13 | 等回复途中授权失效：同一次委托重新发授权卡片，授权后继续等同一条回复，不重新提交 | 我，按 Codex 意见 | 旧令牌剩余时间可能不足一小时 |
| D14 | 管理员每次设置配对都是一个新版本。旧配对下发起的授权、拿到的令牌，在改配或删除之后都不再使用；每次委托也记着它是在哪个配对版本、哪一代授权下发起的，之后只在同一配对同一代下继续，已经取回的结果也一样 | 我，按 Codex 意见 | 防止换了应用之后旧授权借新配对生效 |
| D15 | 取消只是停止等待，不去打断豆包；工具说明里写明 | 我，按 Codex 意见 | 打断接口按会话生效，可能影响同一会话里的另一件事；没有远端确认就不能说"已停止" |
| D16 | 提交时没收到回执：同一个幂等键、同样内容立即再试一次；仍无结果就记为"可能已提交"并如实告知，不换键重发。第二次尝试遇到冲突、或者对方答了成功却没说建了什么，也按"可能已提交"处理；只有明确拒绝才说没发出 | 我，按 Codex 意见 | 往已有会话发消息的重放行为还没在真实环境单独验证过，拿不准时宁可不重发 |
| D17 | 委托记录在它的截止时间过后再留两小时才会被回收（不论到了哪个阶段），这段时间里同一次调用再来仍是同一条记录、同一个幂等键和截止时间；每人最多 50 条，满了就拒绝新的 | 我，按 Codex 意见 | 提前回收会让重放的调用拿到新的键和新的期限 |
| D18 | 已经取回的结果是他本人的内容：令牌自然过期之后仍然可以交给他；管理员收回授权或改了配对之后不行 | 我，回应 Codex 的提问 | 结果在取回时已用他的授权读到并保存在他自己的记录里；自然过期不代表他撤回了授权 |
| D19 | 每次向豆包外发之前（第一次和重试都一样，核对之后紧接着发，中间不等任何别的事）都重新核对：授权代次和配对没变、令牌还是那一个、没过截止。一次都没发出去就如实说"没发"；第一次没回音而权限已变，就记为"无法确认"，不再发 | 我，按 Codex 意见 | 两次尝试之间可能被撤权或改配 |
| D20 | 回复在很长的会话里：每次轮询最多翻五页，下一次从上次停下的地方接着翻，翻过他那条消息或翻到底再回到最新一页 | 我，按 Codex 意见 | 每次都从头翻五页会永远够不到 |
| D21 | 只要对他说过"已经交出去处理了"，之后不管停在哪一步结束（包括等他重新授权时超时），都告诉他一次"不再等了" | 我，按 Codex 意见 | 否则承诺过"完成后回你"却没有下文 |
| D22 | **留给用户定的产品取舍。** 现状：是不是"明确委托"由模型判断，代码只保证下限（D9）。Codex 的意见：按"只在本人明确委托时以其身份外发"的约定，这还不够，建议模型只能提议，由用户在卡片上点一次确认后才外发。我没有采纳为默认：用户此前多次要求"让模型选、不要特化规则"，每次委托多点一次也改变了体验；而且功能默认关闭，要管理员配对后才有。若要改成"先确认再发"，是在工具返回等待时发一张确认卡片，改动集中在连接器里 | 待用户决定；Codex 明确不认可现状满足上述约定 | 风险：模型把"提到豆包"误当成委托，以他的身份在豆包里发起一次对话（内容是模型写的那段话）。读过外部内容的运行不能调用，所以外部内容指挥不了它 |
| D23 | 换令牌时指明只要这次需要的那几项权限 | 我，Codex 复核通过 | 第一次真实授权见到的：本人以前给这个应用授过更多权限，默认签发的令牌带着全部权限，被"多了就拒绝"挡下 |
| D24 | 授权回调取走了邀请而没成功（被拒、账号不对、本人没同意）时，等这张卡片的请求立刻结束，并对本人说一次"授权没有完成，这件事还没有做，需要的话请再说一遍"。等待的条件绑定到具体那张卡片：之后经另一张卡片授权成功，也不会把旧请求带起来。每张卡片记着自己的结局（有人回来了正在核对、成功、没成功），保留到等它的请求不可能再被问到为止，不按条数淘汰；核对途中出任何意外（包括连不上豆包）也算没成功，除非令牌其实已经存下。已经交出去的事在补授权时没成功，说的是"不再等了，可以去那边看"，不引导重新交办 | 我，按 Codex 意见 | 真实环境里见到的：失败后请求还挂着，本人照原话再说，模型看历史只回"在等授权"，拿不到新卡片；Codex 模拟出旧请求和新请求一起恢复、提交两次 |
| D25 | 交给豆包的话用本人的原话，只补它理解所必需的上下文，不加本人没提的要求、范围、格式 | 用户（看到真实转述后） | 第一次真实交办里模型自己加了限定语境、要候选、要来源链接 |
| D26 | 追问不用再点名：本人写这句话时看到的最后一条 agent 答复如果就是豆包做的那一份（按实际送达记录判定，24 小时内），这句话是不是接着那件事由模型判断，是就接到那一项工作的原会话里。中间隔了 agent 自己的答复就不再算；新任务仍然要当次点名；他让 agent 自己答、换了话题、或不想写进豆包会话的内容，agent 自己答；分不清而且会改变话发到哪里时只问一次 | 用户（真实使用后），Codex 同意 | 第一次真实使用：让豆包调研后紧接着追问，没点名，模型改派给了自己的沙箱。Codex 提醒的代价：一句本想在这里问的话（比如带内部数字）可能被写进豆包会话 |
| D22 结论 | 不做每次确认卡片：是不是委托由模型判断，代码保证下限（D9 加 D26） | 用户的方向，Codex 也不主张每次弹卡 | 见 D26 |

## 4. 方案

### 4.1 连接器可以给别的连接器来的人提供工具

现在一个连接器的工具，只给"经这个连接器来的人"用。加一项声明：

```
Connector.serves?: string[]      // 这个连接器的工具，也给经这些连接器来的人用
```

- 取"某个人能用哪些工具"时，把声明了 `serves` 的连接器的工具并进去。
- 工具执行时拿到的上下文不变（谁、来源、他说过的话）。连接器另外拿到聊天连接器核实过的身份标识（见 4.3）。
- "条件还成立吗"（`holds`）和"授权卡片长什么样"先问这些插件连接器：不是自己的条件就不回答，再轮到原来的连接器。

### 4.2 工具 `doubao_ask`，一种新的效果 `act`

```
doubao_ask(text, carry_on)     // carry_on 为 true：接着他最近一次委托所在的会话
```

- 效果是 `act`：它以这个人的身份在外部系统里做事。和 `read` 一样只在本人私聊、只由本人的话引起的运行里提供；**一次运行读过外部内容之后不能再用**（现有规则是读过之后只允许 `read`，不变）。这样文档里藏的指令不能借 agent 去指挥豆包。
- 豆包的回复是外部内容，按现有规则处理：之后这次运行受限，原文在运行结束时清掉，agent 发给他的话留在历史里。
- 要有他明确的委托：工具说明里写明只在他明确要求交给豆包时使用；工具自己再核对他本人的消息里提到了豆包（D9）。
- 这是一个可选工具（`optional`）：只有消息到达时插件连接器标记过的消息才有（D8）。

### 4.3 身份和授权

- 飞书连接器在消息上多带一项飞书核实过的发送者 `union_id`，取自验签后的事件，单独一个字段，不放进 `origin`（`origin` 决定私聊会话的归属，改它会把历史拆开）。
- 管理接口配置一对：哪个聊天应用可以用豆包、调豆包用哪个应用的凭证、按什么核对身份（默认 `union_id`）。
- 没授权时工具返回等待，卡片发在私聊里；回调地址是 `/v1/doubao/oauth/callback`。
- 回调时：换令牌，查 `user_info`，`tenant_key` 和 `union_id`（或 `open_id`）必须和发起请求的人一致，否则什么都不保存。授权范围只要这次需要的那几项，多了少了都拒绝。换令牌时也明确只要这几项：一个人以前给这个应用授过更多权限时，豆包默认签发的令牌带着全部权限（真实环境里见到的），不指明就会被这条规则拒掉。
- 令牌加密保存在这个人自己的 `DoubaoGrant` 对象里，模型和日志里都没有。收回授权：管理接口删除。

### 4.4 一次委托怎么走

连接器为每次调用存一条**操作记录**（在这个人的 `DoubaoGrant` 里）：要发的文字（不可变）、阶段、幂等键、会话编号、用户消息编号。

0. **记下来**：第一次调用就写一条操作记录（阶段"已受理"）：文字、随机生成的幂等键、截止时间、去哪个会话。同一次调用再来（接着办、被打断后重放）都是这一条。
1. **没授权**：等授权（有卡片）。授权后接着办，回到下一步。
2. **提交**：先把阶段改成"提交中"，再调豆包（新会话带第一条消息，或往已有会话发消息）。成功后记下会话和用户消息编号，阶段改为"已提交"。然后返回等待，条件是"这条消息的回复结束了"，**没有卡片**；系统发一句固定的"已经交出去处理了"（D11）。
3. **轮询**：Brain 问"条件成立了吗"，连接器去读消息：找到 `reply_id` 对得上的助手消息且到了终态，就成立；否则回答"还没有，过多久再问"（开头 5 秒，逐步到 60 秒）。
4. **取结果**：条件成立后接着办，同一次调用再跑一遍。这次阶段是"已提交"，只读取、不再提交，把回复的文字和产物（名称、类型、链接）交给模型。失败或被取消就如实说明。
5. **找回**：见 D16。
6. **取消**：见 D15。
7. **期限**：见 D12。
8. **途中授权失效**：见 D13。

为此对等待机制做了几处通用的扩展：
- 等待可以**没有卡片**（`interaction` 可选）。
- `holds` 回答"还没有"时可以带"过多久再问"（`again_in_ms`），Brain 据此安排下一次询问。
- 没有卡片的等待，系统发一句固定的话说明"已交出去"，给模型的说明也相应不同。
- 同一个请求每次进入等待都会立即问一次条件（按"上次被接着办的时间"区分轮次），所以先等授权、再等回复、再等授权都不会漏问。

### 4.5 追问

见 D10。模型不接触会话编号；连接器只会接着这个人自己通过本工具建的会话。

### 4.6 配置

```
POST /v1/admin/doubao/apps
{ "for": { "connector": "feishu", "app_id": "<聊天应用>" },
  "app_id": "<调豆包的应用>", "app_secret": "…", "match": "union_id" }
DELETE /v1/admin/doubao/apps/<聊天应用>
GET/DELETE /v1/admin/doubao/grants/<聊天应用>/<tenant_key>/<open_id>
```

没有配置的聊天应用，私聊里没有这个工具。密钥只进不出：任何接口都不返回它。

## 5. 为什么这样仍然安全

| 关注点 | 怎么处理 |
|---|---|
| 以谁的身份 | 只以私聊里这个人本人的身份，用他自己授权的令牌 |
| 授权的是不是本人 | 回调时核对 `tenant_key` 和 `union_id`（或 `open_id`）；对不上不保存 |
| 谁能触发 | 只有他本人在私聊里直接说的话；定时器、群消息、文档内容、别人都不行 |
| 被读到的内容指挥 | 读过外部内容的运行不能再调用 |
| 豆包的回复 | 当作外部内容 |
| 重复执行 | 幂等键来自调用编号；已提交的接着办时只读不发 |
| 应用信息 | 只在部署的存储里；仓库、日志、模型输入里都没有密钥 |

## 6. 步骤

每步先写测试，过 Codex 复核。

1. 通用扩展：`serves`、`act`、等待可以没有卡片、`again_in_ms`、`holds` 与卡片先问插件。
2. `DoubaoGrant`、回调、管理接口、飞书消息带 `union_id`。
3. 工具 `doubao_ask`、操作记录、轮询、找回、取消、文档。
4. 部署；配置并在真实环境验证（需要用户本人授权一次）。

## 7. 真实环境里还要确认的

- 两个应用下同一个人的 `union_id` 是否相同（不同则按 D3 授权不生效，需要改用同一个应用）。
- 读消息接口带 `order=desc` 是否可用（实测过的是 `asc`），翻页字段是否是 `has_more` / `page_token`（按飞书惯例写的，最多翻 5 页，翻到他那条消息为止）。
- 往已有会话发消息时，同一个幂等键重放是否返回同一条用户消息。
- 产物（文档等）在消息里的字段形状：现在按"名称、类型、链接"取，链接取不到就只给名称和类型。

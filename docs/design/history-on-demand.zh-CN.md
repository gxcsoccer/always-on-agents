# 历史按需读，以及用本人的 GitHub 权限跑沙箱任务

状态：草案 v1，待 Codex 评审、待用户定夺。对应 RFC #100 和 #95 的 B 部分。

两件事放在一份文档里，因为它们卡在同一个问题上：**用某个人的权限读到的东西、在某个地方说过的话，可以流到哪里。** 先把这条规则说清楚（§2），两件事各自的做法（§3、§4）都从它推出来。

## 1. 现状

事实来自对当前代码（main `a83bbb5`）的逐项核对。

### 1.1 模型看得到什么

- 每一轮带上本会话最近 80 条记录（`#transcript`，`MAX_TRANSCRIPT_ITEMS`）。更早的看不到，也没有任何工具去取。模型只有这个窗口和记忆文件。
- **群里的记录是全群共用的一份。** 乙发起的一轮里，能看到甲之前 @ agent 的消息和 agent 给甲的回复，每条消息标着是谁写的。
- 群里只有 @ agent 的消息才会进来。没 @ 它的群聊它没有，代码里也没有任何向平台要聊天记录的调用。
- 沙箱任务只收到交办说明（`brief`），连标题都没有，更没有对话原文。接着做时恢复的是上一个任务的文件和它自己的记录。

### 1.2 已经有的边界

- **每个会话范围是一个独立的 Brain**（一个私聊、一个群各是一个 Durable Object，各有自己的存储）。私聊里的话在结构上到不了群的那个 Brain，反过来也一样。
- **"读过外部内容"的规则**（`sawOutside` / `mayUse`）：一轮里调用过连接器的读工具之后，只能回话和继续读；写记忆、设定时器、交办任务、以本人名义做事都被拒绝。这一轮结束后它的记录被清掉，只留下实际发出去的话（`said` 表）。
- **以本人名义做事的一轮在群里结束后同样被清掉**（`#forgetPersonal`），留下的也只是发出去的话。
- **只给本人看的东西**（授权卡片、发到本人私聊的回执）不进群的记录。

### 1.3 两类毛病

1. **该看的看不到。**"上周说的那个方案"答不上来；沙箱只能靠 Brain 的转述干活，转述漏了什么它无从知道。
2. **#98 合入时记下的已知限制。** 群里的记录是共用的，乙让 agent 以乙的名义在 GitHub 上建 issue 时，甲说过的话可能被写进去。现在只有工具说明里的一句话管着。

### 1.4 更早的决定

- `reply-chain.zh-CN.md` §4 明确否决过"读群聊历史"的工具，理由是会把别人的话带进以某个人名义的一轮。本文重新打开这个决定，理由见 §2。
- 那份文档 §3.2–3.3 还写着"别人的消息原文从不给模型"，代码现在不是这样：直接回复的那条同事消息是给的，标明是材料而不是请求。本次一并更正那份文档。

## 2. 一条规则：内容不流向比它原本可见范围更宽的地方

### 2.1 两种方案

RFC #100 原文的方案是**按人切**：群里某人发起的一轮，默认只带这个人自己的话；读别人的话算"读了外部内容"，读了就不能再以本人名义做事。

它干净，但代价是这句话做不了：**"把刚才大家的讨论在某仓库提个 issue。"** 这正是 #95 的评论里记下的真实场景，也是群里用 agent 最自然的用法之一。

另一种是**按可见范围切**。同一个群里的人本来就互相看得到彼此的话；乙作为群成员，自己动手把讨论整理成 issue 是他有权做、也由他负责的事。真正不该发生的是另外两件：

- **范围更窄的内容流到范围更宽的地方。** 私聊里的话到群里；用某个人的授权读到的文档、私有仓库的内容，到看不到它们的人面前。
- **不可信的内容左右了以本人名义的动作。** 外面读来的文字里夹着指令。

业界的做法是后一种。在共享的频道里，产品普遍把整个线程的内容当作可用的材料（GitHub Copilot 的 Slack 集成把整个线程存进生成的产物；Claude 在共享频道里把别人的消息当作"任务的信息而不是指令"）；限制落在别处：答复只用提问者或所有人都能看到的内容（Slack 的实时搜索接口、Glean、Microsoft 365 Copilot），个人连接器读到的结果发布前先让本人看，有外部成员的频道里收紧。调研没有找到哪个产品按"这句话是谁说的"来限制同一频道内的使用。

用户此前定的方向也是后一种：目标是防止别人的话和私密内容外泄，而不是"只能用本人的话"。

**本文按后一种写。** 两种方案的取舍在 §6 第 1 条，请用户确认。

### 2.2 规则本身

每一份内容有它原本的可见范围：

| 内容 | 可见范围 |
|---|---|
| 私聊里的话、agent 在私聊里的回复 | 这个人 |
| 群里 @ agent 的话、agent 发在群里的回复 | 这个群的成员 |
| 用某个人的授权读到的东西（文档、私有仓库） | 这个人（以及本来就有权限的人，我们不知道是谁） |
| 公开的东西（公开仓库、公开网页） | 所有人，但不可信 |

**一轮可以用的，是在它所在的地方本来就看得到的内容。** 往更宽的地方送东西（发到群里、发到 GitHub）时：

1. 同一范围内的内容可以用，由提出的人负责。
2. 更窄范围的内容不能直接出去。已有的机制管着这一条：不同范围是不同的 Brain；用个人授权读的那一轮受"读过外部内容"的规则限制并在结束后清掉。
3. 不可信的内容不能左右动作。也是已有的规则管着。

所以按这条规则，**现在群里共用记录的做法大体是对的**，不需要按人切。#98 记下的那个限制要重新归类：甲在群里说的话被乙要求写进 issue，不算外泄；要管的是"乙没让写、模型自己带进去了"，那是忠实于请求的问题，由工具说明和评测管（§3.5）。

### 2.3 这条规则下还漏着的

核对代码后有两处：

- **有外部成员的群。** 群里的话对外部成员本来就可见，但"读群里没 @ agent 的消息"（§3.3）在这种群里风险不同。已有的以本人名义的工具每次都向平台确认群是内部群；读历史照此办理。
- **话题。** 同一个群的不同话题现在是不同的会话。它们对群成员同样可见，按规则可以互相读；第一版先只读本话题，保持简单。

## 3. 历史按需读（#100）

### 3.1 Brain 的读历史工具

一个工具，`read_history`。读的是**这个会话自己保存的记录中，窗口之外的部分**：别人写给 agent 的消息，和 agent 实际发出去的话。

参数照业界通行的形状（Slack 的 `conversations.history` 和 `assistant.search.context`、飞书的消息列表接口都是这几样）：

| 参数 | 含义 |
|---|---|
| `query` | 关键词，可空。按字面包含匹配，不做向量检索 |
| `from` | 只看某个人写的，可空 |
| `before` | 只看这个时间之前的，可空；翻页用 |
| `limit` | 条数，上限 30 |

返回每条的时间、谁写的、正文（过长截断并注明），以及还有没有更早的。

**它不算"读了外部内容"。** 它返回的每一条，如果窗口更大本来就会在上下文里：同一个会话、同一个可见范围、同样的来源。所以读了之后工具不受限。

**它不返回的**：被清掉的那些轮次里读来的内容（已经不在记录里，只剩发出去的话）；只给某个人看的东西；别的会话、别的话题。

要改的一处：现在 `said` 表只在私聊、以本人名义的一轮、接续请求的答复这三种情况下记录发出去的话；群里不以任何人名义的一轮，它说的话只留在模型输出的记录里。读历史需要"agent 说过什么"有一个统一的出处，所以把记录条件放宽为：所有实际送达的、agent 自己写的话都记。

保留期不变：消息正文保留 30 天。

### 3.2 沙箱读交办它的那段对话

沙箱里加一个同样形状的读工具，经已有的回调通道向交办它的那个 Brain 要，只能读交办它的那一个会话。

这样 Brain 的交办说明不必面面俱到，沙箱发现缺什么可以自己去看原话。

对照 §2.2：对话的内容进了沙箱，沙箱的产出回到同一个会话，推送要本人批准，出口只通往模型和 GitHub。没有流向更宽的地方。唯一新增的路径是"对话里的话被写进提交"，它经过本人对推送的批准。

对话的内容对沙箱来说是可信的输入（是人写给 agent 的话）；沙箱自己读到的仓库内容、GitHub 上的文字仍然是不可信的，这一点不变。

### 3.3 群里没 @ agent 的消息（默认关闭，需要用户单独决定）

"群里刚才讨论的结论"这类问题，答案往往在没 @ agent 的消息里。要读它们，需要向平台要聊天记录。

- 连接器的 channel 增加可选的 `history`，和 `read_history` 同样的参数；没有它的连接器就只有 §3.1 的那部分。
- 各平台都把这个做成单独的、标为敏感的权限（Teams 的 `ChatMessage.Read.Chat`、Discord 的 `MESSAGE_CONTENT`、Slack 的 `*:history`）。飞书读群历史需要机器人在群里，并且需要"获取群组中所有消息"这项敏感权限。
- **所以它默认关闭**，需要部署者按应用打开，并且需要用户明确同意给应用加权限。
- 只在内部群里读（每次向平台确认）；读到的别人的话标明是材料而不是请求，和现在对"直接回复的那条同事消息"的处理一样。
- 是按需读，不是全量接收：不订阅群里所有消息的事件，只在模型调用工具时按时间范围取一页。

这一步的价值最大，但也最需要用户点头，所以单独列出，不和前两步绑在一起。

### 3.4 默认上下文不变

最近 80 条的窗口保持原样。不做按人切。理由见 §2。

### 3.5 以本人名义写东西时带了谁的话

按 §2.2，这是忠实于请求的问题：

- 工具说明里已有的那句（只写这个人要求写的内容）保留。
- 评测加两组：乙说"把刚才的讨论提个 issue"，正文里有讨论的内容；乙说"把我说的这个问题提个 issue"，正文里没有甲的话。
- 不为此加程序上的隔离。如果评测显示模型经常带错，再考虑别的办法。

### 3.6 和已有东西的关系

- `said` 表：继续是"agent 说过什么"的出处，记录范围放宽（§3.1）。
- 回复链（`quoted` / `chain`）：不变。它解决的是"这条回复指的是哪条"，读历史解决的是"更早说过什么"。
- 记忆文件：不变。它存的是值得长期记住的事，不是聊天记录。
- 没有可以因此删掉的东西。

## 4. 用本人的 GitHub 权限跑沙箱任务（#95 的 B 部分）

### 4.1 已经设计过、已经定了的

`github-as-the-person.zh-CN.md` 在做 A 部分（以本人名义建 issue、评论，已上线）时，已经把 B 的方案和 Codex 定过，用户也定了"先 A 后 B"。这里只列结论，不重新设计：

- **凭据由 GitHub 连接器决定**（§3.4）。顺序：仓库自己的会话或绑定的群，用应用的安装令牌（现状）；否则，私聊、只有一个明确的提出人、他有有效的授权、通过租户边界的核对，用他的用户令牌；否则没有，只能读公开的。
- **不用限定单仓库的令牌**（§3.1）。按人保存一个通用的可续期令牌，留在授权对象里，不进容器；出口代理只给"任务所在的那个仓库"加凭据。这和业界最稳的做法一致（Claude Code 网页版：凭据不进虚拟机，由代理替换）。
- **租户的边界要另外核对**（§3.1.1）。只看"用户与应用的交集"不够；用之前先确认目标仓库属于当前租户名下的安装。
- **授权在启动沙箱之前要**（§3.4、§8.1）。走已有的"发卡片、授权完接着做"；在交办的那一步加一个内部操作"授权后交办原来那件任务"，原请求的编号作幂等键。取消或超时启动零个任务，重放只启动一个。运行中每次现取，不缓存。
- **只借给本人指过的仓库**；接着做和从快照恢复时都要复核。
- **第一版只在私聊里借，群里不借**（§3.5）。
- **撤销**（§3.8）：本人取消授权时，停掉正在用他的凭据跑的任务。
- **署名保持 agent**（§3.7），默认不加共同作者。

### 4.2 它和 §2 的关系

私有仓库的内容，可见范围是"这个人"。第一版只在私聊里借，结果、进度、审批问题都回到这个人的私聊：**没有流向更宽的地方**，所以不需要新的机制。

群里借个人凭据之所以难，正是因为群是更宽的范围：进度、快照、接续、审批都是群共用的。业界也没有哪家产品按读者的权限过滤线程里的输出，都是限制谁能发起，或者把个人权限的使用放到私聊。所以维持"群里不借"，不在这一版里解决。

### 4.3 还要做的

按依赖顺序：

1. **借凭据的判断挪进 GitHub 连接器。** 现在在沙箱任务对象里（`#lend`）。行为不变，只是换地方。
2. **任务知道是谁提出的。** 现在启动参数里没有提出人。加上，只用于向连接器要凭据。
3. **连接器的第三档**：按 4.1 的条件给出用户令牌。出口代理不变（它只管"给不给这个仓库加凭据"，不管凭据是哪种）。
4. **启动前授权**：交办私有仓库而本人还没授权时，走等待机制；授权后启动原来那件任务。先匿名探一下 git 端点，公开仓库不触发授权。
5. **接着做、快照恢复时复核**授权。
6. **撤销时停任务**。
7. **推送**：私聊里本人批准（已有的规则：私聊里是回复的那个人）。

### 4.4 实现前要实测的

- **用户令牌能否直接用于 HTTPS 的 git，凭据形式是什么。** 设计文档 §3.1 记着"可以，形式不变"，但这次调研在 GitHub 官方文档里没有找到明文（文档只对安装令牌写了 `x-access-token`）。需要用真实的授权试一次只读的 `git ls-remote`。这要用到某个人的授权，所以要先得到本人同意。
- 用用户令牌推送时，GitHub 上显示的推送者是谁（预期是本人）。
- 应用没有申请 `checks`、`statuses` 的读权限；沙箱里查 CI 结果在私有仓库上预期会被拒。这不挡 B，但 #87 和 #110 需要，届时一并处理。

## 5. 实施顺序

各步独立，每一步都是测试先行、过 Codex、用户说了才合入和部署。

| 步 | 内容 | 需要用户另外同意的 |
|---|---|---|
| 1 | Brain 的 `read_history`；`said` 的记录范围放宽 | 无 |
| 2 | #95B：借凭据的判断挪进连接器、任务带上提出人（纯重构，行为不变） | 无 |
| 3 | #95B：实测用户令牌用于 git | 用本人的授权做一次只读的探测 |
| 4 | #95B：第三档凭据、启动前授权、复核、撤销时停任务 | 无 |
| 5 | 沙箱读交办它的那段对话 | 无 |
| 6 | 群里没 @ agent 的消息 | 给应用加敏感权限、按应用打开开关 |

第 1 步和第 2 步互不依赖，可以并行。

## 6. 请用户定的

1. **按可见范围切，还是按人切（§2.1）。** 本文按前者写：群里共用记录的做法保留，"把大家的讨论提个 issue"可以做，带了谁的话由提出的人负责。后者更严，但这句话做不了。**建议前者。**
2. **群里没 @ agent 的消息要不要读（§3.3）。** 需要给应用加一项敏感权限。建议先做前五步，这一步等用起来再定。
3. **#95B 实测时用谁的授权（§4.4）。** 需要对一个私有仓库做一次只读的探测。

## 7. 不做

- 不做按人切的默认上下文。
- 不做向量检索；按时间和关键词取不够用时再说。
- 不订阅群里的全部消息。
- 不在群里借个人的仓库权限。
- 不让沙箱自己开 PR、合并（#110 讨论）。

## 8. 验收

- 读历史：窗口之外的一条旧消息能按关键词、按人、按时间取到；取到之后工具不受限；别的会话、别的话题、只给个人看的内容、被清掉的轮次里读来的内容取不到；30 天之外的取不到。
- `said`：群里不以任何人名义的一轮说的话，之后读得到。
- #95B：私聊里对本人的私有仓库交办任务，没授权时发卡片、授权后启动一次且只启动一次；取消或超时不启动；令牌不出现在容器里；别的仓库拿不到凭据；仓库不在本租户的安装名下时不借；撤销后正在跑的任务停下；群里同样的请求不借。
- 忠实于请求：§3.5 的两组评测。

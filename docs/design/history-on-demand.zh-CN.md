# 历史按需读，以及用本人的 GitHub 权限跑沙箱任务

状态：草案 v4。方向已由用户定为丙（2026-11-27，§2.1）；怎么用程序保证丙，见 §2.4，按 Codex 对 v2 的评审改过（§9）。对应 RFC #100 和 #95 的 B 部分。

两件事放在一份文档里，因为它们卡在同一个问题上：**用某个人的权限读到的东西、在某个地方说过的话，可以流到哪里。** 先把这条规则说清楚（§2），两件事各自的做法（§3、§4）都从它推出来。

## 1. 现状

事实来自对当前代码（main `a83bbb5`）的逐项核对。

### 1.1 模型看得到什么

- 每一轮带上本会话最近 80 条记录（`#transcript`，`MAX_TRANSCRIPT_ITEMS`）。更早的看不到，也没有任何工具去取。模型只有这个窗口和记忆文件。
- **群里的记录是全群共用的一份。** 乙发起的一轮里，能看到甲之前 @ agent 的消息和 agent 给甲的回复，每条消息标着是谁写的。
- 群里只有 @ agent 的消息才会进来。没 @ 它的群聊它没有，代码里也没有任何向平台要聊天记录的调用。
- 沙箱任务只收到交办说明（`brief`），连标题都没有，更没有对话原文。接着做时恢复的是上一个任务的文件和它自己的记录。

### 1.2 已经有的边界

- **每个会话范围是一个独立的 Brain**（一个私聊、一个群各是一个 Durable Object，各有自己的存储）。私聊里的话在结构上到不了群的那个 Brain，反过来也一样。
- **"读过外部内容"的规则**（`sawOutside` / `mayUse`）：一轮里调用过连接器的读工具之后，只能回话和继续读；写记忆、设定时器、交办任务、以本人名义做事都被拒绝。这一轮结束后它的记录被清掉，只留下实际发出去的话（`said` 表）。
- **以本人名义做事的一轮在群里结束后同样被清掉**（`#forgetPersonal`），留下的也只是发出去的话。
- **只给本人看的东西**（授权卡片、发到本人私聊的回执）不进群的记录。

### 1.3 两类毛病

1. **该看的看不到。**"上周说的那个方案"答不上来；沙箱只能靠 Brain 的转述干活，转述漏了什么它无从知道。
2. **#98 合入时记下的已知限制。** 群里的记录是共用的，乙让 agent 以乙的名义在 GitHub 上建 issue 时，甲说过的话可能被写进去。现在只有工具说明里的一句话管着。

### 1.4 更早的决定

- `reply-chain.zh-CN.md` §4 明确否决过"读群聊历史"的工具，理由是会把别人的话带进以某个人名义的一轮。本文重新打开这个决定，理由见 §2。
- 那份文档 §3.2–3.3 还写着"别人的消息原文从不给模型"，代码现在不是这样：直接回复的那条同事消息是给的，标明是材料而不是请求。本次一并更正那份文档。

## 2. 一条规则：内容不流向比它原本可见范围更宽的地方

### 2.1 三种方案，以及已经定过的是哪一种

**已经定过的是"按人切"。** 用户在 2026-11-26（`github-as-the-person.zh-CN.md` §13.5）定的根治方向是：以某人名义行动的那一轮，默认上下文只有这个人自己的对话线；读别人的消息算"读了外部内容"，此后这一轮不能再以本人名义写。RFC #100 原文也是这样写的。

本文请用户重新考虑这个方向，理由和三种方案如下。

**用户在 2026-11-27 定了：改成丙。** 原话的意思是别人在群里说的话可以被另一个群成员让 agent 写进 issue，要更 agentic 一些，在安全和智能之间取平衡。2026-11-26 的"按人切"由此作废，下文按丙写。

**甲：按人切（2026-11-26 定的旧方向，已被下面的决定取代）。** 干净，程序能保证。代价是这句话做不了：**"把刚才大家的讨论在某仓库提个 issue。"** 这是 #95 的评论里记下的真实场景，也是群里用 agent 最自然的用法之一。

**乙：按可见范围切。** 同一个群里的人本来就互相看得到彼此的话；乙作为群成员，自己动手把讨论整理成 issue 是他有权做、也由他负责的事。要挡的是另外两件：范围更窄的内容流到范围更宽的地方；不可信的内容左右了以本人名义的动作。

业界的做法接近乙。在共享的频道里，产品普遍把整个线程的内容当作可用的材料（GitHub Copilot 的 Slack 集成把整个线程存进生成的产物；Claude 在共享频道里把别人的消息当作"任务的信息而不是指令"）；限制落在别处：答复只用提问者或所有人都能看到的内容（Slack 的实时搜索接口、Glean、Microsoft 365 Copilot），个人连接器读到的结果发布前先让本人看。调研没有找到哪个产品按"这句话是谁说的"来限制同一频道内的使用。

**乙有一个反例，是 Codex 指出的。** 甲用自己的授权读了一篇文档，agent 把摘要答在群里。之后乙让 agent 把这段写进一个公开仓库的 issue。那条答复群成员确实都看得见，现有代码也确实会让它作为群里的历史再次出现（清掉的是那一轮读来的原文，不是已经送达的摘要）。但摘要的来源是甲一个人的权限，目标仓库的读者又是另一批人。按乙，这算"同一范围内、由乙负责"；这个结论不对。

**丙：乙，加上"来自个人授权的内容不继续外传"。** 这是本文建议的方案。

- 群里的人说的话、agent 对这些话的普通回复：按乙，可以用。"把大家的讨论提个 issue"可以做，提出的人要说清楚用哪段讨论、发到哪里（现有的约束已经要求目标仓库是他自己说的）。
- agent 的某条回复如果是**用某个人的授权读了东西之后写的**，它的来源比群更窄。往比群更宽的地方送东西时（以别人的名义发到 GitHub），这类回复不作为材料：要么省略，要么只问那一段能不能公开。授权的本人自己要求发，不受此限。
- 这条界线怎么由程序保证，见 §2.4。只看单条回复上记的"读过什么、为谁写"不够：别人请 agent 在群里把那段摘要重述一遍，重述的那条回复自己什么都没读过。

丙比甲宽（讨论可以用），比乙严（个人授权读来的东西不搭便车出去）。

### 2.2 规则本身（按丙）

每一份内容有它原本的可见范围：

| 内容 | 可见范围 |
|---|---|
| 私聊里的话、agent 在私聊里的回复 | 这个人 |
| 群里 @ agent 的话、agent 对它们的普通回复 | 这个群的成员 |
| 用某个人的授权读到的东西（文档、私有仓库），**以及 agent 据此写的回复** | 这个人。回复虽然发在群里，往群外送时仍按这个人算 |
| 公开的东西（公开仓库、公开网页） | 所有人，但不可信 |

**一轮可以用的，是在它所在的地方本来就看得到的内容。** 往更宽的地方送东西（发到 GitHub）时：

1. 同一范围内的内容可以用，由提出的人负责。
2. 更窄范围的内容不能出去，包括上表第三行里 agent 的回复。
3. 不可信的内容不能左右动作。

第 2 条里"不同范围是不同的 Brain""用个人授权读的那一轮受规则限制并在结束后清掉"是已有的；"据此写的回复不继续外传"是新加的。

按这条规则，群里共用记录的做法大体保留，不需要按人切。#98 记下的那个限制分成两半：甲在群里说的话被乙要求写进 issue，不算外泄，要管的是"乙没让写、模型自己带进去了"，那是忠实于请求的问题（§3.5）；甲用授权读来的内容被乙带出去，是外泄，由新加的这一条挡。

### 2.4 怎么用程序保证丙

要求有三条：群里照常问答（乙可以追问甲那段摘要）；"把大家的讨论提个 issue"能做；受限的内容进不了往外发的那一步。只给受限的回复贴一个标记、指望模型不用它，满足不了第三条；看到受限内容就整轮禁止往外发，又让第二条经常做不了（窗口有 80 条，里面有一段摘要是常事）。

做法分两半，都建在已有的机制上，不为某一个工具单做。

**一、按轮记"受谁的限制"。** 不逐条消息追来源，记在轮上：

- 一轮用某个人的授权读过东西，这一轮受这个人的限制。
- 一轮看到的内容里（窗口、被引用的回复、读历史的结果）有受限的轮说的话，它继承那些限制。重述、摘要、交办说明因此都带着限制，跨轮、重放、恢复不会丢，因为记在库里（一张小表：轮、受限于哪些人）。
- 来源不明的旧回复（记了读过东西但没记为谁）算"受限、无人可放行"：群里照常看，往外不带。

**二、往外发之前，只重写还没发出的那一个动作。** 以某人名义往群外写的工具被调用时，如果这一轮受别人的限制：

- 这次调用不按模型给的正文执行。原请求、本人指定的目标、执行状态和这次操作的稳定编号都保留；只有正文用筛选过的材料重新生成。
- 重新生成是单独的一步，只给可外发的材料（人自己说的话，和不受别人限制的轮说过的话），不给发消息、起任务之类的工具。受限的内容原处留一句固定的说明。
- 提交前复核一次授权和目标。结果不明先核对回执，本人取消就停。
- 这一轮此前已经发生的事（发过的进度、建好的任务和定时器）不动，各只发生一次。v3 写的"清掉整轮重跑"做不到这一点（清理不会撤回已排队的消息和已建的任务，重跑的调用编号也会变），所以改掉。

它对所有"以本人名义往外写"的工具是同一条路，不为某个工具单做。平时多数轮不受限，不触发；触发时多一次模型调用。授权的本人自己明确要求把那段内容发到那个目标，不触发。

**限制要跟着真正被用到的材料走，不只跟着下一次模型输入。** 已有的工具回包、交办说明、任务结果、为延续请求保存的调用参数（恢复时会原样变成待执行的调用），保存和使用时都带着来源；证明不了来源的不用。是否"出圈"按实际投递的对象判断：另一个私有的目的地也可能是另一批读者。

**"已知没有受限来源"和"没记来源"要分开。** 旧记录里有据文档作答、来源却记成空的回复，不能把空当作"可以外发"。放宽记录范围之前写下的回复一律算来源不明。

**明确不做、作为已知限制的：** 人自己把那段内容重新讲一遍、手工粘贴或截图，没有可验证的来源关联，按这个人提供的群讨论算。不做语义溯源。

**沙箱交办同理：** 交办说明和摘录由这一轮写出，受同样的限制；"读得到"不等于"可以交出去"。恢复旧任务时如果旧快照里已经有受限的原文而资格已变，不用那份快照。

### 2.3 这条规则下还要注意的


- **有外部成员的群。** 群里的话对外部成员本来就可见，但"读群里没 @ agent 的消息"（§3.3）在这种群里风险不同。已有的以本人名义的工具每次都向平台确认群是内部群；读历史照此办理。
- **话题。** 同一个群的不同话题现在是不同的会话。它们对群成员同样可见，按规则可以互相读；第一版先只读本话题，保持简单。

## 3. 历史按需读（#100）

### 3.1 Brain 的读历史工具

一个工具，`read_history`。读的是**这个会话自己保存的记录中，窗口之外的部分**：别人写给 agent 的消息，和 agent 实际发出去的话。

参数照业界通行的形状（Slack 的 `conversations.history` 和 `assistant.search.context`、飞书的消息列表接口都是这几样）：

| 参数 | 含义 |
|---|---|
| `query` | 关键词，可空。按字面包含匹配，不做向量检索 |
| `from` | 只看某个人写的，可空 |
| `before` | 只看这个时间之前的，可空；翻页用 |
| `limit` | 条数，上限 30 |

返回每条的时间、谁写的（人还是 agent）、正文（过长截断并注明），以及还有没有更早的。

**它能返回什么，用的是窗口现在决定"给不给看正文"的同一套判断，不另写一套。** 具体说：

- 只返回这一轮在窗口里本来就有资格看到正文的那类内容。不是凭一个"是否私密"的标志判断：那个标志表示的是"正文要清掉"，拿它当可见范围会判错。
- 核对每条实际投递到了哪里。一个群任务也会产生只发给某一个人的通知；一条回复可能是从另一个话题转过来的。只发给个人的、别的话题的，不返回。
- 被撤回或改过的消息，按现在的版本，不返回旧的正文。
- 回复链上取来的别人的话（`quoted` / `chain`）有它自己的限制（是不是被点名、来源、层数），不摊平成可以搜的正文。
- 来自个人授权的回复（§2.2 表里第三行）返回时带着这个标记；这一轮如果是为别人行事，它们不作为往外送的材料。
- 每次查询明确限制在 30 天之内。现有的清理是按会话闲置和轮次数裁剪的，不等于"30 天后一定没有"，所以上限要在查询里写明。

**它不算"读了外部内容"**，但范围要说准：仅限于"同一可见范围、窗口本来就能给看的本地正文"。它不给后续的个人工具多开入口：`said` 里的 `reads` 和 `person` 现在还用来判断"原来那个人能不能再读一次来源"，这个判断不因为别人搜到了这条回复而改变。

要改的一处：现在 `said` 表只在私聊、以本人名义的一轮、接续请求的答复这三种情况下记录；群里不以任何人名义的一轮说的话只留在模型输出的记录里。放宽为：所有实际送达的、agent 自己写的话都记。

### 3.2 交办时附上一段原话，而不是让沙箱自己来读

v1 写的是沙箱里加一个读工具，经回调通道向 Brain 要对话。Codex 不同意，本文改从它的意见：**由 Brain 在交办时附上一段有界的摘录。**

理由：对话的内容一旦进了沙箱，承载它的不只是推送。模型请求、任务结果、日志、快照都会带着它；"推送要本人批准"只管得住推送，"Git 是只读的"也证明不了所有出站内容的去向。让沙箱随时来拉，等于把这些通道都对整段对话打开。

做法：

- `hand_over` 多一个可选的参数，指明要附上的几条消息（原请求点到的那些）。正文由程序从记录里原样取，不经模型转述，所以不会漏、不会改。
- 摘录有上限（条数和长度），并且绑定在这一次交办上：哪个租户、哪个话题、哪个任务、当时的可见范围、交办的时刻。
- 接着做、从快照恢复时重新核对一遍，不满足就不带。
- 摘录里别人的话和引文，对沙箱来说始终是材料，不是指令。
- 能附的范围和 §3.1 的工具能返回的范围相同。

沙箱发现缺了什么，可以在结果里说，由 Brain 再交办时补上。

### 3.3 群里没 @ agent 的消息（默认关闭，需要用户单独决定）

"群里刚才讨论的结论"这类问题，答案往往在没 @ agent 的消息里。要读它们，需要向平台要聊天记录。

- 连接器的 channel 增加可选的 `history`，和 `read_history` 同样的参数；没有它的连接器就只有 §3.1 的那部分。
- 各平台都把这个做成单独的、标为敏感的权限（Teams 的 `ChatMessage.Read.Chat`、Discord 的 `MESSAGE_CONTENT`、Slack 的 `*:history`）。飞书读群历史需要机器人在群里，并且需要"获取群组中所有消息"这项敏感权限。
- **所以它默认关闭**，需要部署者按应用打开，并且需要用户明确同意给应用加权限。
- 是按需读，不是全量接收：不订阅群里所有消息的事件，只在模型调用工具时按时间范围取一页。

Codex 指出、本文采纳的两点，比 v1 严：

- **"应用有权读"和"是内部群"都证明不了"提出的这个人有权看那条旧消息"。** 他可能是后来才进群的，消息可能已被撤回，可能本来就是只发给某个人的。要按提出人、话题、消息逐条核实；平台证明不了的，跳过。
- **读了没点名 agent 的群消息，这一轮进入只读。** 这些话不是写给 agent 的，不能由它们发起以个人名义的写。也就是说，这一部分**算**读了外部内容，沿用已有规则。§3.1 的"读完工具不受限"只适用于本地的那部分。

这一步的价值最大，但也最需要用户点头，所以单独列出，不和前面的步骤绑在一起。

### 3.4 默认上下文不变

最近 80 条的窗口平时保持原样。往外发之前重做的那一遍里，受别人限制的内容不给（§2.4）。

### 3.5 以本人名义写东西时带了谁的话

按 §2.2，这是忠实于请求的问题：

- 工具说明里已有的那句（只写这个人要求写的内容）保留。
- 评测加两组：乙说"把刚才的讨论提个 issue"，正文里有讨论的内容；乙说"把我说的这个问题提个 issue"，正文里没有甲的话。
- 不为此加程序上的隔离。如果评测显示模型经常带错，再考虑别的办法。

### 3.6 和已有东西的关系

- `said` 表：继续是"agent 说过什么"的出处，记录范围放宽（§3.1）。
- 回复链（`quoted` / `chain`）：不变。它解决的是"这条回复指的是哪条"，读历史解决的是"更早说过什么"。
- 记忆文件：不变。它存的是值得长期记住的事，不是聊天记录。
- 没有可以因此删掉的东西。

## 4. 用本人的 GitHub 权限跑沙箱任务（#95 的 B 部分）

### 4.1 已经设计过、已经定了的

`github-as-the-person.zh-CN.md` 在做 A 部分（以本人名义建 issue、评论，已上线）时，已经把 B 的方案和 Codex 定过，用户也定了"先 A 后 B"。这里只列结论，不重新设计：

- **凭据由 GitHub 连接器决定**（§3.4）。顺序：仓库自己的会话或绑定的群，用应用的安装令牌（现状）；否则，私聊、只有一个明确的提出人、他有有效的授权、通过租户边界的核对，用他的用户令牌；否则没有，只能读公开的。
- **不用限定单仓库的令牌**（§3.1）。按人保存一个通用的可续期令牌，留在授权对象里，不进容器；出口代理只给"任务所在的那个仓库"加凭据。这和业界最稳的做法一致（Claude Code 网页版：凭据不进虚拟机，由代理替换）。
- **租户的边界要另外核对**（§3.1.1）。只看"用户与应用的交集"不够；用之前先确认目标仓库属于当前租户名下的安装。
- **授权在启动沙箱之前要**（§3.4、§8.1）。走已有的"发卡片、授权完接着做"；在交办的那一步加一个内部操作"授权后交办原来那件任务"，原请求的编号作幂等键。取消或超时启动零个任务，重放只启动一个。运行中每次现取，不缓存。
- **只借给本人指过的仓库**；接着做和从快照恢复时都要复核。
- **第一版只在私聊里借，群里不借**（§3.5）。
- **撤销**（§3.8）：本人取消授权时，停掉正在用他的凭据跑的任务。
- **署名保持 agent**（§3.7），默认不加共同作者。

### 4.2 它和 §2 的关系

私有仓库的内容，可见范围是"这个人"。第一版只在私聊里借，结果、进度、审批问题都回到这个人的私聊：**没有流向更宽的地方**，所以不需要新的机制。

群里借个人凭据之所以难，正是因为群是更宽的范围：进度、快照、接续、审批都是群共用的。业界也没有哪家产品按读者的权限过滤线程里的输出，都是限制谁能发起，或者把个人权限的使用放到私聊。所以维持"群里不借"，不在这一版里解决。

### 4.3 还要做的

按依赖顺序：

1. **借凭据的判断挪进 GitHub 连接器。** 现在在沙箱任务对象里（`#lend`）。行为不变，只是换地方。
2. **任务知道是谁提出的。** 现在启动参数里没有提出人。加上，只用于向连接器要凭据。
3. **连接器的第三档**：按 4.1 的条件给出用户令牌。出口代理不变（它只管"给不给这个仓库加凭据"，不管凭据是哪种）。
4. **启动前授权**：交办私有仓库而本人还没授权时，走等待机制；授权后启动原来那件任务。先匿名探一下 git 端点，公开仓库不触发授权。
5. **接着做、快照恢复时复核**授权。
6. **撤销时停任务**。
7. **推送**：私聊里本人批准（已有的规则：私聊里是回复的那个人）。

### 4.4 实现前要实测的

- **用户令牌用于 HTTPS 的 git：有官方明文，不需要靠实测来确认可行。** GitHub 的文档明确写了安装令牌和用户访问令牌都可以用于 HTTPS 的 Git，需要相应的 Contents 权限，令牌作为 HTTP 密码使用（[Choosing permissions for Git access](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app#choosing-permissions-for-git-access)）。v1 说"没找到明文"是我查漏了。
- 对一个真实的私有仓库做一次只读的探测仍然值得做，但它验证的是**这个部署**（应用的设置、安装、令牌确实通），要事先得到本人同意。它验证不了推送时显示的推送者，也验证不了写权限。
- 检查结果的读权限要分三层说清：应用的设置里有没有（旧设计 §10 记着有 Checks 只读）、安装时实际授予了没有、我们发令牌时申请了没有（现在没有申请）。这不挡 B，但 #87 和 #110 需要，届时一并处理。

## 8. 验收

- 读历史：窗口之外的一条旧消息能按关键词、按人、按时间取到；取到之后工具不受限；别的会话、别的话题、只给个人看的内容、被清掉的轮次里读来的内容取不到。Codex 要求加的几种：只发给一个人的通知；被撤回的消息；从别的话题转过来的回复；两个人的消息指向同一条答复；一个一直活跃的会话在第 31 天。
- `said`：群里不以任何人名义的一轮说的话，之后读得到。
- #95B：私聊里对本人的私有仓库交办任务，没授权时发卡片、授权后启动一次且只启动一次；取消或超时不启动；令牌不出现在容器里；别的仓库拿不到凭据；仓库不在本租户的安装名下时不借；撤销后正在跑的任务停下；群里同样的请求不借。
- 忠实于请求：§3.5 的两组评测。
- 不继续外传：甲用授权读文档后 agent 答在群里；乙要求把它写进 issue，正文里没有那段，或者 agent 只问那一段能不能公开；甲自己要求时可以。

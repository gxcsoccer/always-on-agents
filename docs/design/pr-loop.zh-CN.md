# RFC：PR 的评审、跟进修复、审批，哪些值得做

状态：讨论稿 v1，待 Codex 讨论、待用户定夺。对应 issue #110；和 #87（替人盯着一件事）共用一部分基础，见 §5。

issue 问的是：能不能借鉴 Claude Ship "评审 → 修复返工 → 按规则审批"的做法。本文先看它实际是什么（§1），再看我们已经有什么（§2），然后逐段给出建议（§3、§4）。

## 1. Claude Ship 实际是什么

来自官方文档（逐页读过；发布文章本身只取到摘要）。

三个云端的组件，加一个本地命令：

| 组件 | 做什么 | 不做什么 |
|---|---|---|
| 代码评审（已正式发布） | 读 diff 和周边代码，发行内评论和一个检查项 | 只读；不推提交、不构建不运行代码；检查项从不以失败结束；自己不批准也不阻塞 |
| PR 跟进（测试版） | 为 CI 失败（原因在 PR 改的代码里时）、合并冲突、小的评审意见、评审的重要发现推提交；大的或设计层面的意见只回复不改 | 设计上不批准、不合并 |
| 审批（测试版） | 按策略文件报告"还差谁批"；策略允许时由它提交一个真的批准 | 不合并；条件里读不到 CI 结果 |

几点对我们有用的细节：

- **三者用的是同一个 GitHub App 身份。** 分权靠服务端强制，而不是三个身份：令牌留在沙箱外，`git` 和 `gh` 都过代理，代理直接拒绝"批准 PR、改分支保护和规则集、写检查结果、删分支、推标签"。
- **它自己承认有挡不死的地方。** 合并、开启自动合并、强推只靠权限规则加模型判断，文档原话是换个写法的命令可能两道都过；跟进组件还能推到别的分支。自托管时这些限制都不适用。
- **策略文件永远从默认分支读**，不读 PR 自己改的版本。策略文件、`CODEOWNERS`、`.gitattributes` 这类文件的改动必须有人批。没有内置的"风险等级"，低风险要自己用路径和条件拼出来；一条"它可以批"而不带任何评审条件的规则，等于没人看过就批准。
- **它明确警告**：策略里有"不需要人"的规则，再配上自动合并或合并队列，改动可以在没有任何人动手的情况下合进去。
- **谁能触发**：评论里下命令需要写权限；自动评审跳过草稿和 fork；跟进跳过草稿、fork、机器人开的 PR、没有写权限的作者。指令文件从默认分支读。
- **成本**：跟进没有修复次数的上限，靠每个 PR 的花费上限和月度上限；文档承认花费可能超过上限。

同类产品（官方文档）：评审普遍只评论；自动批准要么没有，要么默认关闭并带条件（CodeRabbit）；推修复的限定在一个分支上（Copilot 只推它自己的分支或已有的 PR 分支，Cursor 的自动修复最多三次）；发起人不能批准结果（Copilot）。GitHub 自己的规则：作者不能批准自己的 PR；可以要求"最近一次推送必须由推送者以外的人批准"。

## 2. 我们已经有什么

对当前代码（main `a83bbb5`）的核对。

### 2.1 评审：基本具备

- 在仓库的会话里 @ agent 让它评审，它把活交给沙箱（只读、不改不推），再用 `send_review` 发出：总结加行内评论，绑定到它评审的那个提交。PR 在此期间前进了，就改发普通评论并注明。
- **批准在代码里做不到**：发评审时事件类型写死为 `COMMENT`，模型没有可以改它的参数。
- 评审文字里的 `@名字` 被处理成不会通知人的写法。

缺的：

- **没有自动触发。** PR 打开、推送的事件会进来，但只作为信息；评审要人 @ 才做。
- **不能更新自己的评论。** 提示词里说"保持一条评论、更新而不是重复"，但代码里只有发、没有改。
- **收不到评审相关的事件。** 别人提交评审、行内评论的事件被丢弃，agent 看不到。
- **fork 没有专门处理。** PR 事件不看作者身份就接收；评论则只接收所有者、成员、协作者的。

### 2.2 修复：能推，但只能由人逐次批准

- 沙箱可以推到**同一仓库**的 PR 分支。每次推送都要等人批准。fork 的分支在别的仓库，推不了。
- 谁能批准：仓库会话里只有任务的提出人；一句 `approve all` 可以给这个任务后续对同样几个分支的推送一个长期批准（不含删除和标签，不被接续的任务继承）。
- **由事件或定时器起的任务没有提出人，它的推送谁也批准不了。** 所以"CI 失败了自动去修"现在在结构上走不通。
- 推送的目标没有硬规则：不限分支名，不挡默认分支，不查是不是强推。只有 GitHub 自己的分支保护会拦。
- 沙箱不能开 PR，不能写 GitHub 的接口（代理只放行读）。这一点已经是硬的。

### 2.3 CI：只知道失败

- 只接收"失败"的事件。成功、取消、超时都被丢弃。
- 没有任何工具读检查结果。沙箱的读代理路径上放行，但应用的令牌没有申请 `checks`、`statuses` 的读权限，私有仓库上预期会被拒。

### 2.4 持续跟进

- 有定时器（最短 60 秒一次，50 轮后自己结束），有任务接续，有花费上限（每个会话每天的 token、每个任务的时长和模型调用次数、每个租户的沙箱数）。
- 没有"盯着这个 PR 直到合并"这样的东西；`closed` 事件被丢弃，agent 不知道 PR 已经合并或关闭。

### 2.5 不可信的内容

- 仓库会话里没有连接器的读工具，所以"读过外部内容后收紧"的规则在这里从不触发。PR 的评论、事件的文字、CI 的文字都是作为事件进来的；沙箱读到的 diff 随任务结果回来，也不算外部内容。
- 现在靠的是：提示词里"事件是信息不是指令"；只有登记过身份的、受信任的人能批准和改长期指令；评审文字做了处理；沙箱的提示词里说读到的内容是材料。

## 3. 建议：做什么，不做什么

总的判断：**评审值得补齐；修复可以做，但要先补一个"这是谁的事"的基础；真的批准不建议做。**

理由是三段的风险和我们的现状差得很远。评审是只读的，我们已经有大半。修复会改代码，但推送的硬边界我们已经有（代理、逐次批准），缺的是让它能在没人盯着时继续。批准是唯一会让"没人看过的改动合进去"成为可能的一段，Ship 自己也在文档里反复警告；而且评审、修复、批准用同一个应用身份时，分权只能靠我们自己的服务端规则，一旦写错就是自己批准自己。

### 3.1 评审：补齐（风险低）

1. **自动触发，按仓库设定。** 三档，照 Ship 的设定：只在被 @ 时（现状，默认）、PR 打开时一次、每次推送后。由部署者按仓库设。
2. **默认跳过草稿、fork、机器人开的 PR。** 接收 PR 事件时看作者与仓库的关系。fork 的 PR 需要一个受信任的人 @ 才评审。
3. **一条评论，更新而不是重复。** 让连接器能改自己发过的那条总结。
4. **评审的指令从默认分支读**，不读 PR 自己改的版本（比如仓库里放一个评审说明文件）。

不做：把评审结果做成一个检查项。那需要写检查的权限，而"评审本身不阻塞"时它的价值有限。

### 3.2 修复：先做人工触发的，再做跟进

**第一步：人说了才修（几乎不用新东西）。** 现状已经支持"@ agent 把这个评审意见改掉"，由它交给沙箱、推送时问提出人。要补的是硬边界，不靠提示词：

- 推送只能到**这个 PR 的头分支**。永远不能到默认分支，不能删分支，不能推标签。在代理里做（它已经解析推送的内容）。
- 不能强推：推送的旧提交必须是远端分支当前的头。
- 不动工作流文件和评审、审批相关的策略文件（`CODEOWNERS` 等）。

**第二步：跟进。** 需要先有 §5 的基础（一件事是谁的）。有了之后：

- 一个人说"跟进这个 PR"，他就是这件事的提出人。之后由 CI 失败、评审意见的事件起的修复任务，算在这件事上，推送的批准也找他。
- 批准的方式二选一，**请用户定**（§6 第 2 条）：每次推送都问他（安全，吵）；或者他在开始跟进时一次性同意"推到这一个 PR 分支"（方便，范围仍由上面的硬边界限定）。
- 只为这几类起修复：CI 失败且原因在 PR 改的代码里；合并冲突；受信任的人提的小的评审意见。大的或设计层面的意见只回复不改。这是给模型的原则，不是代码里的分类器。
- **上限**：每个 PR 的修复次数（先定 5 次，Cursor 是 3 次，Ship 没有上限并为此提醒）、每个 PR 的花费上限、合并或关闭时结束、任何受信任的人说停就停。
- 跳过 fork（本来也推不了）和草稿。

### 3.3 审批：只做"报告"，不做真的批准

- **不让 agent 提交批准。** 现状是代码里做不到，建议保持。
- 可以做的是 Ship 的"观察模式"那一半：按仓库里的策略（`CODEOWNERS`、分支保护要求的批准数和检查），在 PR 上说明"还差谁批、还差哪些检查"。这是只读的，对人有用，也是以后如果要做真批准的前置。
- 如果以后要做真的批准，至少需要：单独的开关且默认关闭；策略只从默认分支读；agent 推过提交的 PR 永远不由它批准；策略文件和工作流的改动永远要人批；和自动合并同时开启时明确警告。这些留到那时再设计。

## 4. 不可信的内容

PR 是外面的人能写东西进来的地方。现状的防线（§2.5）对"只评论"够用，对"会推提交的跟进"要加：

- **谁的话能起修复**：只有受信任的人（所有者、成员、协作者）的评审意见和评论。其他人的文字只是材料。
- **CI 的日志是材料**，不是指令。修复任务的边界由代理的硬规则保证，不由"模型没被日志骗到"保证。
- **指令和策略从默认分支读。**
- 沙箱的出口不变：只通模型和 GitHub，写 GitHub 的接口一律不行。

## 5. 和 #87 共用的基础

#87（替人盯着一件事，条件满足时提醒人）和这里的"跟进"是同一种东西：**一个人提出一件要持续一段时间的事，之后由不是他发的消息（定时器到点、GitHub 的事件）来推动。**

三样基础是共用的，建议做成通用的，不为任何一个场景特化：

1. **一件事是谁的，随着它的每一步传下去。** #111 已经为定时器和任务做了这件事（提出人、他点名的人、在哪里）。把它扩到"等一个事件"：一个人让 agent 等某个 PR 上的事件，事件来了，那一轮知道这是谁的事。定时器是按时间触发的，这个是按事件触发的，两者是兄弟。
2. **读 PR 和 CI 的状态。** #87 需要 Brain 直接查（不起沙箱）；这里的"报告还差谁批"也需要。给应用的令牌加上检查和状态的只读权限，做一个范围级的只读工具。
3. **接收更多的事件。** PR 的关闭与合并、评审的提交、检查的成功。并且能送到提出要求的那个会话，而不只是仓库自己的会话。

所以建议的顺序是先做这三样，#87 和这里的跟进都建在上面。

## 6. 请用户定的

1. **范围。** 建议：评审补齐（§3.1）和人工触发的修复加硬边界（§3.2 第一步）先做；跟进（§3.2 第二步）等 §5 的基础；审批只做报告（§3.3）。是否同意，或者想先做哪一段。
2. **跟进时推送怎么批准**：每次都问，还是开始跟进时一次性同意推到那一个 PR 分支。
3. **要不要给 GitHub App 加检查和状态的只读权限。** 这需要在应用设置里改，并且已安装的仓库要重新同意。#87 也需要它。
4. **真的批准**：建议不做。是否同意。

## 7. 不做

- 不合并，不开启自动合并。
- 不做成 Ship 那样的三个独立产品和计费；这里是同一个 agent 的几种能力。
- 不为 fork 的 PR 推修复。
- 不做风险等级的分类器。

# 设计：追问就看历史，需要时再读原文

状态：草案，2026-11-23。方向由用户定下（见第 2 节）。待 Codex 评审。确认后取代契约 [agent-core-step0.zh-CN.md](agent-core-step0.zh-CN.md) 的决定 4 和第 5.2、5.3 节中关于追问的部分，以及第 2 步（`reopen_answer`）的全部内容。

---

## 1. 问题

第一次真实使用时：你先后发了 A、B 两篇文档请 agent 调研，它各回复了一份。随后你没有用"回复"功能，直接问了一个关于 A 的问题，结果接不上。

原因有两层：
1. **agent 不记得自己说过什么。** 读过文档的那次运行一结束，对话记录里除了你的原话，其余全部被替换成一句占位说明。
2. **追问只能走 `reopen_answer`。** 它是专门为追问做的受控重开：不用"回复"时，只认最后一份答复（B）；重开前必须先以你的身份重读原文成功。为了把它从"只认最后一份"放宽，前后讨论过的方案（契约 2a、两版设计稿）每一版都要再加一层机制：标题核对、选择模式、运行时代问、内部交接、逐篇权限核对，越来越重。

## 2. 用户的决定（2026-11-23）

- 从使用者的直觉出发：**追问就应该读历史记录**。agent 发给你的回复就是对话的一部分。
- 只有新问题需要更多信息时，才由 agent 决定是否重读原文、挖掘更多内容。
- 历史里带着文档内容的回复，**不连带限制**之后的运行：之后的运行如果没有读原文，照常可以写记忆、派任务。
- 追问专用的那整套机制**删掉**。

## 3. 方案

### 3.1 保留 agent 真正发出去的话，只清原文

**清理照旧**：读过外部内容的运行结束时（`Runner#forgetOutside`），工具返回的原文、模型中间的推理、工具调用和工具输出，照旧替换成一条固定的占位说明。

**新增一张"已送达"小表 `said`**（PR 2 的迁移）：
- **列**：`outbox_id`（主键）、`run_id`、`session_id`、`text`、`sent_at`、`receipt_subject`（渠道里这条消息的标识）、`reads`（这条消息写出时，这次运行已经成功读过的文档）。
- **`reads` 怎么来**：模型调用 `send_message` 写入发件箱时，把这次运行到这一刻为止成功读过的文档一并记在发件箱这一行上，送达时随正文一起写进 `said`。先根据历史回答 A、再读 B、再回答 B 的运行里，第一条的 `reads` 是空的，第二条是 B。
- **只记这几类**：确认送达、纯文字、发往这个私聊的助手消息。卡片、系统固定通知、审批问题都不记。
- **写入时机**：发件箱确认送达的同一个事务里（`Outbox#attempt` 写 `sent` 的那一步），在清空发件箱正文之前。
- **写入内容**：发件箱这一行**最终发出去的正文**，不是模型某一次调用的参数。被拒绝的调用、被改写掉的草稿、最终失败的消息，都不会进这张表。
- **重复确认**：同一个 `outbox_id` 只写一次。

**组装输入时**（`#transcript`），把每次运行送达过的话放回它那一轮：
- 在这次运行的占位说明后面，按 `outbox_id` 顺序插入这次运行 `said` 里的每一条，作为助手消息。
- 送达确认可以发生在清理之前，也可以在之后，结果都一样，因为是组装时才去查。
- 不追加到对话末尾，所以正在进行或暂停中的运行不受影响。
- 远端已接收、本地还没记下就崩溃了：表里没有这一条，就不出现。只按确认过的来。

**"读过哪篇"的记录**：
- 运行结束时，把这次**成功读取**的文档，以结构化形式写进占位说明那一条（字段 `reads`），同时以固定格式的文字给模型看："（这次读过：<链接>；原文没有保留，需要时可以重读）"。
- 链接取你当初发的那条消息里的原始链接，去掉查询参数，知识库链接保留原路径。
- 读取失败、被拒、在等待、只是提议过的，都不记。

**窗口按看得见的条数算**：
- 现在 `#transcript` 用"最大序号减 79"来定起点，清理留下的空洞也被算了进去，实际看到的远少于 80 条。改为：从最新往前数 80 条真实存在的条目（`said` 插入的也算）。
- 起点仍然对齐到用户那一轮的开头，正在进行的那一轮保持完整。

**保存期限**：
- `said` 随对话记录一起清理：每日清理删掉某次运行的对话条目时，同一事务里删掉这次运行的 `said`。
- `said` 和发件箱的保存期限互不相干：发件箱记录 30 天后删掉，不影响 `said`。

**发件箱照旧**：读过外部内容的运行写出的消息，送达后在发件箱里清空正文，出错日志照旧脱敏。正文现在只存在 `said` 里。

### 3.2 追问：模型看历史作答，需要时自己决定重读

- 追问时，模型在对话记录里能看到它对 A、B 的两份回复，以及当时读过哪篇，直接据此作答，不读任何文档。
- 新问题超出了回复里的内容，就由模型决定重读哪篇。重读还是用现有的读文档工具，以你的身份、用你的权限，和第一次读一样：要授权时照常进入等待，授权后续办。
- **读文档工具能读哪些链接**：
  - **这次请求里你贴的链接**：不变。
  - **用"回复"指着你自己某条消息**：精确绑定到那条消息里的链接，不受时间和条数限制。不变。
  - **新增**：这个私聊里你本人 24 小时内、最多 50 条普通消息里的链接。判断标准和现在"你本人发的"一样：同一个应用、租户、私聊，你本人直接发的普通消息，早于这次请求。链接取连接器在收消息时提取的 `documents`，不从对话记录、助手回复、"读过哪篇"的记录或文档原文里取。
  - 模型给出的链接只是提议，按文档类型和编号去和上面的范围比对，在范围内才读。不再退回"最近的那一个"；不在范围内就报错，让模型问你要链接。
  - 删掉现在"刚贴的那篇只能这样读一次"的限制（`carriedFrom`/`answered`）。它是为旧的"最近一个链接"规则设的，现在对 A 连着问几次都应该能读。
- **回复的是 agent 的某条答复**（比如读完 B 之后，回复 A 的那份总结，问一个新细节）：用 `said` 精确对上。
  - 你回复的那条消息的标识，对应到 `said.receipt_subject`，并核对它属于这个私聊，由此拿到**那一条**的 `reads`。不经过运行、也不看发件箱，所以运行和发件箱记录清理之后照样能对上。
  - **告诉模型的内容**：现在只告诉它被回复的那条消息的发送时间。改为在你那条消息上只存一个指向 `said` 的引用，组装输入时再取出那条送达的原文，作为助手说过的话交给模型。这样不会重复存一份正文，也不会延长它的保存期。如果 `reads` 唯一、核对过、在范围内，还会把那个链接一并告诉模型，即使原来那一轮和你当初贴的链接都已经滑出窗口。原文已经被清理掉的，就只告诉发送时间，和现在一样。
  - **能读的文档**：收窄到那一条的 `reads` 和你本人消息可读范围的交集。A 唯一且在范围内，就只能读 A；模型提议读 B 会被拒绝。`reads` 为空（那条是根据历史回答的），就不自动认定任何一篇。（2026-11-24 起：这种答复不指向任何文档，回复它按普通追问处理，可以读你本人一天之内贴过的链接，由模型说明是哪一篇；不保证是你最初问的那一篇。见 PR #46。）
  - 只需要根据那份答复回答的，不读任何东西。
  - 需要重读、但对不上出处、对上不止一篇、或者超出了 24 小时范围的，问你要链接。
- **授权等待**：照现有做法，等待时把这次依据的你的消息编号和选定的链接存下来，续办时按存下的依据来，不重新在 50 条里搜，不会换成 B。连接器里核对授权实时状态和版本的逻辑（`grant.finish`）保留。

### 3.3 运行级的限制保持不变，但不往后传

- 一次运行**这次真的读了原文**：这次运行里不能写记忆、不能派任务，只能回复你、或者继续读。这和现在一样。
- 输入里有 `said` 插回的、带文档内容的话：**不算**读过外部内容，之后的运行不受限制。这是用户的决定。

## 4. 为什么这样仍然安全

| 关注点 | 怎么处理 |
|---|---|
| 读别人的文档 | 不变：始终以你本人的身份、用你的权限读；只在你本人发话的私聊里提供工具 |
| 读到不该读的文档 | 能读的只有你本人在这个私聊里发过的链接；模型不能凭自己写出的、或从文档里读到的链接去读 |
| 文档里藏的指令 | 读原文的那次运行里，不能写记忆、不能派任务；原文不留在对话记录里。回复会保留，这是用户接受的取舍 |
| 发给别人 | 不变：只发回这个私聊 |
| 权限收回 | 不再读那篇文档；但已经说过的话仍可能被引用。这是用户接受的取舍 |

## 6. 测试

**PR 2、PR 3，先写，在现在的代码上应当失败**。断言下一次真正交给模型的输入，以及真正提交给渠道的文字：
1. **只保留送达的话**：
   - 读过文档的运行结束后，送达的回复出现在下一次输入里，位置在它那一轮；
   - 原文、工具输出、模型中间步骤都不在；
   - 被守卫拦下、作废、放弃、无法确认的消息，从不出现；
   - 续办的草稿被改写过时，只出现最后送达的那一版；
   - 一次运行发了几条、结果有成有败：只有送达的几条，按顺序出现；
   - 重复确认、重启之后，每条送达的消息只出现一次；
   - 回执在下一次运行已经暂停时才到：之后的输入里出现在原来那一轮的位置，不打乱正在暂停的运行；
   - 远端已接收、本地还没记下就崩溃：不出现。
2. **"读过哪篇"**：只有成功读取的才记；链接是你当初发的原始链接；失败、被拒、等待中的不记。
3. **不连带限制**：之后只看历史的运行，可以写记忆，也可以派任务；这一次读了原文的运行，仍然都不能做。
4. **答复和出处按写出那一刻对应**：同一次运行先根据历史回答 A、再读 B、再回答 B，A、B 的链接都在范围内；你回复第一条答复：不自动读 B，B 读取 0 次。
5. **回复的答复已经滑出窗口**：
   - 一条不带链接的答复，在 80 条可见范围之外，你回复它：输入里有它的原文和核对过的 A 的链接；你这条消息本身存的只是引用，不是原文；
   - 另一个私聊里的同一个标识：对不上；
   - 原来的对话记录已经被清理：只告诉发送时间。
6. **回复 agent 的答复**：A、B 都在 24 小时范围内，A 那一轮已经滑出窗口，你回复 A 的总结，模型被脚本强行提议读 B：读 B 0 次，可以读 A；交给模型的输入里有 A 那份送达的原文。
7. **送达的原文是权威的**：
   - 续办运行里先发了合格的草稿 A，后来改写的草稿 B 因超长被拒：历史里只有 A；
   - 改写成功的：历史里只有改写后的那一版；
   - 送达确认在清理之前或之后发生：结果相同。
8. **窗口和保存期限**：
   - 清理后留下空洞的历史（序号 1、28、29、84、85 处各有一条），问 A 的那一轮仍在模型输入里；
   - 发件箱记录过了 30 天被删掉之后，送达的话仍在；每日清理删掉对话条目时，`said` 一起删掉。
9. **读文档的范围**：
   - 你本人 24 小时内、50 条以内发过的链接可以读，边界之外的不能读；
   - 只出现在文档原文、助手回复或模型参数里的链接，不能读；
   - 用"回复"指着你自己的消息时，超过 24 小时也能读那条里的链接；
   - 对 A 连续追问几次，每次都能读 A。
10. **端到端**：
   - 先后读 A、B，然后问一个关于 A 的问题：飞书读取 0 次，据历史作答；
   - 再问一个回复里没有的细节：只重读 A 一次；
   - 读完 B 之后回复 A 的那份总结问细节：读的是 A；
   - 跨越 24 小时边界的真实授权等待：续办时读的还是原来选定的那篇。

**PR 1**：删除之后全部现有测试（去掉追问专用的那些）通过。迁移的测试数据包括：旧的 `reopen_answer` 续办、还没执行的 `reopen_answer` 调用、带期限守卫的待发消息、answers 记录。迁移要运行干净、结局如实；已经尝试发送但结果不明的，保留"无法确认"，不重发，也不记成"从未发送"。

## 7. 要写明的两点

- **80 条是模型每次看的窗口，不是保存期限。** 送达的话存在 `said` 里，和对话记录一起按现有的每日清理规则删除。对话长了之后它们会滑出模型能看到的窗口，届时模型只能重读原文；你用"回复"指着它时，那条原文仍会交给模型。
- **允许的记忆和任务可能带上私聊回复里的话。** 之后的运行不受限制，所以模型写进记忆或派给任务的内容，可能包含它在私聊里说过的、来自文档的话。这是"不连带限制"这个决定的直接后果。私聊送达的承诺只描述那条回复本身发到哪里。

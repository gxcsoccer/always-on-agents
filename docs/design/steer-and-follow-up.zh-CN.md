# 设计：工作还在进行时，新来的话怎么办

状态：草案（v3），2026-11-26。已与 Codex 评审一轮并按意见修订（见 §11），尚未实现。

这份文档回答一个问题：一件交给 worker 的工作还没做完，同一个人又说了一句话，系统应该怎么处理。

---

## 1. 现状

Brain 这一层已经有答案：对话走"推到下一轮"，连发的几条合成一轮（见 `src/brain/runner.ts` 的 `#batch`）。Brain 自己不会被 worker 堵住，新消息来了立刻起一轮。

worker 这一层缺两种处理。一件沙箱任务在跑的时候，模型能做的只有：

| 能做的 | 工具 |
|---|---|
| 直接回答（问进度、问别的） | `work_status`、`send_message` |
| 并行另起一件，互不相干 | `hand_over(continue_from: null)` |
| 停掉 | `cancel_work` |

想"接着正在跑的那件做"会被拒绝（`Tasks.dispatch`：`has not ended yet`）；想往正在跑的任务里加一句话，没有任何通道。

后果是真实使用里会见到的：对同一件事的补充，要么让人等，要么另起一件从头克隆的任务，两件各改各的，互相看不到。

## 2. 用词

行业里这几个动作的叫法基本一致，本文沿用，不另造词：

| 叫法 | 含义 | 出处 |
|---|---|---|
| **steer** | 把话送进正在跑的那一轮；agent 在下一个安全点读到；不中止正在执行的动作，不另起一轮 | pi 的 `steer` 命令、OpenClaw 的 `steer` 模式、Kiro、Copilot SDK |
| **follow-up**（queue） | 等当前这件做完，再作为下一件处理 | pi 的 `follow_up`、OpenClaw 的 `followup` |
| **collect** | 等当前这轮做完，把攒下的几条合成一轮 | OpenClaw 的 `collect`；Anthropic 文章里的 "merge them into a single run" |
| **interrupt** | 中止当前这件，改做最新的这句 | OpenClaw 的 `interrupt` |

Anthropic《Building always-on agents》对运行中来的事件只说了一句："push it to the next run, fold it into the current run, or interrupt and restart"，没有给选择建议，也没有讲后台任务。本文把这三种落到 worker 这一层。

"merge" 一词在业内指 collect（连发合一轮），不指 steer。本文不用它称呼 steer。

## 3. 设计原则

1. **由模型选，代码只保下限。** 新来的话属于哪一种，是判断题，不是规则题。代码保证的是：谁能这么做、做了之后状态是准的、做不成时说清楚为什么。
2. **写在 worker 契约上，不写在沙箱上。** 能不能 steer、能不能排在后面，是 worker 自己声明的能力；Brain 的校验对所有 worker 一样。
3. **复用已有的东西。** follow-up 复用任务接续（`continue_from`、`task_follows`、快照）；steer 复用沙箱里已有的扩展和它回调任务的通道。不引入新的进程模型。
4. **做不成不静默降级。** steer 送不到（任务已结束）就告诉模型，由它改走接续；不在代码里偷偷换一种处理。

## 4. 五种处理

| 意图 | 处理 | 工具 | 结果怎么回来 | 状态 |
|---|---|---|---|---|
| 无关的新事 | **new**：并行另起一件 | `hand_over(continue_from: null)` | 各回各的 | 已有 |
| 不要了 | **cancel** | `cancel_work` | 回一句已停 | 已有 |
| 现在就告诉它 | **steer**：送进正在跑的那件 | `tell_work(work_id, message)`（新） | 只回一次结果，含补充的内容 | 本文 |
| 做完再接着做 | **follow-up**：排在后面，前一件成功后从它留下的工作区启动 | `hand_over(continue_from: <在跑的那件>)` | 两件各回一次 | 本文 |
| 方向错了，停下改做这个 | **interrupt** | 见 §7 | — | 本文不做，留接口 |

collect 属于 Brain 这层，已经有，不在本文范围。

模型怎么选，写进部署的指引（`src/workers.md`），由评测盯住（§8）：

- 补充细节、纠正还没做到的部分 → steer。
- "做完之后再……"、明显是下一步 → follow-up。
- 和那件事无关 → new。
- 分不清指的是哪一件 → 问。

## 5. follow-up：排在一件没做完的工作后面

### 5.1 行为

`hand_over` 的 `continue_from` 指向一件**还没结束**的工作时，不再拒绝，而是写下一件新的任务，状态为 `queued`：

- 不占租户的沙箱名额，不启动 worker。
- 记入 `task_follows`（已有的表），与任务同一处写入。
- 可以被 `cancel_work` 取消，在工作列表里显示为"排在 <前一件> 之后"。上限见 5.3。
- 工具当场回给模型 `status: "queued"`，模型据此告诉对方"等那件做完后接着做"。

前一件结束时（`Tasks.event` 收到它的终态汇报）：

| 前一件怎么结束 | 排队的那件 |
|---|---|
| succeeded | 转为 `dispatching` 并启动，走现有的接续路径（worker 向前一件要快照） |
| failed / lost / cancelled | 不启动；记为 failed，原因写明"它要接着做的那件没有做成"，并叫醒一轮，由模型告诉对方、由对方决定 |

排队的那件启动被 worker 拒绝（比如前一件没能留下快照）同样记 failed 并叫醒一轮。

**谁来启动。** 不由模型在"前一件做完"的那一轮里重新交办：排队的那件在写下时已经固定了交办人、worker、options、bounds，系统启动的就是这个已经校验过的编号。也不只靠前一件的终态汇报：本地取消、判定丢失、启动被拒这些结束方式没有那一声汇报。所以由 `settle`（已有的定时收拾）按持久的前一件状态去拾取排队的任务，`event` 只负责让它尽快醒来。前一件没做成时，排在它后面的一串逐级结束。

**取消与启动交错。** 取消一件排队的任务是本地一步完成的，不去停一个还没启动的 worker。"转为启动"和"取消"都用带条件的状态转换，跨过 RPC 之后再看一眼状态。

**一条线，不分叉。** A 在跑，B 和 C 都说接着 A，会从 A 的同一份快照各开一份，C 看不到 B 的改动。人说"做完再……"时想的是依次做，所以：一件工作后面最多排一件；再来一件，接在队尾那件后面。工作列表里写明每件排在谁后面，模型据此把 `continue_from` 指向队尾；指向已经有后续的那件会被拒绝，并告诉它队尾是哪件。不做通用的队列调度。

### 5.2 校验

与现有接续完全相同，在写入之前做：worker 声明了 `goes_on`；前一件在本会话、是同一个 worker 的、由同一个唯一明确的交办人交办；本轮是那个人自己的一轮。

区别只有一条：前一件的状态允许是进行中（`dispatching | unconfirmed | running | needs_input | queued`），不再要求 succeeded。因此可以排成一串（一条线，见 5.1）。

排队的那件不继承前一件的长期批准，和现有接续一样。

### 5.3 时限与名额

`created_at` 不动，它是交办时间，状态接口、列表排序、审批历史的查询下界都在用。另记一个"开始尝试启动"的时间，只记一次；`accept_by` 和看门狗以它为准，重试不续命。bounds 仍是写下时固定的那一份（`task_bounds`）。

**租户名额。** 启动时才申请。前一件的终态先提交、名额后释放，排队的那件如果抢先申请会碰上"满"。排队是已经答应了人的事，不能因此记失败：名额暂时满时它保持 `queued`，由 `settle` 用同一个编号有界重试；只有"这里根本不许有任务"才是失败。

**两个上限分开。** 同时在跑的件数（`scope_active_tasks`）和在排队的件数是两回事。排队的不算进前者，否则上限设成 1 时一件都排不进去。排队的件数另有一个小的固定上限。

**排队的期限。** 排队超过前一件的寿命上限加一个余量仍没轮到，由 `settle` 记为 failed 并叫醒一轮。

### 5.4 需要存的

- `tasks.status` 多一个值 `queued`。
- 启动时要用的 options 和"开始尝试启动"的时间（一张自己的小表 `task_queued(task_id, options, started_at)`；用独立的表是为了迁移可以重放）。
- 其余复用现有的 `task_follows`、`op_id`、`task_bounds` 和 alarm。

### 5.5 取舍：另起一件，还是让同一件接着干

pi 自带 `follow_up`：同一个进程做完当前的再处理下一句，不用恢复工作区。没有选它，理由：

- 第一件的结果应当先回给人。同一个进程接着干，结果只在最后回一次。
- 寿命、模型调用次数、审批各算各的，不串。
- 对不是 pi 的 worker 也成立：契约上只要求"能从前一件留下的东西接着做"。

代价是多一次恢复工作区（实测几秒）。

## 6. steer：把话送进正在跑的工作

### 6.1 契约

`Worker` 增加一项可选能力：

```ts
/**
 * 把一句话交给一件正在进行的工作。worker 说清楚结果：
 * taken 表示它收下了，会在下一个安全点交给 agent（收下不等于已经读到，见 6.4）；
 * closed 表示这一轮不再收话。抛错表示不知道有没有收下。
 */
tell?(env, id, note: { id: string; text: string }): Promise<{ state: "taken" } | { state: "closed" }>;
```

`note.id` 是 Brain 那次工具调用的编号：同一个编号再送一次，得到同一个结果，不会存两遍。`closed` 表示这一轮不再收话（已经结束，或者已经过了最后一次取的时机），不等于任务已经有了结果。

没有这一项的 worker 不能被 steer，工具说明里告诉模型哪些可以。

### 6.2 Brain

新工具 `tell_work(work_id, message)`。校验在调用 worker 之前：

- 那件工作在本会话、由同一个唯一明确的交办人交办、本轮是那个人自己的一轮（与接续同一条规则）。
- 状态是 `running` 或 `needs_input`。`queued` 的还没开始，不 steer：改它的 brief 不在本文范围，模型应取消后重新交办。`dispatching` / `unconfirmed` 的回"还没确认开始，稍后再试"。
- worker 有 `tell`。

结果：

- `taken` → 记一条审计（`task.told`，只记任务编号和长度，不记内容），回给模型"已收下，它做完手上这一步会看到"。
- `closed` → 回给模型"这一轮不再收话了；可以排在它后面接着做"，不自动转成 follow-up。

**那件正等着批准时。** 话是"先别推"这类：送进下一步撤不回一个正在等批准或已经发出的动作。这时该做的是对那个待批准的操作走现有的拒绝，或取消任务。指引里写明，工具回执里也在任务处于 `needs_input` 时提醒这一点。

### 6.3 沙箱

**任务侧**（`TaskSandbox`）：

- 新 RPC `tell(note)`：这一轮还在收话时把 `{ id, text, at, round }` 追加到 `state.notes`（上限若干条、每条限长；超出则拒绝并说明），返回 `taken`；否则返回 `closed`。重复的 `id` 不再追加，返回当初的结果。`round` 是任务当前的执行轮次（已有的 `runs.length:recoveries`），恢复前后的回执因此分得开。
- `callback("notes", { final })`：扩展来取。返回还没交出去的 notes。`final` 为真且没有可交的，就在同一步里**关闭这一轮的收话**（同步的存储操作，取与关之间插不进一次 `tell`）。此后的 `tell` 得到 `closed`。

**容器侧**（`container/gate.ts`，已有的扩展，它已经在用 `http://brain.internal/callback/<kind>` 回调任务）：

- 在 `turn_end`（一步的工具调用都执行完之后）取一次 notes；有就投递。
- 在 `agent_before_settle`（agent 准备结束前）带 `final` 再取一次；有就投递，agent 会多走一步读到它，然后这个 hook 会再来一次，直到取不到并关闭收话。
- 取的请求有短超时，超时不挡住任务正常进行；没交出去的留给下一次。
- 投递的文字带固定的前言，说明这是交办人在工作进行中补充的话。
- 不凭 `context.canContinue` 决定取不取（实测正常结束时它也可能是 false）。模型调用出错的那一轮不投递（实测出错时 hook 也会触发，盲投只会再发一次请求）。

投递用哪种方式在实现时二选一，都已在 pi 0.87.1 上实测可行（见 §11）：`pi.sendUserMessage(text, { deliverAs: "steer" })`，或者在这两个 hook 里返回一条 `custom_message`（`details` 里带 note 的编号）。后者把编号写进了 session，恢复后能从 session 判断这句话在不在里面，倾向用它。

选扩展而不是把 pi 改成 RPC 模式（`--mode rpc` 的 `steer` 命令），因为现在是一次性进程加文件收尾的模型，检查点、恢复、看门狗都建在上面；换成长驻的 RPC 进程是另一件大事，本文不碰。

### 6.4 "收下"不等于"读到"

`taken` 只表示任务存下了这句话。它被 agent 读到，要等下一个 `turn_end`。两者之间可能发生：

| 情况 | 处理 |
|---|---|
| agent 正卡在一个长命令或等审批上 | 命令结束或审批答复后的那一步读到。对人说的是"已告诉它，它做完手上这一步会看到" |
| 话到的时候已经过了最后一次取 | 收话已关闭，`tell` 直接得到 `closed`，模型当场知道，可以排在后面接着做。不会出现"收下了却没人读" |
| 交出去了，但那一步模型调用失败、任务以失败结束 | 结果里列明哪些话交出去了但任务没有做成；不把"交出去"说成"处理了" |
| 容器丢了，从检查点恢复 | notes 存在任务状态里，不在容器里。恢复之后以**恢复出来的 session** 为准：里面有这句话的编号，就是读到过，不再投；没有，就是恢复出来的这个 agent 没读过，照常在下一步投递。没交出去的同样照常投递。见 6.5 |

### 6.5 送达的语义：至少一次，按编号去重

这是可恢复执行的通行做法（Temporal、LangGraph、AWS durable execution 的文档都是这个说法；Anthropic 的文章里"收件箱是事实来源，worker 崩了由新的 worker 重试事件"也是同一思路）："恰好一次"不是传输能给的，是"至少送达一次"加"接收方按编号去重"拼出来的；只有做不成幂等的动作才退到"最多一次、失败了让人处理"。

落到这里：

- **每句话有编号**（Brain 那次工具调用的编号），从 `tell` 到投进 session 一路带着。
- **接收方的状态就是 session**。投递时把编号写进 session（`custom_message` 的 `details`）。判断一句话读没读到，只看 agent 当前这份 session 里有没有它的编号，不看任务状态里记的"交出去过"，也不看哪次备份在它之后完成。
- **恢复后**：扩展启动时读一遍 session 里已有的编号报给任务；任务把不在其中的、本应已经交出去的 notes 重新标为待投。于是恢复出来的 agent 没读过的话会再投一次，读过的不会。
- **同一份 session 里不会出现两次同一个编号**：扩展投递前先查，任务侧 `tell` 也按编号去重。

重投会不会让 agent 把一个外部动作做两遍：会不会重做，取决于检查点，不取决于这句话。容器恢复后 agent 本来就可能重做检查点之后的那几步，现有的恢复提示已经告诉它"最后几步可能丢了，先看当前状态再继续"。防重复要落在动作本身：同一个提交再推一次没有效果，推送还要过审批（单次批准绑定在具体的前后提交上）。不靠"少送一句话"来防。

### 6.6 取舍：审批

"只有当初交办的那个人能 steer"是对**谁在说话**的校验，不是一次新的批准。steer 不给任务增加任何它原来没有的许可，也不清掉已有的：

- 单次批准本来就绑定在具体的仓库、分支和前后提交上；长期批准限于原任务、原仓库、已批准分支上的非删除更新。这些限制不因 steer 改变，所以不必一律重新审批。
- 补充的话要求的动作超出这些范围时，照原规则重新问人。
- 排在后面的那件（follow-up）不继承长期批准。

## 7. interrupt：本文不做

"停下，改做这个"现在要两步：`cancel_work` 再 `hand_over`，而且被取消的任务不留快照，已做的部分丢掉。

要做成一步，需要取消时也拍一份快照（现在只有成功结束才拍），再允许接着一件被取消的任务。这改的是"什么样的结束可以被接着做"，影响比前两项大，单独立项。本文不为它预留接口。

在那之前，纠正方向用 steer（"别做 A 了，改做 B"）。agent 在下一步之前读到，已经做的不会回滚。

## 8. 评测

`eval/cases.ts` 增加一组，工作列表里有一件在跑的沙箱任务：

| 场景 | 期望 |
|---|---|
| "顺便把 xx 也改了" | `tell_work` 那件 |
| "等它改完再把单测补上" | `hand_over(continue_from: 那件)` |
| 那件后面已经排了一件，"之后再把文档也更新了" | `hand_over(continue_from: 队尾那件)` |
| 那件正等着批准推送，"先别推" | 拒绝那次批准或取消，不是 `tell_work` |
| "另外帮我看下 <别的仓库>" | `hand_over(continue_from: null)` |
| "算了不用做了" | `cancel_work` |
| "做得怎么样了" | `work_status` 或直接答 |
| 两件都在跑，"把那个也改了"分不清 | 问 |
| `tell_work` 回 closed | 告诉对方没送到，可以排在后面接着做；不假装送到了 |

（沙箱不能开 PR，用例里不出现"提 PR"，免得奖励错的路由。）

代码测试里优先验收的时序：名额只有一个时的排队与启动；前一件被本地取消或判丢失；取消排队的那件与它被启动交错；终态汇报重复、重启之后仍只启动一次；最后一次取与新来的 `tell` 交错；收下之后容器丢失；补充的话不能扩大原有批准。

## 9. 实施顺序

1. **follow-up**：只动 Brain（`tasks.ts`、`schema.ts`、`runner.ts` 的工作列表、工具说明）。不动沙箱镜像。
2. **steer**：契约、`tell_work`、`TaskSandbox.tell`、`gate.ts`。要重建镜像；部署后必须在真实容器上实测一次（只有那里能证明话真的到了 agent）。
3. **指引与评测**：`src/workers.md` 和上面那组用例，对真实模型跑。

每步一个 PR，测试先行。

## 10. 已经定的

1. **排队是一条线，不分叉**（5.1）。与业界一致：OpenClaw 每个会话一条车道、按先后排；pi 的 follow-up 是先进先出的队列。分叉在这些工具里都是单独的显式操作，不会因为两句话提到同一件任务就发生。
2. **恢复后按编号去重重投**（6.4、6.5）。v2 选的是"不自动重投、如实告知"，v3 改了：恢复出来的 session 里没有这句话，就是没读过，不投就丢了。

## 11. 评审记录

Codex 评审 v1（`4fb1d84`）的结论：方向可以落；不需要换成 pi 的 RPC 模式，也不需要预留 interrupt 的接口；先把交付语义写清再实现。v2 按它的意见改了：

- **实测了投递时机**（pi 0.87.1，`--mode json`，固定回放的本地 provider）：`turn_end` 和 `agent_before_settle` 都会触发；在任一处投递，下一次模型请求里恰好多出这一条；`agent_before_settle` 投递后不用返回 `continue` 也会再走一步，返回了也不会多走；工具调用之后的 `turn_end` 投递，紧接着的请求就能看到。最后只有一次 `agent_settled`。两条边界：正常结束时 `canContinue` 也可能是 false；provider 报错时 hook 照样触发。**没有测**：Cloudflare 上的镜像、真实模型、容器恢复。
- 排队时碰上租户名额暂时满，不记失败，保持排队有界重试；排队件数与并发件数分开（5.3）。
- 不重置 `created_at`，另记启动时间（5.3）。
- 由 `settle` 按持久状态拾取，不只靠终态汇报；取消与启动用条件转换（5.1）。
- 一条线，不分叉（5.1）。
- `tell` 带编号、幂等；最后一次取与关闭收话原子完成；`ended` 改为 `closed`（6.1–6.3）。
- 恢复后的重投：v2 取了保守的一支（不自动重投），v3 改为它给出的另一支：编号随消息写进 session，按恢复出的那份 session 判断（6.5）。
- 审批：作者校验不是批准；任务等批准时的"先别推"走拒绝或取消（6.2、6.6）。
- 评测里去掉"提 PR"，补了时序验收清单（§8）。

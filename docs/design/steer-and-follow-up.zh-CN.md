# 设计：工作还在进行时，新来的话怎么办

状态：已实现并上线（2026-11-26）。follow-up 见 PR #88，steer 见 PR #89；实现与本文不同的地方见 §10.1，行为以代码和 `docs/workers.md` 为准。

上线后的验证（线上版本 `1d0542b6`，飞书私聊里连发三条）：交办一件先 `sleep 60` 再改 README 的任务；运行中更正要写的内容，记为 `task.told`，沙箱里的扩展在第一步结束时取到这句话，任务按更正写入并标记该句已读；运行中再说"做完之后再加一行"，记为 `queued`，第一件成功后二十多秒由 Brain 自己启动，在前一件留下的工作区里接着做，没有重新克隆。本地用真实的运行时、容器、出口代理和模型也跑过同样的链路（`eval/lab/worker-entry.ts`）。

这份文档回答一个问题：一件交给 worker 的工作还没做完，同一个人又说了一句话，系统应该怎么处理。

---

## 1. 现状

Brain 这一层已经有答案：对话走"推到下一轮"，连发的几条合成一轮（见 `src/brain/runner.ts` 的 `#batch`）。Brain 自己不会被 worker 堵住，新消息来了立刻起一轮。

worker 这一层缺两种处理。一件沙箱任务在跑的时候，模型能做的只有：

| 能做的 | 工具 |
|---|---|
| 直接回答（问进度、问别的） | `work_status`、`send_message` |
| 并行另起一件，互不相干 | `hand_over(continue_from: null)` |
| 停掉 | `cancel_work` |

想"接着正在跑的那件做"会被拒绝（`Tasks.dispatch`：`has not ended yet`）；想往正在跑的任务里加一句话，没有任何通道。

后果是真实使用里会见到的：对同一件事的补充，要么让人等，要么另起一件从头克隆的任务，两件各改各的，互相看不到。

## 2. 用词

行业里这几个动作的叫法基本一致，本文沿用，不另造词：

| 叫法 | 含义 | 出处 |
|---|---|---|
| **steer** | 把话送进正在跑的那一轮；agent 在下一个安全点读到；不中止正在执行的动作，不另起一轮 | pi 的 `steer` 命令、OpenClaw 的 `steer` 模式、Kiro、Copilot SDK |
| **follow-up**（queue） | 等当前这件做完，再作为下一件处理 | pi 的 `follow_up`、OpenClaw 的 `followup` |
| **collect** | 等当前这轮做完，把攒下的几条合成一轮 | OpenClaw 的 `collect`；Anthropic 文章里的 "merge them into a single run" |
| **interrupt** | 中止当前这件，改做最新的这句 | OpenClaw 的 `interrupt` |

Anthropic《Building always-on agents》对运行中来的事件只说了一句："push it to the next run, fold it into the current run, or interrupt and restart"，没有给选择建议，也没有讲后台任务。本文把这三种落到 worker 这一层。

"merge" 一词在业内指 collect（连发合一轮），不指 steer。本文不用它称呼 steer。

## 3. 设计原则

1. **由模型选，代码只保下限。** 新来的话属于哪一种，是判断题，不是规则题。代码保证的是：谁能这么做、做了之后状态是准的、做不成时说清楚为什么。
2. **写在 worker 契约上，不写在沙箱上。** 能不能 steer、能不能排在后面，是 worker 自己声明的能力；Brain 的校验对所有 worker 一样。
3. **复用已有的东西。** follow-up 复用任务接续（`continue_from`、`task_follows`、快照）；steer 复用沙箱里已有的扩展和它回调任务的通道。不引入新的进程模型。
4. **做不成不静默降级。** steer 送不到（任务已结束）就告诉模型，由它改走接续；不在代码里偷偷换一种处理。

## 4. 五种处理

| 意图 | 处理 | 工具 | 结果怎么回来 | 状态 |
|---|---|---|---|---|
| 无关的新事 | **new**：并行另起一件 | `hand_over(continue_from: null)` | 各回各的 | 已有 |
| 不要了 | **cancel** | `cancel_work` | 回一句已停 | 已有 |
| 现在就告诉它 | **steer**：送进正在跑的那件 | `tell_work(work_id, message)`（新） | 只回一次结果，含补充的内容 | 本文 |
| 做完再接着做 | **follow-up**：排在后面，前一件成功后从它留下的工作区启动 | `hand_over(continue_from: <在跑的那件>)` | 两件各回一次 | 本文 |
| 方向错了，停下改做这个 | **interrupt** | 见 §7 | — | 本文不做 |

collect 属于 Brain 这层，已经有，不在本文范围。

模型怎么选，写进部署的指引（`src/workers.md`），由评测盯住（§8）：

- 补充细节、纠正还没做到的部分 → steer。
- "做完之后再……"、明显是下一步 → follow-up。
- 和那件事无关 → new。
- 分不清指的是哪一件 → 问。

## 5. follow-up：排在一件没做完的工作后面

### 5.1 行为

`hand_over` 的 `continue_from` 指向一件**还没结束**的工作时，不再拒绝，而是写下一件新的任务，状态为 `queued`：

- 不占租户的沙箱名额，不启动 worker。
- 记入 `task_follows`（已有的表），与任务同一处写入。
- 可以被 `cancel_work` 取消，在工作列表里显示为"排在 <前一件> 之后"。上限见 5.3。
- 工具当场回给模型 `status: "queued"`，模型据此告诉对方"等那件做完后接着做"。

前一件结束时（`Tasks.event` 收到它的终态汇报）：

| 前一件怎么结束 | 排队的那件 |
|---|---|
| succeeded | 转为 `dispatching` 并启动，走现有的接续路径（worker 向前一件要快照） |
| failed / lost / cancelled | 不启动；记为 failed，原因写明"它要接着做的那件没有做成"，并叫醒一轮，由模型告诉对方、由对方决定 |

排队的那件启动被 worker 拒绝（比如前一件没能留下快照）同样记 failed 并叫醒一轮。

**谁来启动。** 不由模型在"前一件做完"的那一轮里重新交办：排队的那件在写下时已经固定了交办人、worker、options、bounds，系统启动的就是这个已经校验过的编号。也不只靠前一件的终态汇报：本地取消、判定丢失、启动被拒这些结束方式没有那一声汇报。所以由 `settle`（已有的定时收拾）按持久的前一件状态去拾取排队的任务，`event` 只负责让它尽快醒来。前一件没做成时，排在它后面的一串逐级结束。

**启动不堵住 Brain。** `settle` 在 Brain 的 alarm 里先于对话运行，而启动一个 worker（尤其是要恢复工作区的）可能要几十秒。所以这里不等它：把任务转为 `dispatching`、定下获准派发的时间，用很短的时限调一次 `start`。答复了就按答复办（开始了 → `running`；拒绝了 → failed 并叫醒一轮）；没等到答复就留在 `dispatching`，下次 `settle` 用同一个编号再调一次（`start` 本来就对同一编号幂等）。过了 `accept_by` 还没有答复，转入现有的 `unconfirmed`，由那套办法问清楚。

**启动权只在 `settle`。** 排队写下的任务（在 `task_queued` 里有记录的）只由 `settle` 启动：
- 同一次 `hand_over` 调用重放时，只返回它当前的状态，不走启动。
- 一轮运行被放弃时，现有的"把本会话 `dispatching` 的任务转为 `unconfirmed`"（`Runner.#abandon`）不碰它们：它们不属于任何一轮运行。
- Brain 在转为 `dispatching` 之后、答复之前被换掉：任务不在任何一轮运行里，但在 `task_queued` 里，`settle` 下次照上面那条继续，不会永远停在 `dispatching`。

**不经汇报的结束也要往前推。** 取消、判定丢失、启动被拒这些在本地完成的终态转换，凡是那件任务后面排着别的，都立刻安排一次唤醒，不等下一次无关的 alarm。

**取消与启动交错。** 取消一件排队的任务是本地一步完成的，不去停一个还没启动的 worker。"转为启动"和"取消"都用带条件的状态转换，跨过 RPC 之后再看一眼状态。固定的顺序是：先用带条件的更新把 `queued` 转为 `dispatching`（转不动就是已经被取消了，到此为止），再申请名额；名额暂时满，就带条件地转回 `queued`（转不动同样是被取消了）；申请到名额之后发现已被取消，把名额还回去，不启动。取消一件已经是 `dispatching` 的，走现有的停止（它会把那个编号封住，迟到的启动进不来）。

**以前驱的持久终态为准。** 排队的那件看的是它直接接着的那一件（可能本身也在排队）最后落在什么状态，不看有没有收到汇报。`settle` 的下次唤醒时间把排队的重试和到期也算进去，所以前一件在本地结束、或者 Brain 重启之后，队列照样往前走。

**一条线，不分叉。** A 在跑，B 和 C 都说接着 A，会从 A 的同一份快照各开一份，C 看不到 B 的改动。人说"做完再……"时想的是依次做，所以：一件工作后面最多排一件；再来一件，接在队尾那件后面。工作列表里写明每件排在谁后面，模型据此把 `continue_from` 指向队尾；指向已经有后续的那件会被拒绝，并告诉它队尾是哪件。这条核对与写 `task_follows` 在同一个事务里：两个请求同时指向同一个队尾，最多成一个；队尾那件还没启动就被取消了，后面可以再接新的。不做通用的队列调度。

### 5.2 校验

与现有接续完全相同，在写入之前做：worker 声明了 `goes_on`；前一件在本会话、是同一个 worker 的、由同一个唯一明确的交办人交办；本轮是那个人自己的一轮。

区别只有一条：前一件的状态允许是进行中（`dispatching | unconfirmed | running | needs_input | queued`），不再要求 succeeded。因此可以排成一串（一条线，见 5.1）。

排队的那件不继承前一件的长期批准，和现有接续一样。

"一件后面最多排一件"只看**还没结束**的后续：已经结束的任务照旧可以被多件接着做（那是从一份不变的快照各做各的，现有行为）；排着的那件被取消后，后面可以再排。所以不给 `task_follows` 加唯一约束，用查询核对。

排队时给了另一个仓库：现在要等前一件做完、启动时才被 worker 拒绝。没有把这条提前，因为"接着做时哪些 options 必须一致"是 worker 自己的事，Brain 不替它判断；指引里已经要求接着做时仓库留空。实测发现这个晚到的拒绝常见，再给契约加一个"入队时问一下 worker"的口子。

### 5.3 时限与名额

`created_at` 不动，它是交办时间，状态接口、列表排序、审批历史的查询下界都在用。另记一个"获准派发"的时间：拿到名额、真正要去启动 worker 的那一刻才定，只定一次；`accept_by` 和看门狗以它为准，重试不续命。等名额的时间不算在里面（否则等了十五分钟名额，会拿着已经过期的 `accept_by` 去启动）。bounds 仍是写下时固定的那一份（`task_bounds`）。

**看门狗。** 现在任务一写下就设看门狗。排队的任务写下时不设，定下获准派发的时间时才设，否则排着队就会被报超时。

**租户名额。** 启动时才申请。前一件的终态先提交、名额后释放，排队的那件如果抢先申请会碰上"满"。排队是已经答应了人的事，不能因此记失败：名额暂时满时它保持 `queued`，由 `settle` 用同一个编号有界重试；只有"这里根本不许有任务"才是失败。现在申请名额只回答成或不成，要让它把"暂时满"和"上限是零"分开说。本会话的并发上限同理：启动的那一刻再核一次，暂时满就继续排，上限是零才是失败。

**两个上限分开。** 同时在跑的件数（`scope_active_tasks`）和在排队的件数是两回事。排队的不算进前者，否则上限设成 1 时一件都排不进去。排队的件数另有一个小的固定上限。

**排队的期限。** 从它的直接前驱开始跑算起，超过一件任务的寿命上限加一个余量仍没轮到，由 `settle` 记为 failed 并叫醒一轮。前驱自己还在排队的那段时间不算：一条线上每一件各等各的前驱，不把"一件任务的寿命"当成整条线的等待上限。启动的那一刻再核一次本会话的并发上限。

### 5.4 需要存的

- `tasks.status` 多一个值 `queued`。
- 一张自己的小表 `task_queued(task_id, options, started_at, attempts, next_at)`：启动时要用的 options、获准派发的时间、试过几次、下次什么时候再试。用独立的表是为了迁移可以重放；30 天清理时随任务一起清。
- `Tasks.nextWakeAt` 把这张表的 `next_at` 和排队的到期时间算进去，否则没有新消息时 Brain 不会醒，排队的就一直躺着。
- 其余复用现有的 `task_follows`、`op_id`、`task_bounds` 和 alarm。

### 5.5 取舍：另起一件，还是让同一件接着干

pi 自带 `follow_up`：同一个进程做完当前的再处理下一句，不用恢复工作区。没有选它，理由：

- 第一件的结果应当先回给人。同一个进程接着干，结果只在最后回一次。
- 寿命、模型调用次数、审批各算各的，不串。
- 对不是 pi 的 worker 也成立：契约上只要求"能从前一件留下的东西接着做"。

代价是多一次恢复工作区（实测几秒）。

## 6. steer：把话送进正在跑的工作

### 6.1 契约

`Worker` 增加一项可选能力：

```ts
/**
 * 把一句话交给一件正在进行的工作。worker 说清楚结果：
 * taken 表示它收下了，会在下一个安全点交给 agent（收下不等于已经读到，见 6.4）；
 * closed 表示这一轮不再收话。抛错表示不知道有没有收下。
 */
tell?(env, id, note: { id: string; text: string }): Promise<{ state: "taken" } | { state: "closed" }>;
```

`note.id` 是 Brain 那次工具调用的编号：同一个编号再送一次，得到同一个结果，不会存两遍。`closed` 表示这一轮不再收话（已经结束，或者已经过了最后一次取的时机），不等于任务已经有了结果。

没有这一项的 worker 不能被 steer，工具说明里告诉模型哪些可以。

### 6.2 Brain

新工具 `tell_work(work_id, message)`。校验在调用 worker 之前：

- 那件工作在本会话、由同一个唯一明确的交办人交办、本轮是那个人自己的一轮（与接续同一条规则）。
- 状态是 `running` 或 `needs_input`。`queued` 的还没开始，不 steer：改它的 brief 不在本文范围，模型应取消后重新交办。`dispatching` / `unconfirmed` 的回"还没确认开始，稍后再试"。
- worker 有 `tell`。

结果：

- `taken` → 记一条审计（`task.told`，只记任务编号和长度，不记内容），回给模型"已收下，它做完手上这一步会看到"。
- `closed` → 回给模型"这一轮不再收话了；可以排在它后面接着做"，不自动转成 follow-up。

**重放。** 同一次 `tell_work` 调用重放时，先拿它的编号去问 worker 当初的决定，再看任务状态。否则会出现：第一次已经被收下，重放时任务刚好结束，Brain 按状态拦下说"没送到"，模型于是重复派活。审计也只记一次。

**谁能用。** 只有本轮里有会 `tell` 的 worker 时才给模型这个工具；和其他交办工具一样受 `Runner.mayUse` 约束，读过外部文本的那一轮不能用，免得别人写的字被送进正在跑的沙箱。

**那件正等着批准时。** 话是"先别推"这类：送进下一步撤不回一个正在等批准或已经发出的动作。这时该做的是对那个待批准的操作走现有的拒绝，或取消任务。指引里写明，工具回执里也在任务处于 `needs_input` 时提醒这一点。

### 6.3 沙箱：一个取信的回调，取出不消费

**任务侧**（`TaskSandbox`）存本任务收下的 notes，直到任务终态：`{ id, text, at }`，有条数和长度上限；满了明确拒绝新的，不为腾地方丢旧的。

- `tell(note)`：先查这个 `id` 有没有过决定，有就原样返回；否则这一轮还在收话就存下并返回 `taken`，不在收话就返回 `closed`。容器丢了正在恢复的那段时间（任务阶段是 `starting`，Brain 看到的仍是在跑）照常收下，恢复出来的进程会取到。
- `callback("notes", { run, have, final })`，扩展来取：
  - `run` 是这一次进程的执行标识。它在启动进程**之前**就定下、随启动参数交给扩展；任务只认当前这一次的 `run`。旧进程迟到的回调既拿不到话，也关不了门。
  - `have` 是扩展从当前 session 里读到的、本任务已有的 note 编号。
  - 任务一步做差集：收下了但不在 `have` 里的，全部返回。**取出不消费**：回包丢了，下次来取还会拿到。
  - `final` 为真且差集为空，才在同一步里关闭这一轮的收话。此后的 `tell` 得到 `closed`。
  - `final` 为真但任务已经没有余量再走一步（模型调用次数用完，或寿命已到）：不交出，直接关门。否则一件本来已经做完的任务会因为多走的那一步撞上限额而被记成失败，连快照都留不下。没交出的话照 6.4 报告。
- 进程一旦被确认退出（`#settle` 读到退出码，拍最后一份快照之前），立刻关闭收话。否则拍快照的那几秒里来的话会被收下，却不可能再被读到。
- 这个回调每一步都来，不写进任务的事件记录（那里只有两百条的位置，留给审批和错误）。

没有单独的"已交出去"标记，没有启动时的对账通道，也不比较检查点的时间。读没读进 session，每次都由扩展从 session 现报。

**容器侧**（`container/gate.ts`，已有的扩展，已经在用 `http://brain.internal/callback/<kind>` 回调任务）：

- `have` 的来源：`ctx.sessionManager.getBranch()`（当前分支，不是含旁支的 `getEntries()`）里类型为 `custom_message`、带约定的 `customType`、`details.taskId` 是本任务的那些条目的 `details.noteId`。
- 在 `turn_end`（一步的工具调用都执行完之后）取一次；有就投递。
- 在 `agent_before_settle`（agent 准备结束前）带 `final` 取一次；有就投递，agent 会多走一步，然后这个 hook 再来，直到取不到并关门。
- 投递方式只有一种：在这两个 hook 里返回 `custom_message`，`details` 里带 `taskId` 和 `noteIds`。一次取到几句就合成一条。
- 正文带固定的前言：这是交办人在工作进行中补充的话；**你的最后一条回复仍然是整件工作唯一的交付，要包含此前已完成部分的结论，再加上这次补充的结果**。必须写这句：任务的结果只取 agent 最后一条回复，没有它，agent 做完补充后回一句"改好了"，前面那份完整的报告就没了。
- 取的请求有自己的短超时（几秒，不沿用审批回调的二十秒），超时不挡住任务正常进行。最后那次（`final`）多试一两回。
- 进到模型请求里的那条消息要过沙箱出口的白名单（`outbound.ts` 的 `isLocalItem`）。本地实测没有经过这一层，实现时要有测试证明 pi 把 `custom_message` 发出去的样子过得了。
- 不凭 `context.canContinue` 决定取不取（实测正常结束时它也可能是 false）。模型调用出错的那一轮不投递（实测出错时 hook 也会触发，盲投只会再发一次请求）。

选扩展而不是把 pi 改成 RPC 模式，因为现在是一次性进程加文件收尾的模型，检查点、恢复、看门狗都建在上面；换成长驻的 RPC 进程是另一件大事。

### 6.4 "收下"、"进了 session"、"做了"是三件事

`taken` 只表示任务存下了这句话。编号出现在 session 里，表示它已经写进 agent 当前的会话，不表示模型已经照着做了，更不表示做成了。对人说的话按这个分寸来。

| 情况 | 处理 |
|---|---|
| agent 正卡在一个长命令或等审批上 | 命令结束或审批答复后的那一步进 session。对人说的是"已告诉它，它做完手上这一步会看到" |
| 取的回包丢了 | 取出不消费，下次取还在 |
| 话到的时候门已经关了 | `tell` 直接得到 `closed`，模型当场知道，可以排在后面接着做 |
| 最后一次取一直不通；进程被杀、出错退出、被限额或寿命叫停；最后一步没有余量 | 任务不论以哪种终态结束（成功、失败、丢失），都把"收下了但没能确认进 session 的话"随终态报给 Brain；Brain 明白地告诉模型这几句没有送到，由对方决定是否接着做。不能保证"收下了就一定有人读"，能保证的是没读到的一定会被说出来 |
| 进了 session，但那一步模型调用失败、任务以失败结束 | 结果里列明；不把"进了 session"说成"处理了" |
| 容器丢了，从检查点恢复 | 和平时是同一条路：恢复出来的 session 里有的不再投，没有的在下一步投。恢复是新的一次进程，`run` 不同，旧进程的回调作废 |

### 6.5 送达的语义：至少一次，按编号去重

每句话带编号（Brain 那次工具调用的编号），从 `tell` 一路带到 session。接收方的状态就是 session：一句话算不算送到，只看当前这份 session 里有没有它的编号。于是同一句话可能被取多次，但在同一份 session 里只会出现一次。

"至少一次"约束的是**话进会话**。它不让外部动作自动变得幂等：容器恢复后 agent 本来就可能重做检查点之后的那几步，这与有没有 steer 无关。重做一个外部动作对不对，仍按那个动作本身复核（现有的恢复提示让它先看当前状态；推送照旧过审批，批准绑定在具体的前后提交上）。已有的批准不代表动作天然可以重做。

### 6.6 取舍：审批

"只有当初交办的那个人能 steer"是对**谁在说话**的校验，不是一次新的批准。steer 不给任务增加任何它原来没有的许可，也不清掉已有的：

- 单次批准本来就绑定在具体的仓库、分支和前后提交上；长期批准限于原任务、原仓库、已批准分支上的非删除更新。这些限制不因 steer 改变，所以不必一律重新审批。
- 补充的话要求的动作超出这些范围时，照原规则重新问人。
- 排在后面的那件（follow-up）不继承长期批准。

## 7. interrupt：本文不做

"停下，改做这个"现在要两步：`cancel_work` 再 `hand_over`，被取消的任务不留快照，已做的部分丢掉。做成一步要改"什么样的结束可以被接着做"，留待以后。在那之前，纠正方向用 steer。

## 8. 评测

`eval/cases.ts` 增加一组，工作列表里有一件在跑的沙箱任务：

| 场景 | 期望 |
|---|---|
| "顺便把 xx 也改了" | `tell_work` 那件 |
| "等它改完再把单测补上" | `hand_over(continue_from: 那件)` |
| 那件后面已经排了一件，"之后再把文档也更新了" | `hand_over(continue_from: 队尾那件)` |
| 那件正等着批准推送，"先别推" | 拒绝那次批准或取消，不是 `tell_work` |
| "另外帮我看下 <别的仓库>" | `hand_over(continue_from: null)` |
| "算了不用做了" | `cancel_work` |
| "做得怎么样了" | `work_status` 或直接答 |
| 两件都在跑，"把那个也改了"分不清 | 问 |
| `tell_work` 回 closed | 告诉对方没送到，可以排在后面接着做；不假装送到了 |

（沙箱不能开 PR，用例里不出现"提 PR"，免得奖励错的路由。）

steer 的三种顺序必须有测试：取到 A 的回包丢失之后来 `final`；旧一轮的 `final` 晚于恢复和新的 `tell`；`final` 与 `tell` 同时到（先收下的必须被返回，先关门的必须明确得到 `closed`）。

另外要测：做完的任务在最后一步没有余量时不被补充的话拖成失败；合成一条的几句话各自的编号都在；`tell_work` 重放得到当初的答复。

代码测试里优先验收的其余时序：Brain 在排队任务转为 `dispatching` 之后被换掉，下次仍能推进且只启动一次；启动不答复时 `settle` 不被拖住；名额只有一个时的排队与启动；前一件被本地取消或判丢失；取消排队的那件与它被启动交错；终态汇报重复、重启之后仍只启动一次；最后一次取与新来的 `tell` 交错；收下之后容器丢失；补充的话不能扩大原有批准。

## 10. 已经定的

1. **排队是一条线，不分叉**（5.1）。与业界一致：OpenClaw 每个会话一条车道、按先后排；pi 的 follow-up 是先进先出的队列。分叉在这些工具里都是单独的显式操作，不会因为两句话提到同一件任务就发生。
2. **恢复后按编号去重重投**（6.4、6.5）。恢复出来的 session 里没有这句话，就是没进过这份会话，不投就丢了。

## 10.1 实现时改的

实现和实验（`eval/lab/notes.lab.mjs`，真实 pi 0.87.1 加真实的 `container/gate.ts`）之后，相对上文有几处不同，以代码和 `docs/workers.md` 为准：

- **没读到的话只报"几条、什么时候"，不带原文。** 任务的结束会写进会话的共享记录，群里别人的轮次也看得到。原文留在任务里，说的人自己知道说过什么。
- **没有余量时任何一次取信都不交出**，不只是最后一次。交出就会让 agent 多走一步，而那一步会撞上限额，把本来成功的任务变成失败。
- **"已读"按当前这次进程算。** 上一次进程的会话里有，不代表从更早的副本恢复出来的会话里也有；新进程自己报了才算。
- **恢复一开始就废掉旧进程的标识并重新收话**，不等新进程启动。
- **已结束的任务不再接受新的话**：重放一次当初送到过的调用得到当初的答复（凭 Brain 自己的记录），新的调用直接得到"不再收话"，不去问 worker。
- 归还名额另有一张表 `task_releases`：先记账、再在本轮时间内尝试，没确认的按任务编号重试。

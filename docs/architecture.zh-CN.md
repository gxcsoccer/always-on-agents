# 架构

[English](architecture.md) | **简体中文**

## 一段话说清

每个作用域（一个用户、一个群、一个仓库）是一个 Durable Object，叫 Brain。发生的每件事都先写进它的收件箱，再在一次很短的 run 里处理。耗时的事一律交出去，结果以另一条事件的形式回到收件箱。

```
飞书 / GitHub / 控制台 / 定时器 / worker 回报
        │
   入口 Worker             验证、认出租户、确定作用域，立刻返回
        │ ingest()
┌───────▼────────────────────────────────────────────┐
│ Brain（每个作用域一个 Durable Object）                │
│ SQLite: inbox · sessions · items · memory · timers  │
│         · tasks · outbox · runs · audit             │
│         · continuations · answers                   │
│ alarm(): 触发定时器 → 投递发件箱 → 执行 run           │
└───┬────────────────────────────────────┬───────────┘
    │ 派活 / 答复 / 取消                   │ 投递
┌───▼──────────────────────────┐   ┌─────▼──────────────┐
│ TaskSandbox（每个任务一个）    │   │ Connector           │
│ 容器 + 出站代理                │   │ 控制台 · GitHub ·   │
└───┬───────────────────────────┘   │ 飞书                │
    └─ taskEvent(): progress /      └────────────────────┘
       needs_input / result / failed / lost
```

## 五个原语

| 原语 | 落在哪里 | 关键性质 |
|---|---|---|
| 事件收件箱 | Brain 的 `inbox` 表 | 按 `(source, source_id)` 去重；写入成功即确认；每次激活都会检查并补设 alarm |
| 定时器 | `timers` 表，复用对象唯一的 alarm | 到期只往收件箱插一条事件，不直接运行 agent；错过的周期不补发 |
| 记忆 | `memory` 表，按路径存 Markdown | `instructions.md` 和 `index.md` 每次 run 都会加载，分别只加载前 8,000 和前 4,000 个字符，超出的部分不加载；记忆不跨作用域 |
| 权限 | 见[审批](approvals.zh-CN.md) | 由代码判定，不靠提示词 |
| 发件箱 | `outbox` 表 | 在仍待投递的消息之间按顺序投递，失败退避重试，每条消息有幂等键；已经离开队列的消息（已发送、已放弃或不再发送）不会挡住其余的 |

有三样东西建立在这些原语之上。每一样的设计理由见[设计文档](design/agent-core.zh-CN.md)和它的[约定](design/agent-core-step0.zh-CN.md)；connector 需要做什么，见 [Connector](connectors.zh-CN.md)。

**会等待、之后被接着处理的请求。** connector 的工具可以回答“现在还不行”：得先发生一件不归 agent 做的事，比如某个人去授权。Brain 把这个请求保存在 `continuations` 表里，连同之后要再做一次的调用（按工具自己的写法）和它所依据的这个人的原话，然后这次 run 照常结束。“条件可能成立了”的通知，不管来自 connector 还是别处，都只是收件箱里的一个事件、一个去问的理由：Brain 会重新去问拥有这个条件的 connector，条件是否成立、从什么时候开始成立。如果它在截止时间之前就成立了，就由一次单独的 run 把那一次调用再做一遍，并写出一条答复。整个过程有一小时。同样的把关适用于任何一次依据某个条件读过东西的 run，不管是不是接着处理的：读取之后每次调用模型之前、每次要把这次 run 写的消息交出去之前，都会问 connector 条件是否仍然成立。不成立的话，读到的内容不再往前走，并用固定的话告诉这个人：为他写的内容没有发出。在答复第一次交出去之前，这个人可以取消请求或把它换成别的；可能所指的不止一个时，由 Brain 自己问是哪一个。一条回复只有在回复的是工具点明的、请求所依据的消息，或者请求的答复、请求的邀请时，才算是在说这个请求。审批提问是另一种等待，仍按原来的方式保存；管理接口查看作用域时，两种等待以同一种形式列出。

**对人只有一个出口。** 给人看的一切都经过发件箱，包括请他去完成请求所等的那件事的邀请。Brain 手里只有邀请的引用，从不持有它的内容：卡片和其中的链接由 connector 在发送的那一刻生成。绑定在某个请求上的消息，只有在这个请求仍然成立时才会发出，而且不会抢在这个人已经写下、还没被处理的消息前面。一次投递怎样收场，记为四种之一：已发送；从未交出（`void`）；被外部系统拒绝（`dead`）；可能已经送达但无法核实（`unverified`），这种情况下不会再发。在消息之外，connector 还可以在这个人自己的消息上表示“已收到”。

**已送达的答复。** 一次 run 通过 connector 的工具读到的内容，以及它就此说的话，在 run 结束时会从对话记录里移除。运维打开追问功能之后（默认关闭），带着回执送达的答复，如果写它的 run 只读了一样东西、只说了一句话，会在 `answers` 表里单独保存 24 小时，连同它从读到的内容里逐字引用的句子。它只能通过一个工具取回：只给当初收到它的那个人，只在当初的那个对话里，而且要先以这个人的身份把来源重新读一遍，并确认读到的还是原来那样东西；然后模型会被告知保存下来的每个句子是没变、变了，还是无法核实。其中不属于判断的那些决定，是 `src/brain/follow-up.ts` 里的普通函数。这个人的话算不算追问，交给模型判断；可能指的是哪一条答复，由代码限定。

## 作用域和租户

作用域的名字是 `租户:类型:ID`，类型是 `user`、`chat` 或 `repo`。这个名字就是 Durable Object 的名字，所以每个作用域的数据在物理上是分开的。

- 入口 Worker 根据 API key、GitHub 安装或飞书应用登记推出租户，调用方不能自己指定租户。
- 任务 ID 只能在创建它的那个 Brain 的库里查到，拿着别的作用域的任务 ID 什么也做不了。
- 每个作用域和每个租户都有每日 token 额度。用完后该作用域暂停到第二天，不丢事件。

租户、API key 和应用登记存在一个单独的 Durable Object 里，叫 Registry。

## 一次 run

run 只在 `alarm()` 里执行。alarm 不会重入，所以一个作用域同一时刻最多只有一个 run。

1. **认领。** 取最早的一条待处理事件，连同同一会话里其他待处理的事件（数量和大小都有上限）一起认领，创建 run，把这些事件作为一条 user 消息写进对话记录。这些在一个同步事务里完成。
2. **循环。** 对话记录里如果有还没有输出的工具调用，就执行并记录输出；否则调用模型，把返回的内容追加进去。每一步之后状态都已落盘。
3. **结束。** 把事件标为完成，清除当前 run。

**崩溃和部署。** 对话记录就是进度。重新进入同一个 run 时，没有输出的工具调用会被重新执行，所以每个工具的副作用都以工具调用 ID 为幂等键。连续进入五次仍未完成的 run 会被放弃，而放弃这件事不依赖能否通知到任何人。

**为什么不用 Cloudflare Workflows。** Brain 的 run 很短，耗时的活都派出去了。用 Workflow 会多出第二份持久状态，需要和 Durable Object 里的那份保持一致，而“同时只有一个 run”这个保证恰恰会在两者交接的地方被打破。

## 沙箱 worker

每个任务有一个 `TaskSandbox` Durable Object 和一个容器。容器里以无界面模式运行一个 coding agent（[pi](https://pi.dev)）。

**没有网络，也没有凭据。** 容器发出的所有请求都经过 `Outbound`（`src/workers/sandbox/outbound.ts`）：

- *模型接口。* 只放行配置的那个模型和那一个接口。请求大小和每个任务的调用次数都有上限。只允许声明在沙箱内执行的函数工具；对话条目必须是本地 agent 会产生的类型；不能带让服务方去抓取的远程地址。密钥由 Worker 加上。
- *GitHub。* 只放行 git 的智能 HTTP 接口，读操作直接通过。
- *其他一切* 返回 403，并记在任务上。

**推送。** 任务只能推到它启动时指定的仓库。代理把推送请求解析成“哪些引用会移动、移到哪个完整提交号”，人批准的就是这份清单。每个被挂起的请求有自己的编号，答复只能被这一个请求领取一次。挂起的时限由 Worker 一侧强制：到时间，或者挂起方一分钟没有动静，问题就会撤回并通知 Brain。详见[审批](approvals.zh-CN.md)。

**凭据。** GitHub 令牌只借给从该仓库自己的作用域派出的任务，或者从运维方绑定到该仓库的群里派出的任务。使用 GitHub App 时，令牌按安装、按这一个仓库签发，并核对签发结果。推送用的凭据在推送发出的那一刻才取，而不是在等待批准之前。

**回报。** 进度、求批准、结果、失败、丢失都带编号送到 Brain，至少送达一次，Brain 按编号去重。进程退出由包装脚本上报，不依赖模型。

**容器丢失。** 进度回报之后以及每次 alarm 时，任务目录会被备份到 R2（最多每 30 秒一次）。容器没了就起一个新的，还原备份，让 agent 接着原来的会话继续。上一次检查点之后的工作可能会重做。

**部署。** Durable Object 重启时会重新接上容器的出站通道；不这样做的话，容器既调不了模型也回报不了。

**上限。** 启动 5 分钟、空闲 15 分钟、总时长 2 小时、恢复 2 次、模型调用 400 次。每个作用域同时最多 3 个任务，每个租户最多 5 个。任务结束一天后，它的容器、检查点和记录会被删除。

worker 对自己的描述不可信：那只是容器里的一个进程在说话。结果到达 Brain 时会标明“未经验证”。

## Connector

一个 connector 为一个外部系统负责三件事：验证入站请求并把它变成事件；说明是谁引起的、是不是在对 agent 说话；把消息投递出去。Brain 从不直接和外部系统打交道。见 [Connector](connectors.zh-CN.md)。
